## Summary

The pool fix is small in code and large in test surface. The bug (A-CR-02) is exactly one boolean: `src/engine/household/plan.ts:92` sets `pooled = a.scope === 'household' && ...`, so `personalDelta` is null in Just me. A second gate sits one layer up: `householdScope.ts:149` builds the pool only when `hh.scope === 'household'`, `useHouseholdScopeSource.ts:79-80` only fetches partner figures `on ? ... : []`, and the right-answer fixture `fixture.ts:35` repeats the same gate. All three must change together. The correct Just me rule is `count = own + min(0, slice - own)` (a member keeps all their own money unless the pool's slice of them is smaller, in which case they keep only the slice). Because every view then counts at most that member's slice, and slices add up to the pool, the D-05 property holds by construction for any mix of Household / Just me views (proof in "Pool fix"). The published partner figure must be computed WITHOUT the hold-back, or A's figure would depend on B's figure and loop (new pitfall, see P-1).

D-03 over-count is real and is a server problem: opt-ins are per ordered pair (`decide_partner_optins`, PK owner+partner) and `partner_money_total` answers pairwise, so in a 3-person home with A-B and A-C mutual but B-C not, A pools {A,B,C} while B pools {A,B} and C pools {A,C}: the slices add up to more than the money (worked numbers below). A viewer cannot see other people's opt-ins (RLS), so the pool must be computed server-side: one new RPC that returns the one agreed pool (a disjoint partition of mutually opted-in groups, built greedily in join order) with each member's figure and `as_of`.

**P1 answer: NO for pay-ins, no joint-specific projection at all, bills only if the series was explicitly shared.** FA-03 answer: **YES for this month only** (pending outflows on a joint account reach `monthOut`; later months do not). Evidence in "P1 and FA-03".

**Primary recommendation:** Build wave 1 as one engine-first plan (`plan.ts` + `pool.ts` + fixture + property tests) and one server plan (`household_pool()` RPC + publish guard) before any screen; add the new Notices/requests surfaces on a new room-keyed table family (`rooms`, `household_agreements`, `household_asks`, `household_ask_oks`) that never writes to `household_events` for answers, and treat "leaves no row" as a tested invariant (pgTAP + export manifest + delete-account + alert_log purge).

### Pattern 1: Hold-back in every scope (engine)
**What:** `householdPlan` builds `personalDelta` for both scopes. Household: `spendDelta(own, others, spend, myIndex)` (unchanged). Just me: `Math.min(0, spendDelta(...))`.
**Why it is right:** let `s_i` be member i's slice of the pool `P` (slices add up to `P`, `pool.ts:8-9, 186-200`). Household counts `s_i`; Just me counts `min(own_i, s_i)`. Every view counts at most `s_i`, so any mix of views counts at most `sum s_i = P`. A net receiver (`s_i > own_i`) keeps all own money in Just me; a net contributor keeps only `s_i`. The held-back amount is `max(0, own_i - s_i)` and is what "$400 is held back" names.
**Rounding bound:** published figures are rounded DOWN, so `f_i <= own_i`. A's Household slice uses `own_A + f_B`, B's Just me slice uses `own_B + f_A`; with weights `w_A + w_B = 1`, `s_A + s_B <= own_A + own_B` (A-CR-02 failure case: A $0, B $1,000, 50/50: A Household counts $500, B Just me counts min($1,000, 50% of $1,000 = $500) = $500; total $1,000, not $1,400). Staleness (B spends after publishing) breaks the exact bound by at most `w * drift`; that is what D-02 shrinks. The property test states the exact bound for fresh figures and `<= pool + w*drift` for stale ones.
```typescript
// Source: src/engine/household/plan.ts:92 (today) -> proposed
const hasPool = resolved.personal.kind === 'shares' && a.others.some((o, i) => i !== a.myIndex && o !== null);
const personalDelta = !hasPool ? null
  : a.scope === 'household' ? (own) => spendDelta(own, a.others, spend, a.myIndex)
  : (own) => minorUnits(Math.min(0, spendDelta(own, a.others, spend, a.myIndex)));  // D-01: hold back only
```
Free access (`rule: 'shared'`): `resolved.personal` is `BRING` (no pool), so the delta is null in every scope; the joint split is `'whole'` (each member counts the whole joint pot; household totals count it once).

### Pattern 2: One consistent pool (server)
`household_pool()` (security definer, empty search_path like `partner_money_total`): members in join order; greedy: take the first unassigned member m, group = {m} plus later unassigned members x such that opt-in(m<->x) is mutual and x is mutual with every current group member; mark assigned. Return the caller's group with each OTHER member's `rounded_left`, `currency`, `as_of` (skip members with no figure, and name them as "has not published" for the answer). This gives disjoint groups, so no money is claimed by two groups. The existing `partner_money_total` stays for back-compat; `fetchPartnerTotals` moves to the new RPC. pgTAP: 3-user and 4-user matrices (A-B, A-C mutual and B-C not; chain; all mutual; none).

### Pattern 3: Requests that leave no trace
See "Requests: tables, RPCs, RLS, no-trace" below.

### Anti-Patterns to Avoid
- **Writing "Not now"/lapse to `household_events`, `alert_log` (30-day retention, user-readable, in the export manifest) or `settlements`-like status rows.** Use delete-on-answer plus a minimal tombstone that the asker deletes by reading it.
- **Letting `usePublishPartnerFigure` read the same Just me inputs that now carry the hold-back.** The figure would shrink by a function of the partner's figure (feedback loop).
- **Changing `engine/decide/v3` verdict code for OK/limit.** Decoration only.
- **Per-member limits, per-pair opt-in math on the client, any balance in push/Notices text.**

### 12. Pitfalls and the economic-abuse red lines as testable rules
See "Common Pitfalls" and "Red lines as tests" below.

## Common Pitfalls

### P-1: Published figure includes the hold-back (feedback loop)
**What goes wrong:** `usePublishPartnerFigure` builds its figure from `useHouseholdScopeSource(false)` inputs (`:57`). After D-01 those inputs carry the `household-pool` hold-back line, so A's published figure shrinks by a function of B's figure, B's of A's, and the figures chase each other down.
**How to avoid:** compute the figure from inputs with the personal pool taken back out, exactly as `personalPrepared` already does for joint (`jointBack`). Add `personalBack` (or a scope `'figure'` that disables the pool) and a test: publishing figure is independent of any partner figure.
**Warning signs:** published numbers drop every hour with nothing spent.

### P-2: Three consumers of the gate, fixed in one place
`plan.ts`, `householdScope.ts`, `useHouseholdScopeSource.ts` and `fixture.ts` each repeat `scope==='household'`. Changing only the engine leaves Just me with `others` all null (no hold-back, silently). Add one test through `withHouseholdScope` in scope `me` (not only `householdPlan`).

### P-3: Just me must wait for partner figures
Fetching partner totals in Just me makes the answer `pending` (`waiting`, `:91`). Offline or stale figures are read as "not shared" (`freshPartnerTotal`, fail closed for the HOUSEHOLD answer). For the hold-back the safe direction is to use the last cached figure even if old and say how old (as-of line); otherwise a stale/offline Just me answer would silently skip the hold-back. Decide this in O-2; the recommendation is "use any cached figure for the hold-back only, flag age".

### P-4: `whole` is not additive
`jointSlices` sums per-member slices and `zeroShareMembers` sums `cashOf(i)` over members (`zeroShare.ts`). With `whole` both are wrong (double). Provide `jointTotal()` and make every "household total" and the partner-facing figure use it; add a property: `jointTotal` is independent of member count.

### P-5: Event/alert history leaks the no-trace rule
`household_events`, `alert_log`, `alert_outbox`, the export manifest, the undo log (`undo_log`, owner-readable) and TanStack's persisted cache (AsyncStorage) all can keep an ask. Persisted cache: a persisted `household_asks` query keeps an asker's item after delete until refetch; use `shouldDehydrateQuery` to exclude the asks key from persistence (check `src/data/cache/persister.ts` options; `[ASSUMED]` an exclusion hook exists) and do not put asks in `undo_log` (no Undo on Not now).

### P-6: OK expiry and price rules are time-dependent
The 30-day and 7-day windows must use server `now()` (clock skew on phones); the engine takes `now` as a parameter and tests the edges (day 7 +/- 1 s, price equal, price lower, price higher, verdict changed).

### P-7: Request fan-out and push storms

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A member reads another's open check or balance through asks/pool | Information disclosure | audience-scoped RLS; `household_pool()` returns only rounded figures of the caller's own pool; push whitelist |
