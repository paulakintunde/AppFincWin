# Phase 05.1 Plan 31: Owner-local shadow tier and switch-on guard Summary

A `__DEV__`-only dev-menu export of the owner's household snapshot and checks, an env-gated Jest suite comparing today's engine with v3 over that file, and a test that blocks `DECIDE_V3 = true` until the shadow review is marked reviewed.

## Tasks

1. Dev-only export and mount (commit 9281bf47, plus follow-up commit for the lazy mount): `serializeShadowSource` / `parseShadowSource` (format `fincwin-shadow-source` v1; reduced check fields only; the signed-in household only; other formats return null). `ShadowExportDevMenu` registers `DevSettings.addMenuItem('Export Decide shadow source')` only when `__DEV__`, writes `shadow-source.local.json` to the app document directory with expo-file-system and logs the adb fetch command.
2. Local shadow suite and guard: `shadowLocal.test.ts` (`process.env.SHADOW_SOURCE ? describe : describe.skip`) runs `buildDecideSnapshot` + `computeCheck` against `computeV3` per check, asserts a v3 Result for each (I42), refuses a source inside the repo, and writes `shadow-local-report.local.md` beside the source. `switchGuard.test.ts` asserts `DECIDE_V3 === false || approved.reviewed === true`.

## Deviations from Plan

- [Rule 3] The export test is `shadowExport.test.tsx` (not `.ts`) because it renders the menu component.
- [Rule 3] Importing the dev menu statically into `decide.tsx` pulled the Supabase client into the route and broke the existing `DecideComingSoonScreen` test (env validation). The route now requires the menu lazily inside a `__DEV__` branch (Metro folds it out of release bundles, which also strengthens T-05.1-65), and that test mocks the dev menu.
- The report's "cause" column uses v3's own reasons/missing codes rather than the synthetic-data classifier, which needs fixture personas the exported file does not have.
- `v3Settings` is exported as null: no app source for the 05.2 settings exists yet.
