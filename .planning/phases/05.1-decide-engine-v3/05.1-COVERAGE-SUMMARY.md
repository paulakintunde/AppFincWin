## Behaviour-preserving source edits (no behaviour change)

- `bandEdges.ts` `parseRate`: replaced `const [whole = '0', frac = ''] = s.split('.')` with an `indexOf('.')` split. The `whole = '0'` default could never fire (`split` always returns one element). Identical output for every rate string.
- `judge/bands.ts` `layerOfAnswerKey`: replaced `key.split('.')[0] ?? ''` with an `indexOf('.')` prefix. Same reason, same results for every key.

## Mocked tests (real behaviour, unreachable through the public path)

Both files use `jest.mock` to make a callee disagree with its caller so a defensive branch runs:

- `judge/__tests__/judge.fallback.test.ts` mocks `needsInput` to return `[]`. Today `needsInput` and `oneOffPart` both ask for unspent exactly when day one is above this month's room, so judge's own `['unspent_not_confirmed']` fallback and `oneOffPart`'s `needs_input` return cannot be reached via `judge`. The test pins that the fallback still answers `needs_input` with the unspent key.

Each guard's safe behaviour is asserted.

## Bugs found

1. **Fixed: `detectCandidates` ordering depended on input order (I16).** When the same payee appears on two accounts with identical row counts, name, key and anchor date, the sort comparator returned 0, so the output order followed the input order. Fixed by breaking the tie on the first row id (commit `fix(05.1): break candidate ordering ties on first row id`, regression test `month/__tests__/recurring.order.test.ts` fails without the fix: it shuffles and reverses the input). Candidates feed setup offers only (I34), never the verdict.
2. **NOT fixed, outside this task: flaky pre-existing property test.** `v3/__tests__/invariants/monotone.test.ts` "I13 a higher price never makes ready-by earlier" failed once under fast-check seed `-1306121219` (path in the Jest log). Counterexample: Priya-style inputs, `emergency: null`, a 12-month-cadence 18-instalment plan at an APR of `30000000000n` (extreme), price 3,727,926 vs the cheaper price, both `not_yet`, and `readyKey(hi) < readyKey(lo)`. It passed in the other full runs, so the property is seed-dependent and may be a real I13 hole for high-APR long plans (or a `readyBy` kind mix of date vs month). It is unrelated to any edit here (none touch `evaluate`). Worth an owner look before the phase closes.
