# Phase 05.1 Plan 43: Month side of variable and seasonal income Summary

The month layer now reads variable and seasonal earners from their own records: a 12-month window, income swing detection, expected income, lean months and same-season spending, plus the D-58 unseen-pay list that replaces the old 7-day grace guess.

## Rules implemented (for the 05.1-49 owner review)

- **D-33** window: steady 6 months, variable/seasonal 12 (`windowMonthsOf`; `typicalOf({ windowMonths })`). Reason `long_history_window`, notice `history_window_12 { months }`.
- **D-34** swing: exact bigint CV test, `(n*Sum(x^2) - S^2) * 100^2 >= p^2 * S^2`, n >= 3, S > 0 (`incomeCvAtLeast`, `incomeSwings` at 22). `resolvePattern` never relabels a stated pattern; swings set only `treated` and `confirmNeeded`.
- **D-35** expected income: confirmed figure as given (latest `at` wins, unsafe or negative amounts ignored), else only with 12 full months: seasonal = same month last year, variable = second-lowest window income. Money in = max(received, expected) for variable/seasonal. Reason `expected_income_used` when a confirmed figure raised money in.
- **D-36** typical income = median recorded income of the window; each low-month candidate uses its own month's income (still clamped to typicalLeft). Lean = income below window average; `leanLeft` = lowest leftover among lean months (seasonal only).
- **D-37** helpers `dependsOnMonths`, `isLeanMonth`, `leanRun` (for 05.1-44/46).
- **D-39** with 12 full months, everyday still to come uses the same month last year (`e: seasonE ?? typical.e`; `MonthModel.e` stays the typical figure). Reason `same_season_spending`.
- **D-46** notices (after `from_your_figures`, in this order): `history_window_12 {months}`, `income_from_expected {month, amount, source: confirmed|last_year|low, sameMonth?}`, `same_season_compared {lastYear, everyday}`. A steady earner gets none.
- **D-48** `IncomePicture.volatile` = variable/seasonal and window income CV >= `INCOME_VOLATILE_CV_PERCENT` (same `incomeCvAtLeast`).
- **D-58** every unsettled pay occurrence dated before asOf is in `unseenPay {seriesId, date, amount, arrived}`: answered arrived counts as received; answered not yet adds `missed_pay_excluded` and counts nothing; unanswered counts as neither received nor due. Occurrences on or after asOf are due as before. `unseenPay` is present only when non-empty, so steady output with no gaps is unchanged.
