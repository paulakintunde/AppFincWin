## High

### H-01: Cash path counts a pay already received today, so the cash check is optimistic
**File:** `src/engine/decide/v3/cash/path.ts:424-426` (with `src/engine/decide/v3/evaluate.ts:597-617`)
**Scenario:** pay is due on `asOf` and the user has already logged it. `inputs.balance` already contains the money. `buildCashPathV3` then reads `seriesOccurrences(s, asOf, end)`, which is inclusive of `asOf`, and adds `+amount` at index 0. Every point of the 90-day path is overstated by one pay. `paidOccurrences` (evaluate.ts) builds the "already settled" set for `bill` and `debt_payment` only. A shortfall before the next pay is hidden, so `cashCheck` returns `ok` and the purchase fits when cash really dips. This is the verdict-harm direction the project calls out.
**Fix:** include `'pay'` in `paidOccurrences` (match with the same window as `incomeThisMonth`, see M-02) and skip those keys in `buildCashPathV3`:
```ts
for (const s of liveSeriesOf(input.series, asOf, 'pay')) {
  for (const d of seriesOccurrences(s, asOf, end)) {
    if (input.paidThisMonth.has(`${s.id}|${d}`)) continue;
    put(d, BigInt(s.amount));
  }
}
```

### H-02: Early or late pay is double counted (received plus due) in this month's income
**File:** `src/engine/decide/v3/month/incomeProfile.ts:213-228`
**Scenario:** the matcher is `lines.find(l => !used.has(l.id) && l.date >= addDays(occ, -3))`. It has a lower bound only, and bills use a symmetric `abs(daysBetween) <= 3`.
- Pay due on the 31st, received on the 26th (a holiday or weekend shift of more than 3 days). `26 >= 28` is false, so the occurrence is "unmatched". The line is counted in `salaryReceived` and the occurrence is added again to `salaryDue`. Month income is doubled for that pay, `monthLeft` is inflated, and the verdict says "fits".
- Biweekly pay with the first occurrence missed: the day-15 line matches the day-1 occurrence because there is no upper bound. The day-15 occurrence is then "due" again (not yet 7 days overdue), counted again.
**Fix:** use a symmetric window, and match each occurrence to the nearest unused line:
```ts
const match = lines.find(l => !used.has(l.id) && Math.abs(daysBetween(l.date, occ)) <= TWO_DATE_TOLERANCE_DAYS);
```
Consider a wider early window for monthly pay, since banks pay early. Share one matcher between incomeProfile, thisMonth, unspent and evaluate so the four copies cannot drift.

### H-03: `emergencyUntouched` and `emergency_used` can contradict each other, and the Instead "unspent after" differs from the judge's
**File:** `src/engine/decide/v3/instead/futures.ts:503-504` vs `src/engine/decide/v3/judge/judge.ts:593-601, 617`
**Scenario:**
1. A purchase marked emergency, with the ladder using the fund, plus a monthly part that is `monthly_short`. `stricter` makes the code `monthly_short`, and `keepSplit` is true so the split holds an `emergency` segment. The judge emits an `emergency_used` fact, but `insteadFutures` computes `emergencyUntouched = result.code !== 'emergency_use'`, which is true. The same screen then says the fund is untouched while another line says it was used.
2. `buyNow.unspentAfter = unspent - purchase.dayOne` subtracts the full day-one amount. The judge's `unspent_before_after` and line-facts figure subtract only the month and earlier-unspent portions (`dayOne - fromEnvelope - emergencyUsed`). With an envelope or emergency use the two "unspent after" numbers on the same screen differ.
**Fix:**
```ts
emergencyUntouched: !result.facts.some(f => f.code === 'emergency_used'),
unspentAfter: afterFromFacts(result) // read the unspent_before_after fact, or share one helper with the judge
```

## Medium

### M-01: `needsInput` and the month model disagree on an `ended` pay series with `endDate: null`
**File:** `src/engine/decide/v3/judge/needsInput.ts:23-29` vs `src/engine/decide/v3/month/series.ts:479-481`
The owner decided that an ended series with a null `endDate` keeps counting, and `isCounting`, `typicalIncome` and `incomeThisMonth` follow that. `hasConfirmedIncome` returns false for it (`s.status === 'ended'` requires `endDate !== null && endDate >= asOf`). A user whose only pay series is `ended` with no end date gets `no_income_figures` from the judge, while the month model counts the income. The decision is implemented in two ways.
**Fix:** `return isCounting(s, inputs.asOf)` (export it from series.ts), and delete the local copy.

### M-02: Four hand-copied "paid line settles a due date" matchers
**File:** `thisMonth.ts:96-107`, `unspent.ts:704-710`, `evaluate.ts:608-613`, `incomeProfile.ts:213-221`
Three use a symmetric 3-day window with a greedy first-unused match, and one (H-02) uses an asymmetric window. `MATCH_DAYS` is declared three times. The greedy `findIndex` in the first unused line is order-dependent: with two bills of the same series within 6 days, a later line can consume an earlier occurrence. Behaviour is deterministic only because lines happen to be sorted in some paths and not in others (`thisMonth` iterates `input.current.lines` in input order; `unspent` sorts).
**Fix:** one exported `matchOccurrences(occurrences, lines)` helper that sorts both sides and assigns by nearest distance. Define `MATCH_DAYS` in `constants.ts` with a `// Cite:` line (I27).

### M-03: Contract mismatch between engine fact and notice value keys and the en.ts placeholders
**File:** `src/engine/decide/v3/judge/judge.ts:591-605`, `purchase.ts:831-839`, `month/model.ts:407-417`, `judge/lines.ts:115-117` vs `src/i18n/locales/en.ts:2673-2760`
| Code | Engine emits | Copy expects |
|---|---|---|
| `envelope_used` | `amount` | `used`, `name` |
| `quoted_differs` | `computed` | `worked` |
| `implied_rate` | `apr` (the raw scaled Percent as a string, for example `"229000000000"` for 22.9%) | `rate` (a readable percentage) |
| `line_crossed` | `line` = the limit value, `value` | `line` = the line's name, `limit` = the limit, and the sentence says "of your income" for every kind |
| `at_todays_rate` | `currency` | `rate` (the engine has no rate) |
| `deferred_interest_term` | `{}` | `months` |
| `typical_short` | `amount` (negative) | `short` |
| `month_heading_short` | `amount`, `categoryId`, `largest` | `month`, `short`, `line` |
| `month_left_after` | `left` | `month`, `left` |

`line_crossed` for `single_purchase_cap`, `category_monthly_cap` and `unspent_floor` carries a money value, and the copy sentence "to {{value}} of your income" is wrong for those. The copy is marked "05.3 rewrites", but the engine contract is declared FIXED after 05.1-16, so the keys should be settled now. `implied_rate` leaks a scaled bigint string into a user-facing slot.
**Fix:** decide one key set in `types.ts` (document per FactCode in `CodeValues`), emit a readable decimal for `apr` (reuse `percentText` from inputsV2, exported), and add a barrel test that every `{{placeholder}}` in en.ts for a fact or notice is a key the engine emits.

### M-04: `readyMonth` has no upper bound, so `readyBy` can be a malformed year-month
**File:** `src/engine/decide/v3/judge/judge.ts:433-438`
`n = ceilDivide(gap, typicalLeft)` is unbounded. With `typicalLeft` of 1 minor unit and a price of 10^12 the result is 10^12 months. `addYearMonths` then returns `"83333333-04"` (the `padStart` does not truncate) and downstream `until > \`${ready.month}-01\`` compares malformed strings. `futures.buyLater` caps at `SIMULATION_MONTH_CAP`; the judge does not.
**Fix:** return `null` (or a `'beyond_range'` reason) when `n > SIMULATION_MONTH_CAP`, matching `buyLater`.

### M-05: A fractional `unsecured_multiple.times` throws out of `evaluate`
**File:** `src/engine/decide/v3/judge/lines.ts:149` (`BigInt(spec.times)`), `types.ts` (`times: number`)
`LineSpec.times` is any number. `lineSpecOf` in buildV3Inputs and `legacyLimits` force an integer, but `evaluate()` is a public barrel export and `validateLimits` does not check `times`. `BigInt(2.5)` throws a RangeError. `buildPurchase` catches RangeError but `evaluateLines` runs in `judge`, which does not, so one bad own line takes down the whole Decide result.
**Fix:** validate in `validateLimits`, and make the line evaluation total (`Number.isInteger(spec.times) ? ... : return null`).

### M-06: Cash includes savings accounts but a transfer to savings subtracts from unspent
**File:** `src/features/decide/snapshot/v3/buildV3Inputs.ts:61, 289-292` vs `src/features/decide/snapshot/buildSnapshot.ts:221`
`cashLike` (the old builder's `cash`, used as `balance`) is `cash | checking | savings`. `SPENDING_KINDS` is `cash | checking` only. A checking-to-savings transfer is a `saved_invested` line, which `rollForward` subtracts from the user's unspent figure. The money is still in `balance`, so `suggestedUnspent` (balance minus bills minus Erest minus envelopes minus emergency) does not drop. The rolled figure falls and the suggested one does not, so every user with a normal savings account and a move into it gets a `drifted` notice and `rough` confidence (`judgeConfidence` caps drift at `rough`). It also contradicts D-22's partition (I17).
**Fix:** either exclude savings from `balance` when building v3 inputs (and treat only tagged pots and the reserve as separately held), or subtract the untagged savings balance in `suggestedUnspent`. Add a snapshot-level test of a user with savings.

### M-07: Negative unspent anchor, reserve or other signed figures are dropped as "not set"
**File:** `src/features/decide/snapshot/v3/buildV3Inputs.ts:71, 358, 360`
`moneyOf` rejects `x < 0`. A user can honestly confirm a negative unspent figure (overdrawn, card owed), and the engine models negative unspent (`suggestedUnspent` "may be negative"). That value silently becomes `unspent: null`, so the verdict is `needs_input: unspent_not_confirmed` with no way to resolve it.
**Fix:** a separate signed parser for `unspent_anchor` (bounds `-MAX..MAX`).

### M-08: Purchase question library double counts or flips the sign of amounts also modelled elsewhere
**File:** `src/engine/decide/v3/judge/presetQuestions.ts:1033-1037` (`sales_tax`, `trade_in`, `deposit`), `judge/purchase.ts:778-785`
Every `one_off` answer is added to `oneOffExtras` as a cost. `trade_in` is a credit, but it increases day-one cost, while `pay.tradeIn` reduces financed. `sales_tax` duplicates `taxPercent` and `deposit` duplicates `pay.deposit` (which `upfront` already adds). If the UI asks both, day one and the cash path overstate. Per I36 these amounts are user typed, so the engine should not accept two routes for one fact.
**Fix:** give the library entries a `sign`/`role` (`cost` / `credit` / `informational`, with `cash:false` for ones modelled elsewhere), or remove the duplicates from the question library.

### M-09: `customOf` discards all custom options when any one entry is invalid
**File:** `src/features/decide/snapshot/v3/buildV3Inputs.ts:155`
`validateCustomOptions(out).length === 0 ? out : EMPTY_CUSTOM`. A single entry with an empty own-question label, an eleventh cadence or one cadence with `every: 13` wipes every custom item type, purpose and income kind. Saved checks that used a custom item type resolve to `general` with `custom_option_missing`, and custom income kinds fall to `income_kind_unmarked`, changing numbers for an old decision (violates the I42 spirit).
**Fix:** drop only the invalid entries and keep the rest. Truncate lists to `MAX_CUSTOM_OPTIONS`.

## Low

### L-01: Deferred first payment: saved plans break silently
**File:** `src/engine/decide/v3/plan/schedule.ts:278-280`, `judge/purchase.ts:733-738`, `adapters/inputsV2.ts:574`
A `deferred` plan with a `firstDate` that has passed since it was saved makes `buildSchedule` throw a RangeError. `buildPurchase` converts that to `nothing([], ['exceeds_range'])`. The judge then reports `no_price` ("A price is needed first") for a check that has a price. `DATE` in `firstPaymentOf` is also a format regex, not `isValidLocalDate`, so `2026-02-31` is accepted and fails later the same way.
**Fix:** validate in `parseCheckV2` with `isValidLocalDate`, and surface a distinct missing code (`first_payment_passed`) rather than `no_price`.

### L-02: `parseCheckV2` claims totality but passes `layerAnswers` through unvalidated
**File:** `src/engine/decide/v3/adapters/inputsV2.ts:650`, `judge/bands.ts:347-358`
`visibleLayerAnswers` calls `layerOfAnswerKey`, which throws a RangeError for any key without a layer prefix. A stored check with a stray key crashes the first reader.
**Fix:** drop keys that do not validate in `parseCheckV2`, or make `visibleLayerAnswers` skip them.

### L-03: Cash path and ladder can differ by one minor unit under a household share
**File:** `src/engine/decide/v3/judge/purchase.ts:880-891`
`dayOne = myPart(upfront)`, and `purchaseCashFlows` subtracts `myPart(payment)` per payment then `purchaseFlows` re-adds `myPart(payment)`. `myPart(a+b)` is not `myPart(a)+myPart(b)` after rounding. Also clamps at 0, hiding any negative remainder.
**Fix:** subtract at the `upfront` level before applying `myPart` once.

### L-04: `explore` does not clamp `everydayCut`
**File:** `src/engine/decide/v3/instead/explorer.ts:362-365`
`flexibleSavingCut` is clamped to the flexible saving; `everydayCut` can exceed E, so `typicalLeft` can rise by more than the user spends (negative spending).
**Fix:** clamp to `month.e` and set `clamped`.

### L-05: Candidate anchor is the last observed date, so month-end bills drift
**File:** `src/engine/decide/v3/month/recurring.ts:719-727`
`anchorDate: last.date`. Rows on 31 Dec, 31 Jan and 28 Feb give an anchor of 28 Feb, so future occurrences land on the 28th for ever (clamping is computed from the anchor), up to 3 days early. This is within `MATCH_DAYS` only for part of the pattern.
**Fix:** anchor on the modal day of month, or the latest date with the largest day-of-month among the rows for `unit: 'month'`.

### L-06: Non-deterministic or locale-dependent ordering
**File:** `month/series.ts:558` (`a.date < b.date ? -1 : 1` returns 1 for equal dates, so ties follow input order and the "latest" amount can differ), `month/series.ts:575`, `month/incomeProfile.ts:211` (`localeCompare` on ISO dates is locale-dependent under Hermes/Intl)
**Fix:** a shared comparator that tie-breaks on `id` and uses `<`/`>` on strings.

### L-07: Float arithmetic on display ratios
**File:** `src/engine/decide/v3/judge/lines.ts:150` (`Number(...) / 10`), `instead/futures.ts:508` (`months / 12`)
Not money, so low. Emit integer tenths and let the UI format it, to keep the "no floats" rule easy to audit.

### L-08: Shadow export gaps
**File:** `src/features/decide/dev/ShadowExportDevMenu.tsx:573, 578`, `shadowExport.ts`
- `v3Settings: null` is hard coded, although the file header and `ShadowSourceFile.v3Settings` promise the owner's v3 settings. The parity run therefore cannot cover the v3-only inputs.
- `DevSettings.addMenuItem` is registered with no cleanup, so a remount or fast refresh adds duplicate menu items.
- The file is written into `Paths.document` with real financial data (no secrets), `__DEV__`-gated and git-ignored, as required. The adb hint only works on a debuggable build; fine for dev.

### L-09: Misc
- `plan_total` is in `FactCode`, `FACT_KEYS` and en.ts but never emitted (dead contract). `judge/needsInput.ts:35` counts bill payments (`role: 'spending'` with a bill `seriesId`) as the "newest spending entry", which suppresses `records_look_behind`. `needsInput.ts:49` ignores the linked envelope, so an envelope-covered purchase can still ask for unspent. `buildV3Inputs.ts:381` hard codes `unsavedWrites: 0`. `buildV3Inputs.ts:279-280` uses unchecked casts (`rowById.get(...) as NonNullable`, `legsOf.get(...) as Row[]`) that throw a TypeError if a transfer line's row is missing or deleted. `judge/bands.ts` treats `whole === edges[0]` as band 2 but `whole === edges[i]` (i>0) as the lower band; confirm with O11. `withPayment` (purchase.ts:701) overstates total paid when a quote exceeds the computed payment, because `lastPaying` is not recalculated for the larger payment (conservative direction). `computeV3.checkOf` does not convert a stored v2 check typed in a foreign currency.
