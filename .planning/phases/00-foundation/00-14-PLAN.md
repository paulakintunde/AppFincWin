5. `docs/ops/ota-policy.md` (FND-11, Claude's Discretion):
   - Policy: `runtimeVersion: { policy: 'fingerprint' }`. The runtime version is a hash of the native project, so any native change (new module, config plugin, SDK bump) produces a new runtime. Updates only reach binaries with a matching fingerprint. JS-only fixes go out as `eas update`; native changes need a new store build.
   - Channels: development / preview / production map 1:1 to the build profiles, with the branch name equal to the channel name.
   - Publish: `eas update --channel production --environment production --message "<why>"`.
   - Roll back a bad update: (a) republish the last good group: `eas update:list --branch production --json --non-interactive`, then `eas update:republish --group <last-good-group-id> --message "rollback: <reason>"`; or (b) `eas update:roll-back-to-embedded --branch production --runtime-version <fp>` to send users back to the JS embedded in their binary. Clients pick up the rollback on next launch (`checkAutomatically: ON_LOAD`).
   - Staged rollout option: `eas update --rollout-percentage 10` for risky changes. Confirm the flag exists in eas-cli 24.7 and omit it if not.
   - Compatibility rule: server/schema changes must stay compatible with the oldest supported app version; raise `app_config.min_supported_version` by migration when that is no longer possible (D-25, FND-09).
