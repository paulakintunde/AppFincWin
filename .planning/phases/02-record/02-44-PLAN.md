<open_questions_answered>
- Decision "Open for planning" item 2, cross rates via the EUR base when neither currency is EUR: every stored rate is EUR-based (fx_rates.base = 'EUR'). For a GBP line in a USD-home profile, the date's single upstream request is `GET https://api.frankfurter.dev/v2/rates?date=D&base=EUR&quotes=GBP,USD`, and both legs are stored as EUR->GBP and EUR->USD. The conversion is the existing cross through per-EUR rates (SQL `convert_minor_exact` at stamp time, TS `convertMinor` for cached reads), unchanged. An EUR leg needs no fetch. A custom-currency leg fetches its reference currency (existing `resolveQuote`). A leg already covered for that date is left out of the request (`fx_quotes_needing_fetch`).
- Plausibility with sparse data (planner choice): Phase 1 WR-B04 compared against the nearest prior of ANY age. That was safe while fx-sync stored every day. With on-demand storage the nearest prior can be months old, and a legitimate move (ARS, NGN) would be held on most fetches. `PRIOR_WINDOW_DAYS = 7`: history older than 7 days before the row's date is dropped before `classifyRates`, so "no prior within a week" accepts. This matches MON-11's "day-on-day" wording.
- Holds and "alert only on fetch failure": a held value means the fetch produced no usable rate, so it counts as a failed fetch. It writes the existing 'held' alert and triggers the email. Its row stays rate_pending, and the lazy `fx_auto_accept_holds()` accepts it after 2 days (D-12), or the operator drops it (fx_drop_hold, unchanged). 'fallback-used' alerts are NOT written any more: a successful fallback is not a failure, and its attribution still reaches the row via rate_source.
- Alert kind for fetch failures: reuse the existing `'sync-failed'` kind with `detail.via = 'resolve-rate'`, so no constraint migration is needed. Dedupe: skip the insert when a 'sync-failed' alert for the same (detail.date, quotes) exists in the last 24 hours.
- Email: the Resend secrets (`RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `FX_ALERT_TO_EMAIL`) are project-wide function secrets already set for fx-monitor (docs/dependency-register.md). resolve-rate reads them. If any is missing it skips the email silently, and the alerts stay queued with emailed_at null.
</open_questions_answered>
