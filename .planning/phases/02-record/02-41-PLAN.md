<objective>
Make server-side FX stamping work without a daily rate feed. Record what each on-demand fetch learned (`fx_rate_lookups`) and which fetches recently failed (`fx_rate_fetch_failures`). Stamp exact only when the line's own date is covered, and stop requiring a currency to already have a stored rate.

Purpose: decision `02-DECISION-fx-on-demand.md` items 1, 3, 4 and 6. Today `per_eur_rate()` treats any stored rate up to 7 days earlier as exact. With sparse on-demand storage, a 5-day-old rate stored for someone else's line would count as "this date's rate", and the line's own date would never be fetched. `is_iso_currency()` (behind every account/transaction/series/home-currency guard) requires a currency to already appear in `fx_rates`, which on-demand fetching would turn into "reject any currency nobody used yet".
Output: one forward migration (`20261007000400`), a new pgTAP file, existing pgTAP files adjusted only where they encoded the superseded 7-day exact window.
</objective>

ANSWER: redefine it to accept EUR, the ACTIVE block of the ISO 4217 array already in `is_iso4217_code()` (copied verbatim from 20260924000100, the lines under `-- active (ISO 4217, 2025)`), and any code already in `fx_rates` (so nothing valid yesterday becomes invalid). - `public.currencies` is read server-side only by `guard_custom_currency()`'s shadow check (kept; the table is frozen once fx-sync goes) and by fx-sync/fx-monitor (removed). Nothing here writes it.
- `currency_exponent()` and `src/engine/money/currencyExponents.ts` read no table; the money mirror (07, `scripts/gen-money-mirror-test.mjs`) reads neither table. Unchanged.

Planner choices (needed to honour "uses the line's own date" and to keep MON-11's hold working without a cron):
- Coverage: an earlier-dated stored row is exact for `p_on` only when `fx_rate_lookups` records that a fetch for `(quote, p_on)` returned exactly that `rate_date`. A lookup is FINAL when `requested_date <= (fetched_at at time zone 'UTC')::date - 2`. A non-final lookup counts only while `fetched_at > now() - interval '1 hour'`. The fetching row itself is always stamped exact through the existing relax path, so a user never waits for the hour.
- Held rates (checker warning 9): resolve-rate (02-44) writes the lookup for a held value as well. Coverage requires the referenced `rate_date` row to exist in `fx_rates`, so the lookup is inert while the value is quarantined. It starts covering as soon as the hold is confirmed or auto-accepted and the row lands in `fx_rates`, with no extra fetch. A dropped hold's row is deleted, so its lookup is inert again.
- Negative cache (checker warning 10): `fx_rate_fetch_failures(quote, requested_date)` with `failed_at`. `fx_quotes_needing_fetch` omits a quote whose failure for that date is younger than 6 hours. resolve-rate deletes the failure row when a later fetch succeeds.
- The 7-day window survives only as the preference order for a PROVISIONAL value. It no longer makes anything exact.
- Migration order (checker warning 13): this file is `20261007000400`. Plan 02-42's retire-jobs migration takes the earlier `20261007000300`, so a production push that stops after the end_date fix (`20261007000200`) and the retire step can never leave fx-sync re-writing currencies. No `min_supported_version` raise is needed: nothing here drops or renames a table or column, and every old-client read path (`currencies` select, `fx_latest_rates`, resolve-rate `{transactionId}`) keeps its shape.
</open_questions_answered>

New contract (plan 02-44 codes against it):
```sql
create table public.fx_rate_lookups (
  base char(3) not null default 'EUR' check (base = 'EUR'),
  quote char(3) not null check (quote ~ '^[A-Z]{3}$'),
  requested_date date not null,
  rate_date date not null,
  source text not null check (source in ('frankfurter-v2', 'open-er-api')),
  fetched_at timestamptz not null default now(),
  primary key (base, quote, requested_date),
  check (rate_date <= requested_date)
);
create table public.fx_rate_fetch_failures (
  base char(3) not null default 'EUR' check (base = 'EUR'),
  quote char(3) not null check (quote ~ '^[A-Z]{3}$'),
  requested_date date not null,
  reason text not null check (reason in ('both-sources-failed', 'no-usable-rate', 'held')),
  failed_at timestamptz not null default now(),
  primary key (base, quote, requested_date)
);
public.fx_rate_covers(p_quote text, p_on date, p_rate_date date) returns boolean     -- stable, security definer, service_role only
public.fx_quotes_needing_fetch(p_quotes text[], p_on date) returns text[]             -- stable, security definer, service_role only; sorted, distinct, never 'EUR', omits quotes failed < 6h ago for p_on
```
resolve-rate (02-44) upserts lookups with `onConflict: 'base,quote,requested_date'` (updating rate_date, source, fetched_at), upserts failures with `onConflict: 'base,quote,requested_date'` (updating reason, failed_at), and deletes the failure row on success.
