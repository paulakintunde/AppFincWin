<objective>
Make server-side FX stamping work without a daily rate feed: record what each on-demand fetch learned (`fx_rate_lookups`), stamp exact only when the line's own date is covered, and stop requiring a currency to already have a stored rate before it can be used.

Purpose: decision `02-DECISION-fx-on-demand.md` items 1, 3, 6. Today `per_eur_rate()` treats any stored rate up to 7 days earlier as exact. That was right while fx-sync stored every publication daily. With on-demand fetching, stored rates are sparse. A 5-day-old rate stored for someone else's line would be treated as "this date's rate", and the line's own date would never be fetched. Separately, `is_iso_currency()` (behind every account/transaction/series/home-currency guard) requires a currency to already appear in `fx_rates`. Under on-demand fetching that would reject any currency nobody has used yet.
Output: one forward migration, a new pgTAP file, and existing pgTAP files adjusted only where they encoded the superseded 7-day exact window.
</objective>

Decision record "Open for planning" item 1 (who else reads `currencies` / `fx_latest_rates`), server side:
- `is_iso_currency(p_code)` reads `fx_rates` (`p_code = 'EUR' or exists (select 1 from fx_rates where quote = p_code)`). It is called by `is_known_currency()`, which guards `accounts.currency` (20260924000300), `transactions.original_currency` (20260924000400), `recurring_series.currency` (20260926000300), `profiles.home_currency` (20260924000200), and custom-currency `reference_currency` (20260924000100). ANSWER: redefine it to accept EUR, plus the ACTIVE block of the ISO 4217 array already in `is_iso4217_code()` (copied verbatim from 20260924000100, the lines under `-- active (ISO 4217, 2025)`), plus any code already present in `fx_rates`. The last clause keeps every code that was valid yesterday valid today. Withdrawn codes (DEM, FRF, …) are NOT accepted. Plan 02-45's parity test asserts the app's built-in list is a subset of that same active block.
- `public.currencies` is read server-side only by `guard_custom_currency()`'s shadow check, by fx-sync and by fx-monitor. The shadow check stays as is (the table is frozen after fx-sync is removed, and `is_iso4217_code()` is the floor anyway). Nothing in this plan writes to `currencies`.
- `currency_exponent()` (SQL) and `src/engine/money/currencyExponents.ts` hard-code the exponent exceptions and read no table. The money mirror (07 test, `scripts/gen-money-mirror-test.mjs`) does not read `currencies` or `fx_rates`. Neither changes here.

Planner choice (beyond the decision's text, needed to honour "uses the line's own date"):
- Coverage: an earlier-dated stored row is exact for `p_on` only when `fx_rate_lookups` records that a fetch for `(quote, p_on)` returned exactly that `rate_date`. A lookup is FINAL when `requested_date <= (fetched_at at time zone 'UTC')::date - 2`, which covers every time zone and ECB's afternoon publication. A non-final lookup counts only while `fetched_at > now() - interval '1 hour'`. After that, the next line for that recent date goes pending and its follow-up re-fetches, so a later same-day line can pick up the day's real publication. The fetching row itself is always stamped exact via the existing relax path, so a user never waits for the hour.
- The 7-day window survives only as the preference order for a PROVISIONAL value. It no longer makes anything exact.
</open_questions_answered>

New contract this plan creates (plan 02-44 codes against it):
```sql
create table public.fx_rate_lookups (
  base char(3) not null default 'EUR' check (base = 'EUR'),
  quote char(3) not null check (quote ~ '^[A-Z]{3}$'),
  requested_date date not null,
  rate_date date not null,
  source text not null check (source in ('frankfurter-v2', 'open-er-api')),
  fetched_at timestamptz not null default now(),
  primary key (base, quote, requested_date),
  check (rate_date <= requested_date)
);
public.fx_rate_covers(p_quote text, p_on date, p_rate_date date) returns boolean          -- stable, security definer, service_role only
public.fx_quotes_needing_fetch(p_quotes text[], p_on date) returns text[]                  -- stable, security definer, service_role only; sorted, distinct, never contains 'EUR'
```
resolve-rate (02-44) upserts lookups with `onConflict: 'base,quote,requested_date'`, updating rate_date, source and fetched_at.
