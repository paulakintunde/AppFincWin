<open_questions_answered>
- Which currencies count as "already used": the union of `accounts.currency` (fetchAccounts; archived accounts included, since their balances still convert), the line currencies from the existing `account_balances(p_household_id)` RPC (one row per account x original_currency over transactions_active, so there is no full table scan from the client), and `recurring_series.currency` (fetchRecurringSeries). Codes are deduped and sorted, and the new home currency is removed. Custom codes are passed through as-is; resolve-rate resolves them to their reference currency.
- Which date: the device-local today (`localDateIn(new Date(), getDeviceTimeZone())`, the same as useRecordContext's `today`), captured when the change is made. A queued offline change therefore asks for the day the user made it, not the day it flushed.
- Whose household: the cached household id (`queryKeys.household(userId)`). If it is not cached, the helper skips the call and records an outstanding check without a household; the sweep resolves the household then.
- Size: requestRatesForDate takes at most 50 codes (02-44/02-46 contract). More codes are split into chunks of 50, and each chunk counts as one call against the 60/hour limit.
- Device-region default (useSetHomeCurrencyIfDefault): it runs the same helper when it actually applied. For a brand-new user the used set is empty, so no call is made.
</open_questions_answered>
