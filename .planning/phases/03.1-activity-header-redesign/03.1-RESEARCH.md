## Summary

This is a pure presentation refactor of one file's `listHeader` plus the shared compact header. Every data source already exists. The current header (ActivityScreen.tsx lines 225-301) renders, in order: `chrome.largeHeader` (title + sync line; **no eyebrow is passed today**), `UnpaidBanner`, `ActivityHeader` (MonthSwitcher row, `MonthTotalsBar`, a pills row of ViewDropdown / SortDropdown / MoreMenu), a balance note, an Accounts/History links row, `SearchBar`, a tools row (Filter chip, Select all / None while selecting, Select/Done pill), and `SeriesOfferCard`. All state is in `useActivityViewModel` (month, term, scope, filter, view, sort, selection, balanceHeader, monthTools, offers) except `filterOpen`, `hint`, and `confirmOpen`, which are local `useState` in `ActivityScreen`.

Three real gaps versus what the UI-SPEC assumes: (1) the VM exposes `totals` (filter-dependent) but no `monthPosition`; the summary card must compute `monthPosition(monthView.totals, figureRows, figureProjections)` exactly as `useHomeViewModel.ts` lines 66-87 does (the VM already exposes `monthView`), using the unfiltered month data so Home and Activity agree; (2) `useTabRootChrome` / `CompactHeader` have no trailing slot, no separate compact title, and the compact title is hard-coded to the `heading` role (UI-SPEC wants `sheetTitle` 16/600 for Activity), and `showAvatar` exists on `CompactHeader` but is not plumbed through the chrome; (3) rows have no long-press, and the project has no `@gorhom/bottom-sheet` (see below), so "reuse the sheet pattern" means the app's own `Sheet`.

Roughly 30 existing assertions across 6 test files depend on the old header and must be rewritten; there is no Maestro suite in the repo (no `.maestro/`, no yaml flows, nothing in `package.json`), so device/E2E checks are manual acceptance docs under `docs/acceptance/`.

**Primary recommendation:** Build bottom-up in this order: (a) new leaf components with their own tests (glyphs, `HeaderIconButton`, `FilterChipRow`, `ActivitySummaryCard`, `DisplaySheet`, `ActivityMoreMenu`, `SelectBar`), (b) a small pure helper module for filter-chip labels / active-filter count / clear-one-filter (unit-testable, no React), (c) chrome changes (`compactTrailing`, `compactTitle`, `showAvatar`), (d) recompose `ActivityScreen.listHeader` and rewrite the six affected test files in the same plan as the recompose, (e) device checks.

### Pattern 2: Compact header plumbing
`useTabRootChrome` today passes only `title` to `CompactHeader` and the same `trailing` to `TabHeader`. Needed, additive and backward compatible (other tabs pass nothing):
- `TabRootChromeOptions`: `compactTitle?: string`, `compactTrailing?: ReactNode`, `compactShowAvatar?: boolean` (or derive `showAvatar = compactTrailing === undefined`).
- `CompactHeader`: render `compactTrailing` before/instead of the avatar; allow a `titleRole?: 'heading' | 'sheetTitle'` (today hard-coded `heading`, spec A2 wants `sheetTitle` 16/600 for Activity only). `CompactHeader` already has `showAvatar?: boolean`.
- Existing tests that guard this: `src/shell/header/__tests__/headers.test.tsx` (testID `compact-header`, lines 143/151), `src/shell/screen/__tests__/TabRootScreen.test.tsx` line 47, `TabHeader.fontScale.test.tsx`. Keep Home's behaviour byte-identical.
- The compact title is the screen-reader focus target when visible (`focusRef` in `useTabRootChrome`); the title ref must stay attached.
- Compact Search must `scrollTo` 0 first: `chrome.scrollRef` is an Animated ref; the Calendar path already does `(chrome.scrollRef.current as unknown as ScrollView | null)?.scrollTo(...)` (ActivityScreen line 324) and for the FlashList use `scrollToOffset`. The two paths need different calls; wrap in one `scrollToTop()` helper and test both.
- `compactThreshold` is computed from the large header's measured height, which is now just title + sync line (month row etc. are in the list header after `chrome.largeHeader`). So the compact header will appear while the month row, card and chips are still on screen under it; the icons will momentarily exist twice (month row and compact header). Both are live but the month row will be underneath the absolute compact header. This is acceptable (UI-SPEC accepts it) but a11y: the compact header sets `accessibilityElementsHidden` while invisible, so no duplicate announcement when at the top.

### Pattern 3: Search cross-fade
Absolutely overlay the two layers (UI-SPEC), reserving month-row height so the list does not jump. `searching` mode flag is new UI state (call it `searchOpen`); note existing VM `searching` means "term non-empty" and is a different thing (used for empty states and offers). Name them distinctly to avoid a bug. Under Remove animations use duration 0: `ReducedMotionConfig` is mounted globally (motion.ts comment) so Reanimated timings already collapse, but for a plain conditional render use `useReduceMotion()`. Keep the focus handling: on open focus the `TextInput` (SearchBar needs an `autoFocus`/ref prop, today it has none); on Cancel focus the Search icon (`a11yFocus.focusAccessibility`, see `src/shell/a11yFocus`).

### Pattern 4: Long-press to select
`ActivityRow` wraps content in `SwipeRow` (`onPress` renders `<Pressable onPress>` at SwipeRow line 124) with an inner `Pressable` at ActivityRow line 206. Neither has `onLongPress`. Add `onLongPress?: () => void` to `SwipeRow` and to `ActivityRowProps` (not `selectable` guarded: long-press when already selecting should do nothing). Add a named custom accessibility action "Select" (key `a11y.selectRow` exists; SwipeRow builds `accessibilityActions` from `left/right/onPress`, so add a fourth entry). Long-press must (1) `selection.enter()` and (2) `selection.toggle(row.id)` in one batch; not offered in Calendar (the calendar renders rows via `renderRow` so wire it only in the list path or pass undefined in Calendar). Gesture risk: Reanimated `Swipeable` + a long-press `Pressable` can fight; verify on device (Pixel). Mark as a device-only risk.

### Anti-Patterns to Avoid
- **Putting count/figure maths in the component.** Use engine outputs only.
- **Computing the card from `vm.totals`** (filter- and search-dependent). The card shows the month; see Pitfall 2.
- **Hard-coded colours/sizes.** `noRawColours.test.ts` fails the build; use tokens and `layout.ts` sizes. The 4px and -2px offsets are declared one-off exceptions in the UI-SPEC; check `noRawColours` only scans colours (it does by name) but also check whatever "no magic number" lint exists (`eslint.config.js`).
- **Adding `UNSAFE_*` RNTL queries** (project rule).
- **`expo-haptics` old method names.** Only `hapticSelection()` from `@/ui/haptics` is used by Dropdown; no haptics are added in this phase.

## Common Pitfalls

### Pitfall 1: Old a11y labels the tests (and users) rely on are removed
**What goes wrong:** `getByLabelText('Filter')` with `.props.accessibilityState.selected` is used in `ActivityScreen.test.tsx` (449-455) and `unpaidFocus.test.tsx` (193/198/255/265) to detect "filter active". The new Filter icon has no `selected` state; its label changes to "Filter, N active", and Unpaid is not counted (UI-SPEC), so those Unpaid-focused assertions must change to assert the banner ("Showing unpaid bills") and **no** badge.
**How to avoid:** Decide the new assertion style once (banner text for Unpaid; `Filter, 2 active` label for counted filters) and apply across files.
**Warning signs:** `Unable to find an element with accessibilityLabel: Filter` after the swap, because a label that includes the count no longer equals `Filter`.

### Pitfall 2: The summary card follows the filter, the VM `totals` does
`vm.totals` is recomputed from the narrowed rows when searching or filtering (VM lines 148-162), so today the In/Out/count strip changes with filters (ACT-10: "count and figures beside it follow the filtered set"). D-47 says the figure equals Home's (unfiltered month). These conflict if the card is built from `vm.totals`. Recommendation: the big figure, In/Out and still-to-come come from the unfiltered `monthView` position (Home parity, D-47); the entry count in the caption. **This is an open question for the user** (see Open Questions Q1) because ACT-10 behaviour changes: with a filter on, the card no longer narrows. Do not silently choose; the planner should surface it in the plan or pick the "count follows the filter" variant and note it.
Additionally CONTEXT/UI-SPEC D-51 and the existing `showTotals={!flat}` (hidden for Every-month search) are subsumed by "hide card while searching".

### Pitfall 3: Fixed-width assumptions in the month row
`MonthSwitcher` bar is `flexDirection:'row'` with the label `flexShrink:1` and `numberOfLines={1}` (ellipsis). D-55 forbids ellipsis in the month name and wants measure-then-fallback. Measure the name with `onTextLayout` (`lines.length > 1` means no fit) or render a hidden measuring `Text` of the long and short strings and compare to available width from `onLayout`; avoid `Dimensions.get('window').width` thresholds (fails at large text, which is a font-scale not a width problem). Cap: the month text uses the `sheetTitle` role scaling up to 2x. Test with `Dimensions.set` (existing pattern at ActivityScreen.test.tsx 600-632) and `fontScale` mocks (`src/theme/__tests__/fontScale.test.ts`, `TabHeader.fontScale.test.tsx` show how).
Also: in jest, `onLayout`/`onTextLayout` never fire, so unit tests must drive them by `fireEvent(el, 'layout', {nativeEvent:{layout:{width}}})` / `'textLayout'`. Design the `MonthRow` fitting logic as a pure function `chooseMonthLayout({availableWidth, longWidth, shortWidth, iconsWidth})` so it is exhaustively unit-testable and only the thin measuring wrapper is hard to test.

### Pitfall 4: Search state resets
`SearchBar` keeps its own `text` state and syncs from `term` via the render-time `prevTerm` pattern. Unmounting it on Cancel loses nothing as long as Cancel calls `vm.setTerm('')` and `vm.setScope('month')` (UI-SPEC). But if the bar is conditionally rendered inside an `Animated` layer and re-mounted, a pending debounce timer is cleared on unmount (it has cleanup), so a Cancel within 250 ms of typing cannot leak a stale `setTerm`. Good, but add a test: type, Cancel immediately, assert term is `''`.
Also, a filter-intent from Home (`useActivityFilterIntent`) calls `setTerm('')` and `setScope('month')` while Activity stays mounted: `searchOpen` must close in that case, or the user sees search chrome with an empty term and no card. Watch `intent`/`term === ''` transitions, or lift `searchOpen` into the VM and reset it in that effect.

### Pitfall 5: Hidden bands and FlashList header height
The header collapses (empty month, searching). FlashList v2 handles variable header height, but `compactThreshold` uses the *large header* height only; unaffected. The first-entry-above-the-fold acceptance depends on card + chip row + offer card heights, which can only be verified on device (jest has no layout). Plan an explicit device check task.

### Pitfall 6: Chip row semantics and focus
"Removing a filter moves focus to the next chip, or to the Display chip" requires refs per chip (`a11yFocus.focusAccessibility`). The x is a sibling Pressable inside the chip container; the chip container itself must not be `accessible` as one element (otherwise the x is unreachable by TalkBack): make label area and x two accessible children of a plain `View`.

### Pitfall 7: Select mode interactions that must survive
- `selection` is pruned when `itemRows` ids change (hook adjusts during render). Entering Select from More must also close the More menu first, and `setHint(null)` as today.
- Calendar: `selection.active` could be true when the user switches to Calendar via the Display sheet; today the Select pill simply is not offered but an already-active selection persists. Decide: exit selection when choosing Calendar (recommended) and test.
- The FAB hide (`useHideFab('bulkSelect', selection.active)`) stays.

### Pitfall 8: Copy keys and tests that read them
