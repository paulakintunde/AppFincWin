## Notes
- `profiles.region` is granted with `grant update (..., region)`, so `region_subdivision` copies that pattern; `decide_shadow` copies the `decide_v3` no-grant pattern.
- The purge covers decide_links, decide_changes, decide_answers, decide_checks. There is no `decide_outcomes` table (outcomes live on other rows), and debts and savings_goals are left to CMP-F23.
- The purge cron is unscheduled-then-scheduled so a rerun does not duplicate it.
- Region subdivision client access is in separate `fetchRegionSubdivision` / `updateRegionSubdivision` functions rather than widening `MoneyPrefsRow` (which would have broken many fixtures).
- Shadow figures column is sized and typed by checks; code list is the ten answer codes, variants include tight and protection_off.

## Deviations from Plan
1. [Rule 3 - Blocking] `redateOnSignIn` is written as a dependency-injected function but is NOT mounted. The plan said to call it from an existing post-sign-in bootstrap; grep found none (only the `useSampleExists` query and `useSampleData` hook). Mounting it in a screen/provider is a follow-up for the owner of that wiring (pass `hasSamples` from `useSampleExists`, today from the local day, and invalidate sample queries in `onRedated`).
2. The redate function judges staleness by the newest `is_sample` transaction date. If `clear_sample_data` keeps some sample rows, `seed_sample_data` returns already-seeded and the call still reports true; acceptable for the review account.
