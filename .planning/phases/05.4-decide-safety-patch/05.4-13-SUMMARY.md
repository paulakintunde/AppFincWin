# Phase 05.4 Plan 13: prepare once, judge per check Summary

The v3 pipeline now builds the month model, base funds, paid occurrences, pay caps, due drops, the open 90-day cash path and readiness once in `prepare(raw)`; `judgeCheck(prepared, check)` runs purchase, cash and judge per key press. `evaluate(raw, check)` is `judgeCheck(prepare(raw), check)`. No answer changed.

## What was built

- `cash/path.ts`: `buildCashPathV3` split into `openCashPath` (net flows per day, cumulative spread per day, capped pay; price and opening independent) and `applyPurchaseFlows(open, opening, extraOut)`. `buildCashPathV3` stays as a thin wrapper so existing tests and callers are unchanged. Numbers are unchanged.
- `prepare.ts`: `Prepared` holds one reading, or two for thin history (as given, and thin months read as full). Both are prepared once; `judgeCheck` judges each and applies the existing `stricterOf` merge, then attaches readiness (read from the inputs as given).
- `index.ts` exports `prepare`, `judgeCheck`, `Prepared`; barrel test list updated.
- I44 added (invariant index now 44).

## Deviations from Plan

**1. [Rule 3 - Blocking] Pipeline lives in prepare.ts, not evaluate.ts.** `prepare.ts` needs `Evaluation`, `stricterOf` and the helpers that used to sit in `evaluate.ts`, while `evaluate.ts` must import `prepare.ts`; keeping both directions would create a cycle (depcruise `no-circular`). The code moved to `prepare.ts` and `evaluate.ts` re-exports `Evaluation` and `stricterOf`. The acceptance grep `judgeCheck(prepare(` in `evaluate.ts` still returns 1.

**2. The "before" fixture holds digests, not full results.** Full Evaluations for 2,000 cases would be very large; a per-case sha256 of key-sorted JSON detects any field change and names the failing case index.
