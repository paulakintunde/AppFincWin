### Pattern 1: Right-answer table as data, with a "known red" ratchet
**What:** Each case is one JSON object: `id`, `topic`, `persona`, `situation` (plain words, authored), `fixture` (structured inputs: balances, months, bills, debts, safety net, region, the check), `expected` (`code`, `variant`, `afterBuy`, `readyBy`, required reason codes), `why`, `fixIds`, `status` (`approved` | `to_do` | `disputed`), `ownerReason` (D-03). One runner turns approved cases into `it.each`. `knownRed.json` lists approved cases that the current engine fails, each tagged with the fix ID that will turn it green. The runner fails if (a) a case not on the list fails, or (b) a listed case passes (the list must shrink as rules land).
**Why:** satisfies "committed as tests before the first Theme A engine change" and "every case passes" at the end, without a red main. It also gives D-14 for free: the diff of `knownRed.json` per rule fix is the list of changed answers.
**`to_do` cases** (about 6 household cases) become `it.todo` with a count printed, so the "to do until Phase 8" promise stays visible.
**Page:** `build-page.mjs` renders the same JSON (situation, expected answer, why, a small numbers table from `fixture`) so the page cannot drift from the tests. Approval is recorded by editing `status`/`approvedAt` in the JSON in a PR. [ASSUMED: file layout; owner-facing wording in grade-10 English]

### Pattern 2: Plain cross-check calculator
**What:** about 200 lines, own folder, own tiny integer type (`bigint` or plain safe integers), written from the table's rule statements, not copied from `judge.ts`. It takes the same fixture shape and returns `{code, afterBuy}` only (per Theme M: disagreement on code or money-left fails). A fast-check generator makes random fixtures; `numRuns` comes from `CROSSCHECK_RUNS` (default 1000 in PR, 20000 in the nightly workflow). A failure prints the shrunk fixture.
**Independence guard:** an ESLint `no-restricted-imports` override for the folder (allow `fast-check`, test helpers, and the `MinorUnits` type only) plus a depcruise rule. Also run every approved table case through the calculator so the calculator is checked by the table. [ASSUMED: lint rule shape]
**Pitfall:** the calculator may not read the engine's constants. The thresholds (80%, one tenth, 20% APR, 10% interest) are restated from the table in the calculator, so a wrong engine constant is caught by disagreement.

### Pattern 3: Prepare once, judge per key press (ENG-12/13)
`evaluate(raw, check)` currently rebuilds the month model, funds, cash path and judge every call, and runs twice for thin history (`stricterOf`). [VERIFIED: codebase, `evaluate.ts`] Split into `prepare(raw): Prepared` and `judge(prepared, check)`, keep `evaluate = (raw, check) => judge(prepare(raw), check)` for tests and the calculator. The safety property: `judge(prepare(x), c)` deep-equals the old `evaluate(x, c)` on the generated corpus before any rule changes (a pure refactor commit, with a before/after equality test). The cash path depends on the purchase flows, so only its price-independent opening/bills part can be prepared; plan the split on `buildCashPathV3`.

### Anti-patterns to avoid
- **Copying the mockup's maths** (VC-02): spare money and the 90-day path must both stay above the safety net, nothing is clamped at zero, running costs start on their own dates. The current ladder clamps with `Math.max(0, month.monthLeft)`. [VERIFIED: judge.ts line 119]
- **A second "confidence" in disguise:** do not keep a numeric score internally. Settled dispute 3: delete the level, sort reasons by a fixed weight table.
- **Tuning tests to the new engine:** a changed expected answer needs the D-14 page and a popup, never a silent edit of an `expected` value.
- **Reusing `legacy-answers.json` as an oracle** (it is retired); `legacyBaseline.test.ts`, `fixturesExtra.test.ts`, `adapters/__tests__/legacy.test.ts` and `upgradeEvaluates.test.ts` read it and need re-pointing or deleting. [VERIFIED: grep]

## Common Pitfalls

### Pitfall 1: Harvest drags screens in
**What goes wrong:** a commit like 05.3-114 edits both the shared Back helper and the answer screens; copying it whole imports the parked design.
**Avoid:** harvest by path from the file lists in the Harvest Map; reject any path under `features/decide/v3` or `shell/decide/v3`.
**Warning signs:** the diff stat shows `src/features/decide/v3` or `app/(app)` routes.

### Pitfall 2: A migration that forgets `apply_patches`
**What goes wrong:** a new undoable column (overdraft rate, due day) is added but not listed in the re-declared `apply_patches` allow-list and type map; undo then refuses or silently drops it.
**Avoid:** base on the newest definition (after the catch-up files), add both lists, and add a pgTAP case that patches the new column.

### Pitfall 3: Pushing the catch-up migrations twice
**What goes wrong:** `supabase db push` tries to re-apply files already recorded remotely, or fails on a version mismatch.
**Avoid:** run `supabase migration list --linked` after copying the files; Local and Remote columns must match for those five before the first new push. Always `npm run supabase:preflight` first.

### Pitfall 4: Table cases tuned to the engine
**What goes wrong:** a developer edits `expected` to make a failing case pass.
**Avoid:** `expected` is only changed in a PR carrying a D-14 page and `ownerReason`; a CI check compares `expected` blocks for approved cases against the base branch and fails on a change without a `changeApproved` marker. [ASSUMED]

### Pitfall 5: Calculator and engine share a bug
**What goes wrong:** the calculator is "ported" from `judge.ts`, so 20,000 random cases agree on a wrong answer.
**Avoid:** write it from the table's rule statements; independence lint; also run the table through it.

### Pitfall 6: Coverage ratchets break the harvest
**What goes wrong:** harvested engine files drop `./src/engine/decide/` below 100% because tests live elsewhere or cover removed branches.
**Avoid:** harvest tests with sources; run `npm run test:coverage` before anything else is added; fix on the harvest branch.

### Pitfall 7: Stryker times out on property tests
**What goes wrong:** every mutant reruns 2,000-case suites; runs take hours.
**Avoid:** `perTest` coverage analysis, seeded fast-check, fewer runs under an env var, per-PR runs on changed files only, nightly for the whole engine.

### Pitfall 8: GitHub scheduled workflows only run from the default branch
**What goes wrong:** the nightly cross-check never fires until the workflow file is on `main`.
**Avoid:** merge the nightly workflow early (Wave 2), trigger once with `workflow_dispatch`, and confirm the first scheduled run. [CITED: GitHub Actions docs for `schedule`; ASSUMED here, standard behaviour]

### Pitfall 9: Shadow results become identifying
**What goes wrong:** rounded figures plus a stable user ID in a table the owner can query.
**Avoid:** the report script is the only supported reader; rounding function with a test; no free text; nothing from account names or transactions leaves the phone.

### Pitfall 10: Tier words survive in places the guard does not scan
**What goes wrong:** "rough" is a legitimate English word and a code identifier (`rough_figures`, `sourceKind 'rough'`); a naive regex either misses UI or flags everything.
**Avoid:** guard on keys and rendered labels for the v3 engine and verdict copy with an allowlist, rename engine identifiers in the same PR as the type deletion.
