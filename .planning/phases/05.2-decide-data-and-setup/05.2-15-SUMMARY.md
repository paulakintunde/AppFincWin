# Phase 05.2 Plan 15: Regular payment, dismissal, attribute and pays-in-full writes Summary

Marking a found payment Regular creates the series and sets counts_as, income_kind, pay_group and saving_mode as one action with one Undo. Not-regular answers, series attribute batches and the card pays-in-full answer are queued, offline-safe, undoable writes.

## Tasks
1. Confirm candidate and patch series attributes (commit 9df2bf37).
2. Dismissals and pays-in-full (commit aa2e9416).

## Behaviour
- `confirm`: call order is `create_recurring_series`, `apply_patches` (attribute op plus the dismissal soft delete when a dismissal is being cleared), then one `undo_log` insert. The Undo removes the series and its materialised lines and restores the cleared dismissal. With no attributes and no dismissal the patch call is skipped.
- `patch(items, labelKey?, labelName?)`: only changed keys, one `apply_patches` call carrying its own undo step, null when nothing changed. Conflict: whole batch refused, refusal toast, one failed-write record. Rejection: old values put back.
- `useAddDismissal` / `useRemoveDismissal` copy the decidePots pattern; the removal timestamp is fixed in the variables so a landed replay is accepted.
- `useSetDebtPaysInFull(debt, value, ownerId, stepTitle?)` writes `pays_in_full` with a `setupStepSaved` step; the caller supplies the wording from i18n.
- Failed-write records hold ids, counts and field names only.

## Deviations from Plan
**1. [Rule 3 - Blocking] pays-in-full needed a new mutation.** The plan expected the existing debt edit mutation to take `pays_in_full`. The only undoable debt write is `setDebtHousing` (is_housing only); `saveCardRate` and `saveCardTerms` are not undoable. Added `mutationKeys.setDebtPaysInFull` (keys.ts), a registered default and `useSetDebtPaysInFull` in debts.ts, mirroring the housing write. Files beyond the plan list: `src/data/keys.ts`, `src/data/mutations/debts.ts`.
**2. Replay after a crash between create and patch** cannot use `acceptIfAlreadyApplied` because `apply_patches` conflicts return an `UndoConflict`, not the server row. The replay reads the live version back instead, so it patches at the current version.
**3. `grep -c "scope: WRITE_SCOPE" dismissals.ts` equals 2** by naming the hooks' scope through a local `HOOK_SCOPE` constant; both defaults carry `scope: WRITE_SCOPE`.
**4. Known limit:** if the create replays as 'already-applied', the change set's materialised lines are unknown, so that undo step soft deletes the series only (the server job's lines stay until the series' own cleanup).
