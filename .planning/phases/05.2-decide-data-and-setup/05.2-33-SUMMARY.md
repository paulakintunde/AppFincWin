# Phase 05.2 Plan 33: Refund picker and detail rows Summary

Users can link a refund to a purchase from either side, with the "What this does" preview and Undo, and the "Refund of" / "Refunded" tags now work across months.

## Commits
- c67bfe9d: RefundPickerSheet, candidate model, `useRefundLinks` hook, two db reads, keys, copy.
- d2460d73: detail rows (Refund of..., Income type, Refunds group), ActivityScreen wiring, cross-month tags.

## Behaviour
- Picker, both directions. Refund to purchase: same-currency expenses in the 12 months to the refund date; purchase to refund: unlinked money-in on or after the purchase date. Same payee first, then newest, at most 50. Search by payee, note or amount; "Clear search"; empty state. Selecting shows the tile (full / partial / several / over from plan 16's `refundPreview`, the payment-plan line when the purchase has a recurring series or a written Decide link, and the footer line). "Link refund" and "Remove link" use `useLinkRefund` / `useUnlinkRefund` and toast with Undo. The list is the cached window, so it works offline.
- Detail (gated by `useDecideAccess().v3`): money-in rows get "Refund of..." (Not linked, or payee and date) and, unless already a refund, "Income type"; a purchase gets a "Refunds" group (one row per linked refund, any month, opens that refund) and "+ Link a refund".

On-screen rows override the fetched copy, so an optimistic link or unlink shows at once. ## Deviations from Plan
- **[Rule 2] New hook and db reads** for item 2 (handed over), plus `asActivityRow` to open an off-screen purchase in the detail sheet.
- **New copy keys** (en.ts, `activity.refund.*`): `pickerTitleReverse` "Which payment was the refund?", `pickerSublineReverse`, `searchPayments` "Search payments", `emptyTitleReverse` "No payments match", `rowSub`, `rowSubNoCategory`, `refundRowValue`, `refundRowA11y`, and `activity.incomeTag.detailNotSet` "Not set". The UI-SPEC gives no title or search label for the reverse picker; these are drafted in its voice and need a copy review.
- `flowOf` calls a linked refund "out" (it sets `is_refund`), so the detail rows read money-in from the sign, otherwise a linked refund could never reach "Remove link".
- Detail rows with an `action` are rendered by the sheet (they open sheets and need linked data); `detailRowsFor` stays pure and only decides which exist. The rows sit after Note.
- `TransactionDetailSheet.test.tsx` gained mocks for `useDecideAccess` (v3 false) and the supabase client; no assertions changed.

## Known caveats
- `refundDetailRows.test.tsx` is order sensitive: the two switch-off sheet tests fail (sheet never mounts) if placed after the test that presses "+ Link a refund". Reproducible, cause not found in the time spent (suspected Sheet module state across renders in jest); tests are ordered so that test runs clean, deterministically across repeated runs.
- No ActivityScreen-level test for the `onRefundLink` / detail callback wiring (the screen harness mocks the whole view model); the pieces are covered separately (picker, detail rows, tag sheet prop).
- Text fit is by construction (label/amount rows stack under 360 dp or font scale above 1.3, amounts `numberOfLines={1}`); not checked on device at 320/402 dp x 1.0/2.0.
- The picker's plan line uses the household's written Decide transaction links plus the recurring series id; a link is not role-checked (day_one / payment) because the household-wide read used for it has no role column.
