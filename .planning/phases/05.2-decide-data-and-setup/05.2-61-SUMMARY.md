# Phase 5.2 Plan 61: Toast Undo (N-04) Summary

**Outcome: N-04 is not closed.** The diagnose-first gate was applied. Seven jest cases and a live run on the Pixel 9 both show the toast Undo reaching `apply_undo_step` and the step ending 'undone'. No root cause was found, so Task 2 (the fix) was NOT started and no production code changed. Only the regression test file was added.

## What was done

### Jest (Task 1), real UndoToastHost + real useUndo + real write queue + fake Supabase
File: `src/features/record/history/__tests__/UndoToastHost.decide52Flow.test.tsx`. All 7 pass on current code, so there is no failing assertion to quote.
- Per family (paymentDismissed, setupReset, incomeTagged, seriesStopped), with each caller's exact toast shape (kind, text key, params): Undo press sends `['apply_undo_step', { p_step_id }]`.
- B: real `useAddDismissal` forward write, Undo pressed straight after: rpc is sent, after the step insert, with the same id as the recorded step, and the 'Undone' toast shows.
- C: the immediate `insertUndoStep` fails (500), step goes down the queued `recordUndoStep` path, Undo pressed at once: the rpc runs after the queued step insert (not before), 'Undone' shows.
- D: one app host and one sheet host with a sheet open, then closed: only one Undo is visible at a time and each sends exactly one rpc.
Candidates (a) id mismatch, (b) queued step record ordering, (c) null label, (d) guardSession wipe, (e) missing defaults, (f) two hosts / press target were each checked by these cases. None reproduced.
Note: in jest the `expo-crypto` `randomUUID` is undefined unless mocked, so a hook-driven case needs `jest.mock('expo-crypto', ...)` (done in the test); without it the toast gets no stepId and shows no Undo. This is a test-environment fact, not an app bug.

### Device fallback (Pixel 9, 55240DLAQ000EQ, dev client, Metro 8075)
Temporary `[undo-probe]` logs in `UndoToastHost.onUndo`, `ToastView` action press, `useUndo.undo`, the undoStep `mutationFn`/`onSuccess`/`onError`. Real taps via `adb`.
Decisive lines (incomeTagged: Activity, IncomeTagSheet "Other", "Tagged 2 payments from Sale" toast):
```
[undo-probe] ToastView action press
[undo-probe] host.onUndo 25 13d5006d-9a58-41bb-989e-49b7cf2651a7 incomeTagged true app true true
[undo-probe] useUndo.undo 13d5006d-9a58-41bb-989e-49b7cf2651a7
[undo-probe] mutationFn 13d5006d-...        (0.8 s after the press)
[undo-probe] onSuccess 13d5006d-... undone  (3.5 s later)
```
A fresh Activity mount afterwards shows the Sale row back to "New income - what is it?", so the undo took effect on the server. A second run (a "marked unpaid" toast from Mark as pending) gave the same chain, onSuccess `undone`.
Observations that may explain how N-04 was perceived, not proven to be its cause:
- Press to server reply was about 4 s on this device and network. During that time the toast is already gone and nothing says an undo is pending. Checking the undo_log within a few seconds would show 'available'.
- After 'undone', the Activity list still showed the undone tag (pending patch) for at least 5 s, until the screen was re-mounted. The cache looked unchanged although the server was done.
- History at the end: the top "regular payment" step (paymentDismissed) is status refused ("recurring_dismissals was changed on another device after this"), which makes every row under it "Undoes 0 changes" for "Undo to here". That is a legitimate server refusal from the walkthrough's own later "Clear Not regular", not a lost tap.
Not reproduced on device: paymentDismissed, setupReset, seriesStopped (no live pay series, Decide answers already empty after the owner's cleanup, setup stepper not driven). Their toast path in the host is the same code as incomeTagged and the jest cases cover it.
All probes were removed (`git grep -n "undo-probe" src` returns nothing; the three probed files were restored with `git checkout --`).

## Root cause
Not found. Stated plainly: with the current code the toast Undo press reaches `apply_undo_step` for the incomeTagged family on a real device and for all four families in jest. The reported symptom (rows stay 'available', resolved_at null) is not explained by the client path. Open possibilities for the next step: (1) the walkthrough build predated some 05.2 change (check the build id the owner tested); (2) the ~4 s unacknowledged RPC window with the owner reading undo_log too early; (3) a family-specific forward-write problem not reproduced here (the paymentDismissed / setupReset / seriesStopped forward mutations were exercised in jest only for dismissal; the others only via hand-made toasts). Recommend the owner re-tries the four families on the current build and, if one still fails, the probes above can be re-applied in under a minute.
