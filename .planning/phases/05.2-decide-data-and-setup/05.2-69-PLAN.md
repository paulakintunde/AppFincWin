<objective>
Fix the two critical defects in "Regular" on the Regular payments step (CR-01, CR-02) and the replay hole in the same write (WR-01). All three are confirmed in code:

- CR-01 (verified by the orchestrator and re-read here): `detectCandidates` returns `amount: minorUnits(Math.abs(median))` (src/engine/decide/v3/month/recurring.ts `candidateFrom`), and `markRegular` in RegularStep.tsx passes `amount: Number(candidate.amount)`. Neither the RPC nor `materialise_series` changes the sign. A bill is stored as money in. `regularLoansSteps.test.tsx:147` asserts `amount: 150000` for an 'out' candidate and locks the bug in.
- CR-02 (verified): `runConfirm` calls `createRecurringSeries(client, vars.series, { anchorTransactionId: null })` with no link ids. In `create_recurring_series` (20261010000300) `materialised_through` then becomes `greatest(anchor_date, month start) - 1`, so a bill whose latest logged row is in the current month gets a pending occurrence on that same date: counted twice, plus an overdue "Mark paid" row.
- WR-01 (verified): on `already-applied` the code builds `{ inserted: [], linked: [] }`. Undo then soft-deletes the series and leaves its materialised lines live. With the CR-02 fix it would also leave the logged rows linked to a deleted series.

Link choice (Claude's discretion, differs from the reviewer's wording): pass `anchorTransactionId: null` and `linkTransactionIds: candidate.rowIds`, not an anchor row. Reasons: (1) an anchor transaction overrides `anchor_date` with that row's own date, which would undo the L-05 month-end rule (`candidateFrom` anchors a 28 Feb / 31 Jan bill on the 31st); (2) an anchor row deleted on another device makes the whole RPC raise 22023, while a missing link row is skipped by the RPC's candidate CTE. Linking every row still sets `materialised_through = max(linked local_date)`, so nothing is materialised on or before a logged date.

No migration: the RPC already accepts `p_link_transaction_ids`, and apply_patches already allows `transactions.recurring_series_id / occurrence_date` set to null for the undo.

Production data: the orchestrator checked production. No bill series has been created through this path (only test pay series, since deleted), so no data repair is needed. Pay series created here were positive and correct.

Output: sign-correct, linked, replay-safe confirm with failing-first tests. The list-side consequence of linking (the confirmed card must stay visible) is plan 05.2-70.
</objective>
