# Phase 05.2 Plan 19: Real V3 inputs and the useDecideV3 read hook

## What is mapped (no stub left)
- Pattern and confirmed flag, with the six setup pay types onto salary, commission, freelance, none (pension to salary, own business to freelance).
- Account use from the account columns (`uses` argument still overrides, tests only). The M-06 "stated uses decide what counts" rule now follows stored uses.
- Envelope `accountId` (stored first, transfer-leg guess as fallback) and `bucket`.
- Line `refundOf`, income kind and counts-as from the transaction row (counts-as falls back to the series).
- Series `countsAs`, `incomeKind`, `savingMode`, `payGroup` from the series row; a `series_extra` entry overrides field by field.
- Dismissals (payee keys), pay arrivals, expected income, held bridges (only while their check is live), unexplained answer (all three parts or nothing).
- D-23 checked: a 30000 saving series with two 15000 buckets counts 30000 set aside, with two 25000 buckets 50000.

## Deviations from Plan
- **Pot mapping**: `account_id` and `bucket` are read from the goal row in `buildV3Inputs` (looked up by pot id), not carried through the old engine's `PotInput` in `buildSnapshot.ts`. This avoids changing the old-engine type. `GoalSource` gained optional `account_id` and `bucket`.
- **engineIncomeTypes** also passes engine values (`salary`, `commission`, `mix`) through, because existing exports, shadow sources and tests store those. Unknown values are still dropped.
- **Store-only fields**: `spread_months`, `everyday_override_at` and `reserve_goal` are carried on the settings source but not mapped. The engine reads `coversMonths` per line (nothing stores it per line) and has no input for the other two, so mapping them would be a guess.
- **oneSource.test.ts** allow-list widened to the three db row-type modules `settingsSource.ts` imports (`import type`), as the plan permits.
- **Existing test updated**: the envelope expectation in buildV3Inputs.test.ts now includes `bucket: false`.
- A check with no plan link keeps its bridge held (cannot be shown to have ended).
- `buildV3Inputs` is called by `useDecideV3` alongside `computeV3`, which builds its own copy, so inputs are built twice per recompute (the inputs are returned for the D-19 readout).
- `DECIDE_V3` still appears in the pre-existing header comment of `computeV3.ts` (not touched); the switch itself is only in availability.ts.
