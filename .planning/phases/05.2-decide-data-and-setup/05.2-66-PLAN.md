<objective>
The data side of "Not my pay" (F-02, owner decision). The 14 "Refund - Online Store" rows are stored as plain money in (is_refund false, no refund_of), so the plan-51 refund rule cannot see them, and the pay step offers them as pay. The user needs to say "this isn't my pay" once and have it stick.

Storage choice (Claude's discretion, recorded here): reuse `recurring_dismissals`, with the reason carried in a namespaced key: `payee_key = 'not-pay:' + <candidate key>`, direction 'in'. This needs no migration. The table already has household RLS, a guard trigger, soft delete for Undo, apply_patches support, export (exportManifest) and purge on account deletion.
Two alternatives were rejected. A `reason` column on recurring_dismissals, or a new decide_answers kind, would each need a migration and an owner-approved production push. decide_answers keys are also capped at 80 chars, and a candidate key can be longer.
The trade-off is that the reason lives in the key, so every reader of recurring_dismissals must ignore these rows (Task 1 checks every reader). A not-pay answer is per household, like "Not regular", because the found payer is read from household transactions.
Output: pure key helpers, dismissal labels, detection wired to the answers, tests. The UI is plan 05.2-67.
</objective>
