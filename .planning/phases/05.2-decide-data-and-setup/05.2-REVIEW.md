## Summary

New controls carry roles, labels and state. The RLS, column grants and cross-household FK guards in the 20261028 migrations are sound. apply_patches allow-lists and types every new column, and the N-04 fix (2403d8ca) covers the four 05.2 caches.

## Critical Issues

### CR-01: "Regular" on a found bill creates a money-IN series

**File:** `src/features/decide/setup/steps/RegularStep.tsx:187` (source: `src/engine/decide/v3/month/recurring.ts:153`)
**Issue:** `candidateFrom` returns `amount: minorUnits(Math.abs(median))`, which is always positive. `markRegular` passes `amount: Number(candidate.amount)` with no sign. Neither `create_recurring_series` nor `materialise_series` changes the sign. So marking "Rent £1,500" Regular stores a +150000 series. Every occurrence then materialises as +£1,500 money in. Decide reads it as income rather than a bill, and the cash path is off by 2 x £1,500 a month. The test `regularLoansSteps.test.tsx:147` asserts `amount: 150000` for an `'out'` candidate, so it locks the bug in.
**Fix:**
```ts
amount: candidate.direction === 'out' ? -Number(candidate.amount) : Number(candidate.amount),
```
Fix the test as well. Add a guard in `runConfirm` that `Math.sign(series.amount)` matches the candidate's direction.

### CR-02: "Regular" duplicates payments that are already logged

**File:** `src/features/decide/setup/steps/RegularStep.tsx:180-195`, `src/data/mutations/seriesAttributes.ts:98`
**Issue:** The series is anchored on `candidate.anchorDate`, which is the date of the last logged row (or an older month-end row). It is created with `anchorTransactionId: null` and no `linkTransactionIds`. `materialise_series` starts at `anchor_date`, so it inserts a pending occurrence on that past date (and on any later past dates). The logged row it duplicates stays unlinked. Result: the latest payment is counted twice in Activity and in Decide's months, and an "overdue" Mark-paid row appears.
**Fix:** Pass `{ anchorTransactionId: candidate.rowIds.at(-1), linkTransactionIds: candidate.rowIds }` to `createRecurringSeries`, as the Record-tab offer flow does. Return the `linked` rows in the change set so Undo unlinks them.

### CR-03: The new settings money columns carry no currency

**File:** `src/features/decide/snapshot/v3/settingsSource.ts:52-63`, `src/features/decide/snapshot/v3/buildV3Inputs.ts:511-514`, `src/data/mutations/decideSetup.ts:233`
**Issue:** Only `reserve` is checked against `settings.currency !== home`. The other columns reach the engine as home-currency minor units however they were typed: `everyday_override`, `unspent_anchor`, `steady_amount`, `rough_saving/debt/invest`, `unexplained_amount`, and the `decide_answers.amount` values for expected_income and held_bridge.
- `useStamped` takes the currency from the stored row (`current?.currency`), not from home. With no settings row yet, it writes no currency at all.
- `change_home_currency` never touches decide_settings.

Scenario: a user sets everyday spending to £2,000 (200000), then switches home currency to JPY. Decide now reads ¥200,000 (about £1,000), and the verdict is wrong.
**Fix:** Stamp with `rc.homeCurrency` whenever a money column is written. In `buildV3Inputs`, set every settings money field to null when `st.currency !== home`. Add a currency (or a home-currency stamp) to the `decide_answers` money kinds, or clear them on a home-currency change.

## Warnings

### WR-01: A replayed confirm records an Undo that leaves the materialised lines live

**File:** `src/data/mutations/seriesAttributes.ts:98-100, 120-122`
**Issue:** Suppose `create_recurring_series` committed but the client timed out (`timeoutFetch`). The retry then gets `already-applied`, so `createdSet` is null and the change set has `inserted: []`. Undo soft-deletes the series and leaves every pending occurrence it materialised behind, now orphaned.
**Fix:** On `already-applied`, read the live rows (`transactions where recurring_series_id = id and deleted_at is null`) with their versions, and build `inserted` from them.

### WR-02: "Not my pay" is household-wide, but the answer is about one person

**File:** `src/features/income/steps/PayStep.tsx:126`, `src/features/income/notPay.ts:21-24`, `supabase/migrations/20261028000800_recurring_dismissals.sql:22-24`
**Issue:** The not-pay row is a household `recurring_dismissals` row, and `notPayMatcher` reads every member's rows. Partner A taps "Not my pay" on B's salary. From then on, B's own income setup never offers B's salary as the found pay. Income setup itself is per user (decide_settings).
**Fix:** Scope not-pay answers to the user. Either add `created_by` to the key (`not-pay:<uid>:<key>`) and filter on `created_by === userId` in `notPayMatcher` and in `useIncomeContext`, or move them to an owner-private table.

### WR-03: A dismissal for a key that is already live fails instead of being read as landed

**File:** `src/db/recurringDismissals.ts:47-55`, `src/data/mutations/dismissals.ts:66-74`
**Issue:** The 23505 replay path only looks the row up by client `id`. It fails when another device (or a stale cache) already holds a live row for the same household + payee_key + direction. That hits the `recurring_dismissals_live_key` violation, which throws "rejected", rolls the optimistic row back and records a failed write, even though the answer is already in place. Undoing a "Show again" after a fresh re-dismissal hits the same 23505 inside apply_patches.
**Fix:** On 23505, also fetch by `(household_id, payee_key, direction, deleted_at is null)` and return that row as landed. Skip the undo step when the row is not this write's.

### WR-04: The decide_answers live key ignores the household

**File:** `supabase/migrations/20261028001000_decide_answers.sql:31-32`
**Issue:** The unique index is `(created_by, kind, key)`. RLS and the client query are per household. After a user moves households, an old live `expected_income` row for `2026-11` is no longer visible. The client then inserts a new row, hits 23505, and records a permanent failed write.
**Fix:** Index on `(created_by, household_id, kind, key)`, done additively: create the new index, then drop the old one.

## Info

### IN-01: Key truncation can split a UTF-16 surrogate pair
**File:** `src/features/income/notPay.ts:13`, `src/data/mutations/incomeTagModel.ts:8`
**Issue:** `.slice(0, 200)` and `.slice(0, 60)` count UTF-16 units. An emoji at the cut leaves a lone surrogate, which Postgres rejects. A cut not-pay key also loses its `|CUR|sign` suffix.
**Fix:** Cut on code points: `Array.from(s).slice(0, n).join('')`.

### IN-02: month_marks can look changed when it is not
**File:** `src/data/mutations/decideSetup.ts:97-105`
**Issue:** `JSON.stringify` compares key order, and jsonb sends its keys back in a different order. So an unchanged month_marks can read as changed, which writes again and bumps the version. That bump makes earlier settings Undos refuse.
**Fix:** Compare with sorted keys.

N-05 (undo-to-here refusing after a later undone step) was not re-reported: it is deferred to 05.3 as D-15.
