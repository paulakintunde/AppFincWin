# Phase 05.2: Decide data and setup - Context

**Gathered:** 2026-10-27
**Status:** Ready for planning (updated 2026-10-27: D-15..D-23)

<domain>
## Phase Boundary

This phase stores everything the new Decide (v3 engine, phase 05.1) needs. Each piece is asked once and can be edited.

It delivers:
- the income profile, as one shared component (`IncomeProfileSteps`) that Phase 9's main onboarding reuses;
- the Decide setup stepper and Decide settings;
- income tags and prompts in Activity;
- the unspent-money and emergency-fund sheets;
- refund links, and the engine's refund re-dating;
- the per-account v3 switch (05.1 D-15);
- the additive migrations, with purge and export coverage.

Decide stays hidden (`DECIDE_OPEN = false`) for everyone else. Out of scope:
- the Decide screens (home, check, answer, plan, "What could I do instead?");
- the screens for the in-check questions;
- the refine check-in cards;
- cutover.

All of these are phase 05.3.

</domain>

- **Data rules:** every piece of data in `00-UPGRADE-PLAN.md` §4 is added, edited, deleted, updated and undone as that section describes:
  - through the serial write queue, offline, with `undo_log` and the Undo toast;
  - `version` bumps;
  - soft deletes;
  - a hard purge on account deletion.
- **Migrations:** the list in `00-UPGRADE-PLAN.md` §7.3, all additive. `decide_cleanup` waits for cutover.
- **Engine-input storage:** everything `05.2-OWNER-NOTES.md` lists, saved and reused, and asked again only when the figure behind it changes (05.1 D-59). That covers:
  - income pattern (D-34) and expected income (D-35);
  - held-back bridges (D-38);
  - the volatile-income answer per plan (D-48, `CheckV2.volatileCover`);
  - account use (D-54/D-55);
  - the unexplained-money answer (D-50);
  - the pay-arrival answer per pay date (D-58);
  - rough figures (D-57).

  The engine types already exist in `src/engine/decide/v3/types.ts`: `IncomeProfile`, `ExpectedMonthIncome`, `HeldBridge`, `AccountUse`, `V3Account`, `UnexplainedAnswer`, `PayArrival`, `RoughFigures`, `UnspentAnchor`, `EmergencyFund`, and `Envelope.accountId`.
- **One source of truth (05.1 D-53):** Decide reads accounts, Activity, series, envelopes, goals and debts through the snapshot. It never copies them.
- **Refund rules:** decisions 1 to 4 in `05.2-OWNER-NOTES.md`, which were locked on 2026-10-26:
  - engine view only;
  - a credit counts as a refund only when the user links it;
  - a shortfall goes to the original purchase's category.

### What users see before switch-on
- **D-01:** Everything new in this phase stays hidden until Decide switches on. That includes:
  - the Activity "How are you paid?" card;
  - income tagging;
  - the "new kind of income" question;
  - the setup stepper and Decide settings;
  - the refund link.

  The one exception is named test accounts (D-02). Nobody else is asked a question that nothing uses yet.
- **D-02:** Build the per-account switch (05.1 D-15) in this phase.
  - The owner's and demo accounts see the new setup, settings and Activity parts on the Pixel; everyone else sees nothing.
  - The switch is read in one place, `decideEngine()` in `src/features/decide/availability.ts`.
  - The existing hardcoded `DECIDE_V3` and `DECIDE_OPEN` constants stay false for everyone else.
  - The 05.1 switch guard must still pass.

### Where the account questions live
- **D-03:** "What is this account for?" (everyday · mixed · kept for one thing (which one) · savings I don't touch) is asked in Decide setup **and** on each account's own edit screen.
  - The answer is stored on the account, so there is one source.
  - Decide settings links to it.
  - It is a **needed (●) step**, placed first in "Your money now", before unspent money, because the unspent sum depends on it.
  - One screen lists every account.
  - **The minimum setup becomes 6 screens, about 3–4 minutes.** ROADMAP success criterion 1, which says 5 steps and about 3 minutes, is updated to match.
- **D-04:** Setup step 10 (emergency fund) asks for the amount and the account that holds it. You aren't asked twice:
  - if that account holds only the fund, its use is set to "kept for one thing: emergency fund" (`dedicated`, `emergency`);
  - if it also holds spending money, its use is set to `mixed`.
- **D-05:** On the account-use screen, after "mixed" is picked:
  - it lists the envelopes and goals, and the user marks which ones sit in this account (saved as `Envelope.accountId` on each envelope);
  - it then asks "Anything else set aside here?" with an amount (`AccountUse.mixed.extraSetAside`, D-55).

### Refunds linked to a purchase (resolves the open items in 05.2-OWNER-NOTES.md)
- **D-06 Over-refund:** the refund up to the purchase price goes back to the purchase month. Anything above the price is money in for the month the refund arrived, so past months never gain money that wasn't there.
- **D-07 History:** re-dating always applies to every past month, worked out from the records each time.
  - This changes past months' everyday totals and so the typical-month median, which is intended.
  - Nothing extra is stored, and unlinking reverses it.
- **D-08 Several refunds:** any number of refunds can link to one purchase.
  - The purchase shows the total refunded.
  - Any total above the price follows D-06.
- **D-09 Payment-plan purchase:** a refund of a plan purchase is a credit to the purchase month.
  - The plan's payments continue until the user edits or ends the plan, because the lender decides what happens to it.
  - Decide shows a declarative note: "This plan has a refund. Has the plan changed?"
  - The app never shortens the plan itself.
- **D-10 In Activity:** both rows point to each other.
  - The refund row shows a "Refund of {payee} · {date}" tag, and tapping it opens the purchase.
  - The purchase row shows "Refunded $X".
  - Balances stay exactly as logged.
- **D-11 Engine check:** refund re-dating is an engine change in `src/engine/decide/v3`, which stays pure with 100% branch coverage. After it:
  - re-run the shadow comparison and the I28 back-test;
  - any answer that newly becomes a fit (`fits_month` / `fits_unspent`) needs a written reason the owner approves, the same as 05.1 D-14, and this is a blocking checkpoint;
  - other changed answers are listed by cause;
  - add refund golden cases: full, partial with shortfall, over-refund, several partials, and a plan purchase.

### The refine check-in and going live
- **D-12:** The refine check-in is split between the phases.
  - 05.2 stores `refine_last_at` and `refine_snooze_until`, and builds the pure `month/refine.ts`, tested for "never suggests a change smaller than the noise" (`00-UPGRADE-PLAN.md` §4.12). refine.ts takes the triggers and returns the card list with its numbers.
  - 05.3 builds the home card and the review cards.
- **D-13:** For the in-check questions, 05.2 builds saving and reading only:
  - did your pay arrive;
  - what this money is for;
  - can you cover it in low months;
  - expected income;
  - the bridge held back at Go ahead.

  Each answer gets storage, a write-queue mutation with Undo, offline support, purge and export coverage, and mapping into `buildV3Inputs`. Their sheets belong to 05.3, inside the check, because the check is the only place they appear.
- **D-14:** Production migrations need **one approval near the end** of the phase:
  1. All new columns and tables are built and tested locally, including pgTAP RLS tests.
  2. A human-gated plan then shows the owner one plain list of every change.
  3. It runs `npm run supabase:preflight` and then `npm run supabase:db:push` only after the owner's OK.

  Nothing is dropped.

### Income counting questions (update, 2026-10-27)
- **D-15:** **Everyone** is asked "Does your income change by season?" (steady · changes month to month · follows the seasons → `IncomeProfile.pattern`), salaried users included. Seasonal wage work exists, for example school staff paid 10 months a year.
- **D-16:** These are **two screens, season first**.
  - The season question comes first.
  - Then, only for changing income (commission, freelance, business or no fixed income), "How should Decide count it?" with the 4 methods (`IncomeProfile.variable`) and its 3a–3c follow-ups.
  - Each screen keeps one question.
  - The season question is optional (○), because the engine asks it during a check when it finds swings (D-34).
- **D-17:** The setup pay types map onto the engine's `IncomeType` with **no engine change**:
  - "Pension or benefits" counts as regular pay (amount, how often, next date) → `salary`;
  - "My own business" counts as changing income → `freelance`;
  - the user's own choice is also stored (`income_types` keeps the 6 setup values), so the wording shows what they picked.

### Where test accounts start in 05.2 (update, 2026-10-27)
- **D-18:** For test accounts (D-02) only, the Decide tab shows a **simple setup page** in 05.2:
  - "Set up Decide" or "Finish setup";
  - Decide settings;
  - the unspent-money and emergency-fund sheets.

  Everyone else still sees "Coming soon". 05.3 replaces this page with the real home.
- **D-19:** The setup page also shows a **plain readout of what the engine now receives**, for the owner to check that answers land correctly. Example: "Accounts counted: 2 of 3 · Unspent $2,400 (Oct 3) · Next question: Did your pay arrive?". It is test accounts only, and 05.3 removes it.

### Life-change prompts (update, 2026-10-27)
- **D-20:** The separate "update" prompts in `00-UPGRADE-PLAN.md` §4.1–4.5 are **merged into the refine check-in** (D-12). They are:
  - a new pay amount, or a pay type that stops;
  - a steady amount above income for 2 months;
  - series drift over 5%;
  - a card not paid in full for 2 statements;
  - the everyday override expiring (90 days, or the median moving 20%);
  - a suggested under-logged month.

  Each becomes a refine card, shown at most once a month, with "Later" for 14 days. 05.2 builds the pure detection rules in `month/refine.ts` (tested, including "never smaller than the noise"), plus storage for what was asked or snoozed. 05.3 shows the cards.
- **D-21:** **No change is ever applied without the user choosing it.** The only automatic behaviour stays automatic: unspent money rolls forward, and the typical month follows the records.

### Saving buckets over regular saving (update, 2026-10-27)
- **D-22:** When the buckets' monthly amounts add up to more than regular saving:
  - the total line says "$X more than your regular saving.";
  - it offers two buttons: "Lower a bucket" (opens the bucket list) and "Raise my regular saving to $Y" (edits the saving series through the existing mutation);
  - the user may leave it as is, and setup still moves on.
- **D-23:** If it is left as is, Decide counts the **larger** of the bucket total and regular saving as money set aside each month. The planner must check that the snapshot never counts a bucket's monthly amount and the saving series twice.

### Claude's Discretion
- How the refund link is stored, for example a nullable `refund_of` transaction id. Whichever it is, it needs RLS and must be covered by purge, export and undo.
- How the per-account switch is stored and read, as long as it is read in one place, cannot be enabled by the client for other accounts, and keeps the 05.1 switch guard green.
- How the new engine-input answers are split across tables and columns, within the additive rule (§7.3 names a starting set).
- How plans and waves are ordered. The engine refund change and its shadow re-check (D-11) should land before the owner checkpoint.

## Existing Code Insights

### Reusable Assets
- `src/db/*`: one module per table, including `decideSettings.ts`, `recurringSeries.ts`, `transactions.ts`, `savingsGoals.ts`, `debts.ts`, `accounts.ts` and `undoLog.ts`. New columns extend these modules rather than adding parallel ones.
- `src/features/decide/pots`: the envelope (pot) screens and mutations, which already have Undo.
- `src/features/decide/onboarding`: the existing rough-figures onboarding, the starting point for the setup stepper.
- `src/features/decide/snapshot/v3/buildV3Inputs.ts` and `computeV3.ts`: the snapshot already feeds v3. Today accounts map with `use: null` (05.1 D-62 "until 05.2").
- The existing series sheet, the debt sheets, the write queue and the Undo toast (`src/state/undoToast.ts`).

### Established Patterns
- The serial write queue, using TanStack paused mutations and `setMutationDefaults`, with `version` bumps and the "changed elsewhere" message.
- Migrations are timestamped SQL in `supabase/migrations`, with pgTAP tests run by `supabase test db`. The CI `rls` job pulls images from `public.ecr.aws`.
- Purge and export are covered in migrations (for example `20260926000500_undo_log.sql` and `20261011000200_statement_uploads_purge.sql`). Every new table and column must join them (C13).
- Gates after every wave:
  - typecheck;
  - eslint with 0 errors;
  - depcruise (engine purity);
  - `check:ignores`;
  - `verify:gates`;
  - `test:coverage` (100% branch on engine and snapshot);
  - CI green.

### Integration Points
- Activity screens: the "How are you paid?" card, income tags, the new-payer question and refund links, all behind the D-02 switch.
- The account edit screen: the account-use question (D-03).
- `recurring_dismissals` and `recurring_series` (`counts_as`, `income_kind`, `saving_mode`, `pay_group`) feed `month/recurring.ts`.
