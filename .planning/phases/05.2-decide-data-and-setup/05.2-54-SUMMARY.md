# Phase 05.2 Plan 54: Duplicate candidates and Clear "Not regular" Summary

Regular-payment candidate ids are now unique per account, only true duplicates collapse, refunds are excluded, and a "Not regular" answer can be cleared with Undo.

## F-07 duplicate source

Two accounts, different transaction ids, same dates; not the same ids twice. detectCandidates groups by payee and account, so a second account with its own rows gives a second candidate with equal key and anchorDate and disjoint rowIds (proved by the fixture test). The old id `key|anchorDate` then collided. The walkthrough-like fixture gives 2 candidates before and 2 after; the ids now differ (`key|accountId|anchorDate`) and the meta line names the account when a payee repeats.

Doubled ids fed to the engine give no candidate at all (the repeated dates break the cadence), so the hook now skips an already-seen transaction id before detecting. Whether the two Bookshop rows are an import duplicate (same purchase recorded in two accounts) cannot be told from code. Logged as a follow-up for the 05.2-59 re-walk: if so, it is an imports finding, not fixed by hiding a card.
