# Phase 05.2 Plan 16: Income tagging and refund link writes Summary

Saving an income type is one queued batch with one Undo, including the once-only payer rule and the earlier untagged payments from that payer. Refund link and unlink are single undoable writes, with pure models for the "What this does" preview and the "Refunded" total.

## Tasks
1. Pure models (commit f33ec0dc): payerKeyOf, earlierUntagged, refundTotals, refundPreview, with tests.
2. Mutations (commit 54f6b1ee): useTagIncome, useLinkRefund, useUnlinkRefund, registered under tagIncome, linkRefund, unlinkRefund.

## Behaviour
- With "Apply to future payments" on: a payer rule is inserted with a client uuid (duplicate read back; if another device made it first with a different answer it is patched in the same batch). Rows the user already tagged are skipped, as is the payment itself if repeated.
- Without it: no rule, only this payment, label `incomeTypeSaved`. With it: label `incomeTagged` with `{n, name}`; the caller picks the toast copy.
- Offline: one paused mutation; cached month rows show the tag with `pending: true`; the new rule is added to the prompts cache.
- Failed-write records hold ids, counts and column names only (asserted: no payer name, no amount).

## Deviations from Plan
- **Row cap (T-05.2-16-04):** the plan says cap earlier rows at 5,999. The undo step also carries one rule op, so the cap is `MAX_TAGGED_ROWS = MAX_UNDO_OPS - 1` (5,999) in total rows including the payment itself, i.e. 5,998 earlier rows. The UI should say so when the cap trims the list.
- The plan interface names `payerKeyOf(description)`; the transaction field is `name`, so callers pass `tx.name`.
- Added `mergeIntoMonths` (exported from incomeTags.ts) as a shared cache helper; refundLinks imports it.
