<objective>
The two migrations the review fixes need. Both are written and tested locally here. Production push is owner-approved in plan 05.2-75, run by the orchestrator with `npm run supabase:db:push`. No production query or push in this plan.

1. WR-04, re-verified: in 20261028001000_decide_answers.sql the unique index is `decide_answers_live_key on (created_by, kind, key) where deleted_at is null`, while RLS and the client query are per household (`household_id in user_household_ids()`, `queryKeys.decideAnswers(userId, householdId)`). After a household move the old live row is invisible. The client inserts, gets 23505 on a different row, and `insertDecideAnswer`'s read-back by id finds nothing, so it records a permanent failed write. Fix, as the reviewer proposed: create the household-keyed index first, then drop the old one. The new index is strictly looser, so creating it can never fail on existing data. No code or `on conflict` clause names the old index (grep confirmed).
2. CR-03 server half (see plan 05.2-71 objective): `change_home_currency` (20261010000400, not redefined since) gains two statements. Why a migration was chosen: decide_answers has no currency column, and adding one would mean replacing apply_patches' whole allow-list function. Clearing the two money answer kinds on a switch is smaller, and it matches D-59 (asked again when the figure behind it changes). Stamping `p_from` on null-currency settings rows lets plan 71's read guard treat them as the old currency after the switch.

Other fixes checked for migrations: CR-01, CR-02 and WR-01 need none (the RPC already takes link ids, and apply_patches already allows unlinking). WR-02 needs none (it uses the existing created_by plus a key format). WR-03 needs none.
</objective>
