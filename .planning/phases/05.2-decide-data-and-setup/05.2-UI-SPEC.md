# Phase 05.2 — UI Design Contract (Decide data and setup)

> Visual and interaction contract. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This file extends `05-UI-SPEC.md` (and through it `03-UI-SPEC.md` and `03.1-UI-SPEC.md`); it does not replace them.** Anything not stated here is inherited unchanged: theme tokens, `space` / `size` / `radii`, type roles, the `Sheet` engine (backdrop, drag, stacking, dismissal), toast and `UndoToastHost`, sync line, back history, FAB rules, reduced motion, the Decide copy guard (DCU-09). >

CLAUDE.md fidelity rule holds: **no new colour, gradient, shadow, type size, weight or icon set.** `noRawColours.test.ts` must keep passing. ## Setup stepper

### Shell (`SetupStepper`)

- **Presentation:** full-screen stack pushed over the Decide tab (`fw-push` in, `DURATION.push`), FAB and tab bar hidden (03 D-10). Android back and edge swipe do exactly what the on-screen Back does.
- **Header row:** Back circle (left); section name centred (`label`, `inkDim`, one line, ellipsis; wraps to two lines above 1.3x); right slot: **"Skip"** (`label`, `ink`, underlined, 44 high) on optional steps, or the plain text **"Needed"** (`label`, `inkMuted`, not a button, `accessibilityLabel` "Needed, this step can’t be skipped") on needed steps.
- **The section name has no counter.** The mockup’s "Income · 1 of 12" is dropped: the guide says sections, not numbers, so a branch never makes the count jump. Accessible name of the rail: "Section {n} of 5, {name}".
- **Rail (`SetupRail`):** five segments for Income · Regular payments · Spending · Your money now · Answers. Sections passed and the current one `accent`, later ones `line3`. Not tappable (jumping is done from Decide settings). The current section is named in the header text, so the rail is decoration (`accessibilityElementsHidden`) and the header carries the section for TalkBack. Standalone mode (Activity prompt) hides the rail and shows the single section name "Your income".
- **Body:** `Screen` scroll view, `keyboardShouldPersistTaps="handled"`, 22 side padding. Order: step title (`heading`, `accessibilityRole="header"`, receives focus on every step change), optional intro (`body`, `inkDim`), the controls, a "Why we ask" line (`s13_5`, `inkMuted`, starts "Why we ask: ..."). Where the records offer a prefill, the `PrefillNote` sits directly under the title.
- **Footer:** primary `Pill` "Next" (48 high, full width) and below it the text button "Finish later" (`label`, `inkDim`, 44 high, centred). The last optional step reads "Finish setup"; Welcome reads "Start". Needed steps with an incomplete answer: Next is `disabled` and a one-line reason (`meta`, `inkMuted`) sits directly above it ("At least one is needed to continue.").
- **Transition between steps:** content `fw-rise` (`DURATION.entrance`); the rail and header do not animate except the segment fill (`DURATION.progress`, once); both collapse under reduced motion. Focus moves to the new title.
- **Saving:** every step saves when Next is pressed (and on Skip only if an answer was already typed and valid; otherwise nothing is written and the step shows "Not set" later). A save goes through the serial write queue, works offline, bumps `version`, writes `undo_log`, and shows the standard Undo toast **only if the step changed something** ("{Step title} saved", action "Undo"; Undo restores that step’s previous answers). The toast is anchored above the footer (`bottom = footer height + space.gapMd`) and replaces the previous one; it never covers Next. Unchanged step: no write, no toast.
- **Back:** goes to the previous visible step with its saved answers showing; on the first step it returns to Welcome; on Welcome it closes. Never prompts, never loses anything.
- **Finish later:** saves the current step if its answers are valid, closes the stepper, returns to the Decide setup page, toast "Setup saved. Pick it up any time." (no Undo: nothing new is written beyond the step save, which already had its own toast). A half-done setup is marked **rough** (below).
- **Offline:** everything saves to the queue and the shipped `SyncStatusLine` / `SyncProblemLine` appear under the header only when offline or when writes are pending or failed (absent when online), unchanged copy. Prefills come from the cached snapshot. A failed write uses the existing failed-writes path.
- **Rough marking:** "rough" means a needed step has no answer yet, or a needed answer is a typed figure with fewer than 3 months of records behind it (the `rough_*` figures). The Decide setup page and Settings show a `StateChip` "Rough" (`warn1` on `warnTint`) and a **"Finish setup"** link until every needed step is answered. Finishing resumes at the first unanswered needed step.
- **Haptics (via `src/ui/haptics.ts`, async API only):** `selectionAsync` when choosing a card, chip, month tile, toggle or segment; `notificationAsync(Success)` once when the Summary appears. Nothing on Next, typing or scrolling.
- **Analytics (no amounts, no names):** `decide_setup_started`, `decide_setup_step_saved` {step key}, `decide_setup_finished`, `decide_setup_left` {step key}. Added to the catalogue.

### Flow, sections and branching

Needed (●) steps cannot be skipped. Optional (○) steps show Skip. The minimum setup is **6 screens, about 3 to 4 minutes**: how are you paid, regular pay **or** how to count changing income (its follow-up sits inline on the same screen), regular payments, everyday spending, account use, unspent money.

| Section (rail) | Step key | N / O | Shows when | Notes |
|---|---|---|---|---|
| (none) | `welcome` | n/a | always, first run | Start / Not now |
| Income | `paid` | ● | always | multi-select |
| Income | `pay` | ● | Salary or wages, or Pension or benefits chosen | one pay per card; "+ Add another regular pay" |
| Income | `season` | ○ | always (D-15), after `pay` / `paid`, before `method` | own screen (D-16) |
| Income | `method` | ● | Commission or tips, Freelance, My own business, or No fixed income chosen | follow-ups 3a / 3b / 3c inline on this screen |
| Income | `other` | ○ | always | chips; each chosen shows its detail card (4a) inline |
| Regular payments | `regular` | ● | always | candidate rows from the records |
| Regular payments | `loans` | ○ | always | debts + card pays-in-full question |
| Regular payments | `saving` | ○ | always | Fixed / Flexible + saving buckets (7a) + D-22 line |
| Spending | `everyday` | ● | always | prefilled typical month |
| Spending | `unusual` | ○ | 2 or more months of records | otherwise skipped silently |
| Your money now | `accountUse` | ● | at least one account that holds money | first in section (D-03) |
| Your money now | `emergency` | ○ | always | amount + account (D-04) |
| Your money now | `envelopes` | ○ | always | |

| Answers | `share` | ○ | always | |
| Answers | `detail` | ○ | always | |
| Answers | `reminders` | ○ | always | |
| (none) | `summary` | n/a | after the last step | |

A salaried user with no side income, one account and no unusual months sees about 15 screens (6 of them needed; see setupFlow.test.ts). Branch changes never alter the rail.

**Choice controls (shared rules).** Single choice = `ChoiceCard` list (radio, `accessibilityRole="radio"`, ink fill when selected, 12 gap, minimum 58 high) or a `Chip` row for short values (radiogroup, wraps, never `flex: 1`). Multi choice = `CheckRow` list (checkbox role, 44 hit) or a wrapping `Chip` set with `accessibilityState.selected`. Money = `MoneyInput` in a `fill6` tile (radius 16, 56 high minimum, `heading` size figure, currency prefix) with a visible caption above it (`label`) and a hint below (`meta`, `inkMuted`). Dates = `DateField`. Percent / months = `CustomValueChips`. **Nothing is pre-selected on a question the engine needs an honest answer to** (pay type, counting method, season, account use, Fixed / Flexible); prefills are shown as a `PrefillNote`, never as a selected state.

### Screen: Welcome (`welcome`)

- Title "Set up Decide" (`display`). Body (`body`, `inkDim`): "A few questions so Decide can check purchases against your real month. It uses your records and what you tell it. You can change any answer later."
- Meta line: "The required steps take about 3 to 4 minutes. Finish later saves your place."
- Footer: primary "Start"; secondary text button "Not now" (closes; nothing written).

### Screen: How are you paid? (`paid`) ●

- Title "How are you paid?"; intro "Choose all that apply."
- Six `CheckRow` cards (58 high): Salary or wages · Commission or tips · Freelance or self-employed · My own business · Pension or benefits · No fixed income right now. "No fixed income right now" is exclusive (choosing it clears the others; choosing another clears it).
- Why we ask: "Steady pay and changing pay are checked in different ways."
- Next disabled until one is chosen ("At least one is needed to continue.").
- Stores the six setup values in `income_types` (D-17); the engine mapping is computed from them (Pension or benefits counts as regular pay, `salary`; My own business counts as changing income, `freelance`). The summary and settings words use what the user picked.

### Screen: Your regular pay (`pay`) ●

- Title "Your regular pay". `PrefillNote` when found: "We found {payer} paying about {amount} around the {day} of each month." (the mockup’s "Acme Ltd" example).
- Card per pay (one visible, "+ Add another regular pay" (`ink`, underlined) adds a card; each extra card has a "Remove" text button, danger, 44 high): caption "Take-home amount, after tax" with `MoneyInput`; "How often" `Chip` row Weekly · Every 2 weeks · Monthly; meta under it: "Paid on the 1st and 15th? Choose Every 2 weeks. Decide counts it as 24 payments a year."; "Next pay date" `DateField`.
- Why we ask: "Your regular pay is the starting point for every month."
- Next needs an amount above 0, a frequency and a date. Saving creates or updates the regular income series through the existing series mutation.

### Screen: Does your income change by season? (`season`) ○ (D-15, D-16)

- Title "Does your income change by season?" Intro: "This includes wages paid for part of the year, like school staff paid 10 months."
- Three `ChoiceCard`s, none selected: **Steady** "About the same each month." · **Changes month to month** "Some months are higher or lower." · **Follows the seasons** "Some months are always higher or lower, or have no pay."
- Why we ask: "A quiet season can be planned for instead of showing up as a surprise." Stores `IncomeProfile.pattern` (`steady | variable | seasonal`).
- Skip leaves it unset; the engine asks during a check when it finds swings (D-34). Asked of everyone, salaried users included.

### Screen: How should Decide count it? (`method`) ●

- Title "Your income changes. How should Decide count it?" Intro "Pick the one that fits you. Nothing is chosen for you."
- Four `ChoiceCard`s, none selected, each with title, description and an italic-free example line (`s13_5`, `inkMuted`; the mockup’s italics are dropped, no new style):
  - **Match what comes in.** "Count income only once it arrives." Example "$2,200 came in this month, so this month has $2,200."
  - **Spread large payments.** "A big payment covers several months." Example "A $9,000 contract paid in March covers March to May: $3,000 a month."
  - **Pay myself a steady amount.** "Count a fixed amount; extra money adds to unspent money." Example "You count $3,500 a month. A $5,000 month adds $1,500 to unspent money."
  - **Go by my bank balance.** "Look at what’s in the bank, minus bills coming up." Example "Balance $8,000, minus 2 months of bills, is what’s available."
- Follow-ups appear **under the selected card** with `fw-rise`: Spread: "How many months does a large payment usually cover?" chips 1 · 2 · 3 · 6 · 12 · "It varies, ask me each time". Steady: caption "What steady amount do you count each month?" `MoneyInput`, meta "Your last 6 months averaged {X}; your lowest month was {Y}." (when 6 months exist, else omitted). Balance: "How many months of bills should be held back?" chips 1 month · 2 months · 3 months.
- Why we ask: "Uneven income can make a month look better or worse than it is. You decide which picture fits you."
- Next needs a method plus its follow-up answered. Examples use the owner’s illustrative figures; they are static copy, not the user’s data.

### Screen: Any other money coming in? (`other`) ○

- Title "Any other money coming in?" Intro "Choose all that apply, or None."
- Wrapping chips: Side business or gig work · Rent from a property or room · Dividends or investment income · Interest · Child support or family support · Other · None (exclusive).
- Each chosen chip adds a detail card (4a): name (`sheetTitle`) with the found amount right-aligned (`body`, nowrap, e.g. "$600/mo" from records, else a `MoneyInput` caption "About how much"); "How often" chips Weekly · Every 2 weeks · Monthly · Every 3 months · Yearly · It varies; "What happens to it?" two-option `SegmentedToggle` **"I spend it or it’s available"** / **"It’s reinvested or kept"**. "Other" adds a text field "What is it?" (max 40 characters).
- Why we ask: "Only money you actually use counts toward your month. Reinvested dividends don’t."
- Stores a regular income series per line with `income_kind` and `counts_as` (`available` / `kept`).

### Screen: Your regular payments (`regular`) ●

- Title "Your regular payments". Intro: "We found these in your records. Only the ones you confirm count as regular." Counter line (`label`, `ink`): "{n} of {m} marked".
- A `Card` row per candidate (candidates are computed on device, not stored): name (`sheetTitle`) and "{Monthly} · around the {day}" (`meta`, `inkMuted`) left, amount right (`body`, nowrap). Under it three buttons **Regular** · **Not regular** · **Edit** (44 high, `Chip`-styled; one row of three at 360 dp and above and scale 1.3x or less; stacked full width otherwise). - Also reachable from: the transaction detail ("Income type" row) and the regular-income series sheet (new rows **"Income type"** and **"Counts toward my month"**).

### `IncomeTagSheet` and the once-only new-payer question

- `Sheet`. For a new payer the eyebrow reads **"NEW KIND OF INCOME"** (`eyebrow`, `warn1`); manual re-tagging omits it. Title **"What is this income?"** (`sheetTitle`). Sub-line "{payer} · +{amount} · {date}" (`meta`, `inkMuted`, amount nowrap).
- Kind chips (radiogroup, wrapping, none selected): Salary or wages · Commission or tips · Side business · Dividends · Interest · Rent · Family support · Other. (The mockup’s "Refund or one-off" is **not** included: a credit counts as a refund only when the user links it, so refunds use the picker below.) Under the chips a text link (`label`, `ink`, underlined, 44 high): **"It’s a refund of a purchase"**, which closes this sheet and opens `RefundPickerSheet` for the same transaction.
- "Does it count toward your month?" `SegmentedToggle` **"I spend it or it’s available"** / **"It’s reinvested or kept"**, neither selected.
- `ToggleRow` **"Apply to future payments from {payer}"**, default **On**, with a count line above Save (`meta`, `inkMuted`): **"This also tags {n} earlier payments from {payer}."** (singular "1 earlier payment"; the line is absent when there are none). The count is shown before the user saves, so nothing is changed without being told (D-21). Earlier payments the user already tagged themselves keep their own tag.
- Buttons: secondary **"Not now"** (closes; the chip stays, so the question is asked again until it is answered) and primary **"Save income type"** (disabled until a kind and a count choice are made).
- Save writes the transaction’s `income_kind` / `counts_as` and, when the toggle is On, the payer rule, in **one queued batch mutation** (this transaction, the payer rule and every earlier untagged payment from that payer, one `undo_log` entry). Toast with **one Undo that reverses every row**: **"Tagged {n} payments from {payer}"** (n counts this payment and the earlier ones; "Tagged 1 payment from {payer}" for one; "Saved for future payments from {payer}" when the toggle is On and nothing else was tagged; "Income type saved" when the toggle is Off). **Offline:** the batch is queued as a single item; every affected row’s chip updates at once and shows the shipped pending marker; the sync line shows pending writes; Undo while queued reverses the whole batch locally before it syncs; a failed batch uses the existing failed-writes sheet with the label "Tagged payments from {payer}" and no row is left half-tagged. Haptic: `selectionAsync` on chips and toggles.
- Once answered with the toggle On, the question is never asked again for that payer. A payer already covered by a rule shows the tagged chip with no question.

### Refund link (D-06 to D-10)

- **Entry:** on a money-in transaction’s detail a new row **"Refund of..."** (value "Not linked" or "{payee} · {date}"). Also from the tag sheet link above. A purchase’s detail has a **"Refunds"** group: one row per linked refund (payer, date, amount, chevron to the refund) and a text button **"+ Link a refund"** (`label`, `ink`, underlined) (picker in the reverse direction, listing unlinked money-in transactions).
- **`RefundPickerSheet`:** title **"Which purchase was refunded?"**; sub-line "{payer} · +{amount} · {date}"; a `TextInput` "Search purchases" (matches payee, note, amount); a list capped at 50 candidates (expenses in the same currency in the last 12 months; same payee first, then newest), each a radio `Row` (payee `sheetTitle`, "{date} · {category}" `meta`, amount `body` nowrap). A purchase already part-refunded also shows "Refunded {x} so far" (`meta`, `warn1`). Empty search: "No purchases match" / "Try a payee name or an amount."
- **"What this does" tile** (`fill1`, radius 16, `s13_5`, `inkDim`; appears once a purchase is selected), exactly one of:
  - full: "This refunds the whole purchase. Decide treats {purchase month} and {refund month} as net $0 for it."
  - partial: "{x} of the purchase stays as spending in {purchase month}."
  - several: "Refunded so far: {sum} of {price}."
  - over (D-06): "{x} more than the price. That part counts as money in for {refund month}."
  - plan purchase (D-09), added as a second line: "This purchase is on a payment plan. The plan’s payments continue until you change or end the plan."
  Always the footer line: "Your balances and records stay exactly as logged. Only Decide’s view changes."
- Buttons: primary **"Link refund"** (disabled until selected); when already linked also text **"Remove link"** (danger, no confirm; toast "Refund unlinked" with Undo). Link toast **"Refund linked"** with Undo.
- **In Activity (D-10):** the refund row shows a tag **"Refund of {payee} · {date}"** (`fill1`, `inkDim`, `tabLabel`; tapping opens the purchase’s detail). The purchase row shows **"Refunded {x}"** (same style; the total of all linked refunds; tapping opens its detail). Balances and the row amounts are not changed. Labels: "Refund of {payee}, {date}. Opens the purchase." / "Refunded {x}. Opens the purchase."
- Linking, unlinking and every additional refund are queued writes with `version` and `undo_log`; the picker works offline from the cached list.

## Interaction states and motion

- **Motion (via `src/theme/motion.ts`; reduced motion collapses all):** stepper push `DURATION.push`; step content and revealed follow-ups `DURATION.entrance` (`fw-rise`); rail fill `DURATION.progress`, once; sheets per 03. No new motion token.
- **Pressed:** tappable rows, cards, tags, links `PRESSED_OPACITY` (0.72). Disabled primary `Pill`: shipped disabled look plus `accessibilityState.disabled`.
- **Loading:** skeleton bars (`fill1`, final size, no shimmer) for the worked sum, the readout, the candidate lists; container `accessibilityState.busy`.
- **Offline:** every save is queued; every read is from the cached snapshot; the sync line shows the state. Queued state of a row: the shipped pending marker on the row (the same one Activity rows use).
- **Failed write:** the existing failed-writes path; the step stays on screen with its answers.
- **Conflict:** the existing "changed elsewhere" message when `version` mismatches.
- **Haptics (complete list, async API only):** `selectionAsync` on choosing; `notificationAsync(Success)` when the Summary appears; a swipe or removal uses the shipped `hapticLight`. Nothing on typing, scrolling, Next, or toasts.

## Accessibility and quality rules

- **Fit:** every screen and sheet is checked at **320 and 402 dp wide, at font scale 1.0 and 2.0** (and the Pixel density matrix in the project memory). Body text wraps or stacks; capped display figures hold at 1.3x. Choice-card lists, month tiles, three-button rows, figure strips and label-figure rows reflow to one column above 1.3x scale or below 360 dp. The footer (Next + Finish later) stays visible at 2.0x; the body scrolls, the footer does not.
- **No broken numbers:** all currency goes through `heroAmountText` / `useMoneyFormatter`, one line, never split; tests assert it for the hero figure, the worked-sum lines, tag chips, refund tags and readout values at 2.0x.
- **TalkBack / VoiceOver:** every control is a real button, radio, checkbox, switch or input with a label. Step titles are headers and take focus on each step change. The rail is hidden from assistive tech; the header text carries "Section {n} of 5, {name}". `ChoiceCard` = radio with checked state; `CheckRow` = checkbox; `ToggleRow` = switch; month tiles announce "{Month}, {amount}, {status}. Tap to change." and announce the new status; the "Needed" text reads "Needed, this step can’t be skipped"; disabled Next announces its reason line (the reason is `accessibilityHint`); the D-22 tile is a group "{text}. Two choices." Toasts are polite live regions with the Undo action focusable. Sheets trap focus and return it to the opener.
- **Touch targets:** 44 dp minimum everywhere (`hitSlop` for chips-in-rows, checkboxes, chevrons, tag chips).
- **Contrast:** at least 4.5:1 for all text (pairs listed under Color; forbidden pairs listed there). Non-text meaning is never colour-only.
- **Reduced motion:** all entrances and the rail fill collapse; nothing relies on motion to convey state.
- **Privacy:** no amounts or names in analytics or notifications.
- **Data rules (UI-visible):** every write goes through the serial write queue, works offline, writes `undo_log`, bumps `version`, uses soft deletes, and has the Undo toast (tables above); all new surfaces vanish for accounts without the switch.
