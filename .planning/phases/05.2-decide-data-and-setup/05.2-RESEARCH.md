## Summary

Everything the v3 engine needs from the user is either a stub today (`buildV3Inputs` returns `unexplainedAnswer: null`, `payArrivals: []`, `expectedIncome: []`, `heldBridges: []`, `pattern: null`, account `use: null`) or has no column at all (income profile, unspent anchor, everyday override, month marks, rough_saving/debt/invest, series `counts_as`/`income_kind`/`saving_mode`/`pay_group`, `recurring_dismissals`, bucket, refund link, account use). None of the §7.3 migrations exist yet; the latest migration is `20261024000200`. [VERIFIED: grep of `supabase/migrations/*.sql` for every new column name returned nothing]

The phase has five hard technical spines, in order of risk:

1. **Undo for settings is not free.** `decide_settings` has `user_id` as primary key, no `id`, and `apply_patches` / `undo_log` only know uuid-`id` entities. The existing settings mutation is an unconditional upsert with no undo step. Setup steps need an Undo toast backed by `undo_log`, so the table needs an `id` and an entry in `apply_patches` (the 7th full copy of that function). `PatchValue` is scalar-only, so `text[]` / `jsonb` columns must be patched as strings with an explicit cast branch.
2. **Saving buckets collide with a database constraint.** `savings_goals_pot_shape` (20261024000100) forces every pot to have a target and `ready_by` and a null `monthly_amount`, and `guard_savings_goal` resets `monthly_amount` on pots. UI-SPEC buckets have a monthly amount, an optional goal and no date. The `savings_goals_buckets` migration must relax the shape check and the guard for bucket rows; the engine already supports `target = null` with `monthlyAmount` (`potSetAside`).
3. **Refund re-dating needs a new optional engine field and a pre-pass.** Refunds today are a `refund` line role netted in the month they arrive. A linked refund needs `V3Line.refundOf` (additive optional) and a pure pass that moves the refund into the purchase month (capped at the price, surplus stays as money in) before every consumer reads `months`.
4. **D-23 is a real double count.** `setAsideOf()` (`month/model.ts`) adds fixed saving series AND every envelope's monthly set-aside. Bucket envelopes are carved out of regular saving, so the engine needs to know which envelopes are buckets (`Envelope.bucket`, additive optional) and count `max(bucketTotal, fixedSavingTotal)` for that group.
5. **Production gate.** Several things only work once migrations reach production (per-account flag on the owner's real account). D-14 allows exactly one approval; the plan must end in a blocking human checkpoint that runs `npm run supabase:preflight` then `npm run supabase:db:push`.

Two scope realities the planner should know: there is **no user-account-deletion function and no data-export feature in the repo yet** (ACC-10 and DAT-02 are Phase 10); "purge" today means `ON DELETE CASCADE` foreign keys, proven by pgTAP `36_account_deletion.test.sql`. 05.2 therefore proves cascade for every new table and adds an export manifest that Phase 10 will consume. And UI-SPEC names `src/features/activity/` and `src/features/income/`; **Activity actually lives at `src/features/record/activity/`** and `src/features/income/` does not exist yet.

**Primary recommendation:** Build in this order: (W1) additive migrations + pgTAP + generated TS row types and db modules, behind the new `profiles.decide_v3` flag; (W2) engine/snapshot pure work (refund field, D-23 fix, `refine.ts`, real `buildV3Inputs` mapping) at 100% branch coverage; (W3) mutations (settings with undo, account use, series attributes, income tags, refund link, answers table, buckets); (W4) UI (shared `IncomeProfileSteps`, stepper, settings, sheets, Activity parts, test-account page); (W5) shadow/I28 re-run with owner checkpoint on new fits; (W6) blocking production-migration checkpoint.

### Pattern 1: A queued, undoable single-row edit (copy this)
**What:** Forward write through a `setMutationDefaults` entry with `scope: WRITE_SCOPE`, `retry: shouldRetryWrite`, optimistic cache patch, version chain, then `recordUndoStepSafely` with inverse ops built from the captured before-state and the version the server returned.
**When to use:** every account, series-attribute, savings-goal, debt, transaction and answer write.
**Analog files:** `src/data/mutations/decidePots.ts` (add/edit/delete/done/reopen with undo), `src/data/mutations/accounts.ts` (`editAccount`, line 133), `src/data/mutations/debts.ts`, `src/data/mutations/patches.ts` (`useBulkPatch`, line 254, one atomic `apply_patches` with one undo step).
```typescript
// Source: src/data/mutations/decidePots.ts (read 2026-10-27)
qc.setMutationDefaults(mutationKeys.addPot, {
  mutationFn: (vars: AddPotVars) =>
    guardSession(vars, async () => {
      const client = await writeClient();
      const row = await insertSavingsGoal(client, vars.row);          // 23505 is read back as landed
      const step = buildStep(vars.stepId, 'potAdded', labelParams(vars.row.name),
        inverseOfInserts('savings_goals', [{ id: row.id, version: row.version }]));
      await recordUndoStepSafely(qc, client, step, vars.ownerId);
      return row;
    }),
  scope: WRITE_SCOPE, retry: shouldRetryWrite, retryDelay: writeRetryDelay,
  onMutate: async (vars) => { markSession(vars); /* optimistic upsert with pending: true */ },
  onError: async (err, vars) => { /* roll back cache; recordFailedWrite with ids only, no amounts */ },
});
```

### Pattern 2: Settings write (the existing singleton) plus an undo step
**What:** Keep `upsertDecideSettings` (unconditional upsert; `DECIDE_SETTINGS_PATCH_KEYS` mirrors the grant). After success, record an undo step whose op patches the previous values back with `expectedVersion = row.version`. Needs the `id` column and the `decide_settings` entity (see Pitfall 1).
**Analog:** `src/data/mutations/decideSettings.ts` (confirmed-row map, `pendingSettingsEdits`) for the forward half; `decidePots.ts` for the undo half.

### Pattern 3: Batch write with one Undo (payer tagging, refund link, Reset)
**What:** One `apply_patches` call with up to 6000 ops and one `p_undo_step`. A conflict refuses the whole batch.
**Analog:** `useBulkPatch` in `src/data/mutations/patches.ts`; offline it is one queued item (matches UI-SPEC "queued as a single batch"). The undo step for "Tagged {n} payments" is the same op list with the previous `income_kind`/`counts_as` values.

### Anti-Patterns to Avoid
- **Writing a Decide copy of data another feature holds** (05.1 D-53). Account use lives on `accounts`; envelope placement on `savings_goals`; regular payments are `recurring_series`; candidates are never stored.
- **Reading `DECIDE_V3` anywhere except `availability.ts`.** `availability.test.ts` asserts exactly two mentions in exactly one file. [VERIFIED: `src/features/decide/__tests__/availability.test.ts`]
- **Importing from `src/engine/decide/<file>` outside the barrel.** depcruise rule `decide-engine-barrel-only` allows only `index.ts` and `v3/index.ts`. New exports (`refine`, `redateRefunds` if the snapshot needs them) go through `v3/index.ts`, which `barrel.test.ts` pins. [VERIFIED: `.dependency-cruiser.cjs`]
- **Float money or `Number` sums in the engine.** bigint inside functions, `minorFromBigInt` out.
- **Copy that advises.** DCU-09 guard (`src/i18n/__tests__/decideCopy.test.ts`, `catalogue.test.ts`).

## Refund linking (D-06..D-11)

**How refunds are represented today.** `transactions.is_refund` marks a money-in row (check: positive amount, not a transfer). `buildSnapshot` copies it to `RecordLine.isRefund`; `buildV3Inputs.roleOf` maps money-in `isRefund` to `LineRole 'refund'`. Statement import (`src/engine/statement/refundMatch.ts`) already *suggests* refunds of earlier purchases and assigns the purchase's category — that is the existing suggestion mechanism; it never links. Engine uses: `month/typical.ts` `everydayByMonth` subtracts `refund` from the month it is dated in (floored at 0); `month/thisMonth.ts` subtracts refunds from the month's everyday; `funds/unspent.ts` `rollForward` adds a later-month refund back in full (the 05.1-18 finding, documented in `funds/build.ts`). [VERIFIED: file reads]

**Storage (recommended).** `transactions.refund_of uuid` (nullable self-FK, `on delete set null`) plus the existing `is_refund`. Linking sets both in one `apply_patches` op list (`{refund_of, is_refund: true}`), one undo step; unlinking sets `refund_of = null` (leave `is_refund` as the user had it: if the user never flagged it before, restore the previous value from the captured before-state). Multiple refunds → many rows with the same `refund_of` (D-08). Totals refunded on a purchase are derived, not stored.

**Behavior of unlinked `is_refund` rows is unchanged** (netted in their own month). This is consistent with owner decision 2 ("counts as a refund only when the user links it") only if "refund" here means *re-dated*; flag for confirmation (Open Question 8).

**Engine change (D-11).**
- `types.ts`: add optional `refundOf?: string | null` to `V3Line` (additive; the file header allows "additive optional fields only" with a note in the plan SUMMARY and a 05.3 heads-up).
- New pure `month/refunds.ts`: `redateRefunds(months: readonly V3Month[]): readonly V3Month[]`. For each `refund` line with `refundOf`: find the purchase line by id across months; if absent (purchase older than the 12-month read window, or deleted) leave the refund where it is (conservative; document). Sum linked refunds per purchase in date order; the part up to the purchase price is moved to the purchase's month (re-dated copy of the line with the purchase date's month, same category as the purchase — **the shortfall stays as spending in the purchase month and the refund line takes the purchase's category**, owner decision 3; use the purchase `categoryId` when the refund's differs); any amount above the price stays in the refund's own month as `other_in` money in (D-06). ## Common Pitfalls

### Pitfall 1: `decide_settings` cannot be undone as it stands
**What goes wrong:** Setup steps promise "Undo restores that step's previous answers" via `undo_log`; `apply_patches` selects `... where t.id = $1` and only allow-listed entities, `UndoEntity`/`UNDO_ENTITIES` exclude settings, and the table has no `id` (PK `user_id`).
**Why:** The table was built as a singleton with unconditional upserts and no undo (`decideSettings.ts`).
**How to avoid:** `decide_settings_v3` adds `id uuid not null default gen_random_uuid() unique`; add entity `decide_settings` (scope = `user_id = auth.uid()`) to `undo_log_fill`, the three entity lists and `v_col_type` in the re-created `apply_patches`; add it to `UndoEntity`, `UNDO_ENTITIES`, `WriteEntity`. `PatchValue` is `string|number|boolean|null`: patch `text[]`/`jsonb` columns as strings and add `text[]`/`jsonb` cast branches to `v_col_type` (`($2 ->> key)::text[]` accepts `'{a,b}'`; `::jsonb` accepts a JSON string). The inverse of the first-ever write must be a patch back to nulls, so ensure the row exists (empty upsert) before capturing the before-state.
**Warning signs:** `apply_patches: op N has an unknown entity` or `patches unknown column` at replay time; Undo does nothing for a settings step.

### Pitfall 2: Buckets violate the pot shape constraint
**What goes wrong:** Inserting a bucket (no target, no date, monthly amount) fails `savings_goals_pot_shape` (`kind <> 'pot' or (target is not null and ready_by is not null and monthly_amount is null and check_id is null)`); `guard_savings_goal` also forces `monthly_amount := old.monthly_amount` for pots; client `NewPot` requires `target` and `ready_by`; `validatePot` rejects `target < 1`.
**How to avoid:** the `savings_goals_buckets` migration re-creates both the constraint (bucket rows: `bucket is not null` ⇒ target and ready_by optional, `monthly_amount` allowed) and the guard from the LATEST definition; extend TS types/validation; engine side already works with `target = null` (`potSetAside`). pgTAP: non-bucket pots still rejected without target/date; bucket accepted at $0.
**Warning signs:** `23514 check_violation` on bucket insert; monthly silently reset to null.

### Pitfall 3: Seven copies of `apply_patches`
**What goes wrong:** Re-creating the function from an older file silently drops entities/columns added later (e.g. `is_housing`, `savings_goals` widening).
**How to avoid:** copy from `20261024000100_pots_and_debt_housing.sql` (latest), diff to confirm only intended lines changed; pgTAP `55_decide_patches` / `61_pots_and_debt_housing` / `35_series_undo` must still pass; add one new test per added entity/column. One migration (`apply_patches_v3`) after all table migrations so it can reference them.

### Pitfall 4: Per-account flag read in two places
**What goes wrong:** A second reader of `DECIDE_V3` or an inline `profile.decide_v3` check breaks `availability.test.ts` ("only availability.ts mentions DECIDE_V3, exactly twice") or lets screens disagree.
**How to avoid:** one hook, one function; tests per surface.

### Pitfall 5: Suggested account use counted as real
**What goes wrong:** UI shows a guess ("Everyday?") but stores it, so unspent money counts an account the user never confirmed.
**How to avoid:** guesses are client-only until "These look right" or the row is edited; stored `use` null means unanswered and `buildV3Inputs` passes `use: null` (engine reports `account_use_question`).

### Pitfall 6: Double counting set-aside (D-23)
See D-23 section. Test with concrete numbers; also check the instead/explorer code path for another sum.

### Pitfall 7: Refund re-dating applied in only some consumers
**What goes wrong:** `typical` re-dated but `rollForward` reads raw months (or vice versa), making unspent and typical month disagree.
**How to avoid:** one pre-pass at `evaluate()` entry; grep every reader of `inputs.months`; a golden that checks both `typicalLeft` and `unspent` for the same linked refund.

### Pitfall 8: One step, many writes, one Undo
**What goes wrong:** A stepper step creates a series (RPC), patches attributes, writes settings and moves an account use; there is no single transaction for all of these, so "Undo this step" can undo only part.
**How to avoid:** decide per step what is atomic: express as `apply_patches` where possible (patches on existing entities); for inserts use `inverseOfInserts` into the same step id; document steps that need two Undo entries and make the toast label say what it undoes. Test partial failure leaves no half-state (the UI-SPEC requires "no row is left half-tagged").

### Pitfall 9: Held-bridge release
**What goes wrong:** A stored bridge is never released when the plan is paid off or cancelled, so unspent stays understated.
**How to avoid:** derive in the mapper: a bridge counts only while its check is `bought` and not deleted, and (for plans) while its debt/series is live with balance > 0; unit-test each release path in the 100% snapshot folder. Storage keyed by check id.

### Pitfall 10: UI-SPEC paths and unspent date type
UI-SPEC names `src/features/activity/`; real path is `src/features/record/activity/`. UP §4.9 types `unspent_anchor_at` as `timestamptz` but `buildV3Inputs` expects `YYYY-MM-DD` (`dateOf`). Use `date` columns for `*_at` fields read by the engine mapper.

### Pitfall 11: Stale `reviewed` / approved-changes after the refund change
**What goes wrong:** Refund goldens change legacy comparisons, `approved-changes.json` gets stale entries or missing new-fit reasons and `shadow.test.ts` fails CI.
**How to avoid:** the plan sequence is engine change → run shadow + I28 → owner checkpoint → update `approved-changes.json` with owner-approved reasons → green. Never edit the file to silence the gate.

### Pitfall 12: Local machine load
05.1-32 notes 8 UI suites timing out under heavy CPU load. Run suites per folder (`npx jest <path>`) and use `--maxWorkers=4` for coverage; don't treat load flakes as regressions without re-running alone.

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Client enabling the v3 flag for itself | Elevation of privilege | No update grant on `profiles.decide_v3`; pgTAP asserts `42501` |
