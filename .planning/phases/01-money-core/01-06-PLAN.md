FND-10 is about compatibility with old app versions, not lock or style hygiene, so the gate KEEPS exactly these rules (names as squawk spells them; confirm each exists in 2.66.0): `ban-drop-column`, `ban-drop-table`, `ban-drop-database`, `renaming-column`, `renaming-table`, `changing-column-type`, `adding-required-field`, `adding-not-nullable-field`, `ban-truncate-cascade`. Write `.squawk.toml` with `excluded_rules = [ ...every other rule in the live list... ]` and a leading comment explaining why (FND-10 / D-27: compatibility only; lock-safety rules are out of scope for a single small production project and would flag every Phase 0 migration). 2. Run `npx squawk-cli supabase/migrations/*.sql` and confirm every existing migration (Phase 0 plus 20260924000100-000500) passes. If a kept rule flags an existing Phase 1 migration, that is a real finding: fix the migration if it is not yet pushed (none of the 2026092400* files are pushed yet), otherwise stop and report.
3. `scripts/check-migration-compat.mjs` (Node builtins only, ESM). Usage: `node scripts/check-migration-compat.mjs [dir]` (default `supabase/migrations`). Logic:
   - Read `*.sql` files sorted by filename.
   - Track the floor: start at null; for each file, in order, apply `insert into public.app_config ... ('min_supported_version', 'X')` and `update public.app_config set value = 'X' where key = 'min_supported_version'` (case-insensitive regex, tolerant of whitespace) to update the floor BEFORE evaluating that file's markers only if the update appears above the marker line; simplest correct rule: a file's markers are checked against the floor as it stands after all EARLIER files (a floor bump and a destructive change must ship in separate migrations, the bump first, per expand/contract).
   - For every `-- squawk-ignore <rule>` line whose rule is one of the kept compatibility rules, the same file must contain `-- contract-ok: min_version >= X.Y.Z`. Missing marker → error naming file and rule.
   - Parse X.Y.Z as semver (numeric compare of three parts). If floor is null or floor < X.Y.Z → error: "`<file>` needs min_supported_version >= X.Y.Z but the floor at that point is <floor>".
   - A marker without any squawk-ignore is allowed (no-op) but printed as a warning.
   - Exit 1 on any error; print `MIGRATION COMPAT OK (<n> files, floor <v>)` on success.
4. Add npm scripts to package.json (do not touch dependencies): `"lint:migrations": "squawk supabase/migrations/*.sql && node scripts/check-migration-compat.mjs"` (use `npx squawk-cli` if the installed binary name is not `squawk`; check `node_modules/.bin`), `"verify:migrations": "node scripts/verify-migration-gate.mjs"`, `"check:money-mirror": "node scripts/gen-money-mirror-test.mjs --check"`. On Windows the glob in an npm script is not expanded by cmd; make `check-migration-compat.mjs` optionally invoke squawk itself with an explicit file list (spawnSync with the resolved file paths) and have `lint:migrations` call only the node script, so the command is shell-independent.
