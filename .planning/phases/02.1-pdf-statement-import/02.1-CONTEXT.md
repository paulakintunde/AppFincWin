# Phase 2.1: PDF statement import - Context

**Gathered:** 2026-09-26
**Status:** Ready for planning

<domain>
## Phase Boundary

A user can import a **text-based PDF** bank or card statement through the same statement-import pipeline Phase 2 builds for CSV and OFX. The pipeline covers the format read-back, preview, duplicate check, transfer suggestions and one-step undo. Figures are committed only when the balances reconcile or the user has reviewed every row that could not be verified. If the PDF has to leave the phone to be read, the file is deleted straight after reading, no statement content reaches logs or error reports, and the privacy copy says where the file is processed and how long it is kept.

Requirements: IMP-01, IMP-02, IMP-03, IMP-04.

PDF is **one more format adapter** into Phase 2's pipeline (Phase 2 D-40). It produces a `StatementDraft` like the CSV and OFX adapters. Phase 2.1 does not build a second transaction model, a second preview, or its own duplicate, transfer or undo logic.

Not in this phase: scanned or photographed statements (OCR), an AI reader for unknown layouts, keeping a copy of the original statement, splitting one PDF into several accounts, the share-sheet entry point, queueing PDF reads while offline, and Free/Pro gating (Phase 9).

</domain>

<decisions>
## Implementation Decisions

### Where the PDF is read
- **D-01:** **Research decides where the PDF is read.** The candidates are on the phone, a Supabase Edge Function, or a separate worker service. Research must test each candidate against real statements, not only reason about it.
- **D-02:** **Tie-break: the phone wins if it is good enough.** Keeping "your statement never leaves your phone" (Phase 2 D-17) is worth some reading quality. A server is used only if on-device reading cannot meet the D-03 bar.
- **D-03:** **"Good enough" means:** a typical statement of up to about 10 pages reads with its balances reconciling, in under about 10 seconds on the iPhone XR, without running out of memory. A server option has to clear the same outcome bar.
- **D-04:** **If the file is uploaded, it is processed only in the existing Supabase project's region (us-west-2),** under the same DPA as all other user data. There is no second region, and the region is named in the privacy copy. A separate worker service can win only if Supabase cannot do the job, and it then brings a new sub-processor and DPA. Research must call that cost out explicitly.
- **D-05:** **Upload consent is a one-line notice on every PDF import,** shown before the file is sent. Example: "To read a PDF we send it to our server in the United States. It's deleted straight after." Continue proceeds. There is no settings toggle and no remembered consent. If reading happens on the phone, this notice does not appear.
- **D-06:** **If server reading is needed and the phone is offline, the app says so and queues nothing.** Example: "PDF statements need a connection to read. Try again when you're online." CSV and OFX still import offline, as in Phase 2.
- **D-07:** **Size limit is about 25 pages or 10 MB.** Larger files get a clear "split the file" message, in the same way as Phase 2's 5,000-row limit (D-18). Research may adjust the figures if real statements need it, but a limit must exist.
- **D-08:** **The PDF comes in through the file picker only.** It uses the same "Choose file" entry as CSV and OFX (`expo-document-picker`, installed by Phase 2), and the format is sniffed from the file's content (Phase 2 `sniffFormat`).
- **D-09:** **PDF import is built for all users, with no gating.** Tiering belongs to Phase 9, which should weigh the server cost if reading turns out to be server-side.

### File retention and privacy
- **D-10:** **An uploaded PDF is deleted as soon as its rows are extracted,** before the user commits. The preview, a flipped format reading (Phase 2 D-42) and the commit all work from the extracted draft, never from the file.
- **D-11:** **There is no "keep a copy" option in Phase 2.1.** The original file is never retained. Phase 2 D-45 already keeps each row's raw values for tracing. IMP-03's "a kept file is removed on account deletion" clause therefore has nothing to act on in this phase. Record that explicitly so Phase 10's account deletion knows there is no statement store to purge.
- **D-12:** **Abandoned uploads are purged within 24 hours.** A scheduled job (pg_cron, as the FX jobs already use) deletes any statement file older than 24 hours, whatever its state. It is a backstop for when the normal delete in D-10 fails, such as a crash or a closed app.
- **D-13:** **The server keeps nothing from a statement.** Extracted rows go back to the phone in the response and are never written server-side. The only stored data is what the user commits, through Phase 2's normal transaction path, with RLS and FX stamping unchanged.
- **D-14:** **When a statement can't be read, only an anonymous layout fingerprint may be kept.** That means: the bank name if detected, page count, column headers, and which step failed. It must never include amounts, names, dates, descriptions or account numbers. Its purpose is to decide which bank templates to add (D-18).
- **D-15:** **Server logs and Sentry get metadata only:** outcome, duration, page count, file size, layout id and error class. Never text, amounts, names, file names or account numbers. It is enforced by a scrubber, alongside the existing `src/services/errors/scrub.ts`, plus an automated test that runs a sample statement through reading and asserts nothing from it appears in logs or error events (IMP-03).
- **D-16:** **The phone's temporary copy is deleted too.** The picker's cached copy of the PDF is removed once the import is committed or cancelled, so the statement isn't left in the app's storage.
- **D-17:** **Privacy copy states where the file is read and how long it is kept (IMP-04).** In the import screen and in the privacy policy. If reading is server-side, example wording: "PDF statements are read on our server in the United States and deleted straight after. CSV and OFX files never leave your phone." If research picks on-device reading, the copy says the PDF never leaves the phone. The voice stays declarative, with no "we recommend" (PROJECT.md compliance rules).

### Layouts and files that can't be read
- **D-18:** **One generic reader, with bank templates added only where needed.** A generic reader for tables and text in any text PDF is gated by Phase 2's reconciliation (D-46). A template for a specific bank is added only when real users upload that bank and the generic reader gets it wrong. This fits Phase 2 D-11 (no presets up front).
- **D-19:** **Research chooses the test banks and statements** from the sample statements it can find, with personal details removed. Neither the user nor this discussion named particular banks. The fixture set should cover at least one current account, one savings account and one credit card, statements with and without a running balance, and one statement that spans the new year.
- **D-20:** **An unreadable PDF gets a plain reason and a pointer to CSV/OFX.** Example: "We couldn't read this statement's layout. Most banks also let you download CSV or OFX from online banking, and those import reliably." Nothing is committed, and the file is deleted under D-10 and D-12.
- **D-21:** **Password-protected PDFs are supported.** The app asks for the password and uses it only to open this one file. The password is never stored or logged. If reading is server-side, it travels with the upload over TLS and is discarded after reading.
- **D-22:** **One account per import**, as in Phase 2 D-12. If a PDF covers several accounts (for example chequing and savings), the user picks which section to import and runs the import again for the others.
- **D-23:** **Rows the reader isn't sure of are flagged, never guessed silently.** Examples are a description that wraps onto the next line, a line with no date, or an amount that could belong to either column. These rows appear in the preview as "couldn't verify", alongside rows that fail reconciliation, and the user must review each one before committing (IMP-02).
- **D-24:** **A PDF with no balances asks for one.** The user enters the statement's closing (or opening) balance. If the rows then reconcile, no row-by-row review is needed. If the user skips this, every row is treated as unverified and a single explicit confirmation, "I've checked these N rows", commits them. This is how IMP-02 is met for statements without balances.
- **D-25:** **Card lines with a foreign-currency purchase use the billed amount** in the account's currency. The original foreign amount and currency are kept as provenance (Phase 2 D-45) and do not drive FX stamping.
- **D-26:** **There is no "banks known to work" list in the app.** Users just try a file, and unreadable ones get the D-20 message.
- **D-27:** **A line date with no year takes it from the statement period.** A statement running from December into January assigns the year by position. If there is no period and the year is ambiguous, the user is asked as part of the format read-back (Phase 2 D-42).

### Scans, OCR and AI
- **D-28:** **OCR is not in Phase 2.1.** A PDF with no text layer is detected and explained. Example: "This looks like a scanned statement. Download it from online banking as a PDF, CSV or OFX file instead." Nothing is committed.
- **D-29:** **There is no AI reader in Phase 2.1.** This fits Phase 2 D-14 (no LLM). It avoids a new sub-processor, a new DPA, new privacy disclosure, and the risk of rows that look right but were invented. It can be revisited once the D-14 layout fingerprints show how many layouts go unread.

### Claude's Discretion
- **The on-device / Edge Function / worker choice (D-01)**, within D-02 to D-04. It is settled by testing in research against the D-19 fixtures.
- The reading technique: text-layer extraction, table detection, and how rows are recognised.
- The shape of the upload and read API, Storage bucket naming and policies, and how the purge job is scheduled, within D-10, D-12 and D-13.
- The exact size limit, if research shows the D-07 figures don't fit real statements.
- How bank templates are expressed (code or data), and whether they can be updated without an app release.
- Exact copy, drafted in the declarative voice and marked draft in `copyStatus.ts` like other Claude-written copy.

</decisions>

- `engine/` purity, enforced by dependency-cruiser. If reading happens on the phone, the PDF-to-`StatementDraft` conversion should be a pure `engine/` module where possible. Any native or WASM PDF library stays outside `engine/` and passes it plain text or table cells.
- Property-based and fixture tests for parsers (Phase 2 D-17), and the 100% coverage bucket for financial-correctness modules in `jest.config.js`.
- Additive migrations only (Phase 1 D-26/D-27). A Storage bucket or purge job arrives as a new migration.
- All copy uses i18n keys, and Claude-written copy is marked draft.

- The import screens (02-27): the upload notice (D-05), password prompt (D-21), offline message (D-06), unreadable and scanned messages (D-20, D-28), closing-balance prompt (D-24), and the "couldn't verify" row state (D-23).

<specifics>
## Specific Ideas

- The upload notice is one line, not a sheet or a setting, and appears on every PDF import (D-05).
- The target experience: a PDF imports exactly like a CSV or OFX file, down to the same read-back sentence ("We read this as a credit card statement…"), with a PDF-specific step only where needed (notice, password, closing balance).
- Keep Phase 2's promise wherever possible. If on-device reading clears the D-03 bar, the whole product can still say "statement files never leave your phone."

</specifics>

<deferred>
## Deferred Ideas

- **OCR for scanned or photographed statements**: a later phase. It would need a reconciliation gate and probably server-side OCR (D-28).
- **Opt-in AI reader for unrecognised layouts**: a later phase, informed by the D-14 failure fingerprints. It needs a DPA, a zero-retention agreement and a privacy disclosure, and may never supply confirmed figures (D-29).
- **Keeping a copy of the original statement** (an opt-in "keep" with a list and delete): a later phase. Phase 10 account deletion would then have to purge it (D-11).
- **Opt-in "send this statement" so a bank can be added**: needs its own consent, retention and handling rules (D-14).
- **Splitting a multi-account PDF across several accounts in one import** (D-22).
- **Share-sheet "Open in FincWin"** for PDFs from Mail or banking apps (D-08).
- **Queueing PDF reads while offline** (D-06).
- **Free vs Pro gating of PDF import**: Phase 9, which should weigh server cost if reading is server-side (D-09).

</deferred>
