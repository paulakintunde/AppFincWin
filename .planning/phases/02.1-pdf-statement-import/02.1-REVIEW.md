# Phase 02.1: Code Review Report

**Reviewed:** 2026-10-11
**Depth:** deep (cross-file: migrations ↔ apply_patches/undo ↔ client write keys; engine ↔ hook exponent lookup; edge function ↔ client contract)
**Branch:** feat/02.1-pdf-import vs origin/main
**Status:** issues_found

## Summary

The security work holds up. I traced the storage RLS, edge function auth, password handling, SECURITY DEFINER/search_path, grants, the generated column and its interaction with `clear_sample_on_edit`/`stamp_fx_rate`/`apply_patches`/`undo_replay`, and the finalize retry/undo paths for held fee lines. I found no exploitable path in those areas. Points verified:

- Uploads can only be inserted into the caller's own folder, one level deep, and clients have no select/update/delete policy. `read-pdf-statement` checks that the path's folder equals the JWT user id before the service role touches anything. A foreign path gets `not-found`, with no download and no delete. The upload is removed in `finally` on every outcome the function owns.
- The password is validated (1..256), passed only to `openPdf` and never logged. `buildLogLine` builds its output from an allow-list. The client never puts the password in state, a ref or analytics.
- `stale_statement_uploads` is `security definer`, `search_path=''`, and only `service_role` can execute it. The purge secret lives in Vault, has its own header and is compared in constant time.
- The generated column only references `rate_source`, a plain column. `clear_sample_on_edit` now excludes `conversion_source`. `apply_patches` cannot name `stmt_orig_*`, `fx_fee_of` or `conversion_source`, so undo ops never try to write them. `transactions_active` was re-created with the new columns appended and its grants re-issued. Column insert grants are scoped correctly, and there are no update grants. `insertTransactionsBatch` uses `ignoreDuplicates` (ON CONFLICT DO NOTHING), so the new insert-only columns do not need an UPDATE grant. Migrations 20261011000100..300 sort after 20261010000600, and no conflicting migration exists on main.
- Finalize: a lost response after `apply_patches` succeeded replays as `already-applied`, and held fees are re-inserted idempotently. A set-aside mark-paid re-points its fees to the fallback line. `n` counts each fee once.

The defects are in the **statement-reading correctness** layer, the area CLAUDE.md treats as harm-bearing. Two HIGH issues produce wrong stored data with no warning to the user:
1. Any three-letter word on a PDF continuation line ("REF 123456") is stored as a foreign original amount, because the app's `exponentFor` never returns null.
2. Any dated transaction whose text contains a balance phrase, for example a purchase at **NEW BALANCE**, is silently dropped and its figure is taken as the statement's closing balance.

The unit tests miss both. Every test stubs `exponentFor` with a 3-code allow-list, and no test has a dated row containing a summary phrase.

## High

### HI-01: Foreign-amount parsing accepts any 3-letter token as a currency, so garbage provenance is stored permanently

**Files:**
- `src/features/record/import/useStatementImport.ts:254-260` (`exponentFor`)
- `src/engine/statement/foreign.ts:59-74, 76-92` (`CODE_FIRST_RE` / `CODE_LAST_RE` / `readAmount`)
- `src/engine/statement/pdf/toDraft.ts:159-165` (`foreignOf`)
- `src/engine/money/currencyExponents.ts:45-47`

**Issue:** `exponentFor` wraps `resolveExponent(code)` in a try/catch and claims that an unknown code returns null. Without `customDecimals`, though, `resolveExponent` simply returns `currencyExponent(code)`, which is `ISO_EXPONENT_EXCEPTIONS[code] ?? 2`. It never throws. The catch branch is dead and every string gets exponent 2.

`parseForeignNote` relies on `exponentFor(code) === null` as its only check that a currency is real. It runs on every PDF continuation line (`descriptionParts.slice(1)`), and its regexes match any `[A-Za-z]{3}` followed or preceded by a number.

**Failure scenario:** a UK statement row has the wrapped line `REF 123456789`. It becomes `foreign = { magnitude: 12345678900, currency: 'REF' }`. Other lines such as `TEL 0800123`, `ATM 0042` or `12 PCS` behave the same way. `toImportCommit` writes `stmt_orig_amount=-12345678900, stmt_orig_currency='REF'`, which passes the DB check (`^[A-Z0-9]{2,4}$`, abs ≤ 1e13).

The row now shows `REF 123,456,789.00` under its amount in Activity. The detail sheet prints "charged £12.40 at 0" as the bank's conversion. Because the column is insert-only, nothing corrects it except editing the amount.

The same false positive affects OFX `CURSYM` and the CSV "Original currency" column (only the `^[A-Z]{3}$` shape is checked). It also defeats Phase 2's existing `unknown-currency` row issue for CSV and OFX.

The tests miss it because they all stub `exponentFor` with a short allow-list:
- `foreign.test.ts:14`
- `fixtures.test.ts:33`
- `importPipeline.pdf.test.ts:22`

**Fix:** make the app's lookup reject codes it does not know, and tighten the DB check to match.
```ts
// useStatementImport.ts
import { isoCurrency } from '@/engine/money/isoCurrencies';
function exponentFor(code: string): number | null {
  const iso = isoCurrency(code);
  if (iso !== undefined) return iso.exponent;
  const custom = customCurrencyFor(code); // the user's own custom currencies, if supported for import
  return custom ? custom.decimals : null;
}
```
```sql
-- follow-up migration
alter table public.transactions drop constraint if exists transactions_stmt_orig_currency_check;
alter table public.transactions add constraint transactions_stmt_orig_currency_iso
  check (stmt_orig_currency is null or stmt_orig_currency ~ '^[A-Z]{3}$');
```
Add an engine test that runs `parseForeignNote('REF 123456', …)` against the real ISO lookup and expects null. Also add a hook-level test that uses the production `exponentFor`.

### HI-02: Dated transaction rows containing a balance/limit phrase are silently dropped and become the stated balance

**File:** `src/engine/statement/pdf/rows.ts:324-349` (`classify`), called for every line at `rows.ts:426` and `:455`

**Issue:** `classify` checks `hasAny(up, OPENING_PHRASES)`, `hasAny(up, CLOSING_PHRASES)`, `up.includes('CREDIT LIMIT')` and `up.includes('AVAILABLE CREDIT')` with a substring match on the whole line. It does this before deciding whether the line is a transaction. Only the bank and card hints are gated on `undated`.

**Failure scenario:** the line `14 Sep  NEW BALANCE LONDON  89.99  1,203.11` (New Balance is a common retailer) matches `CLOSING_PHRASES`, so the function returns `true`:
- The purchase never becomes a row, so the transaction is lost with no issue flag. The only `summary-lines-removed` warning is set by the REMOVED_PHRASES branch, not this one.
- `s.closingText` is overwritten with that line's last numeric cell, the running balance 1,203.11. Last write wins, so if the real "New balance" summary appeared earlier (summary box at the top of the statement), the stated closing is now wrong.

The import can then reconcile against the wrong closing figure. A similar line such as `BALANCE BROUGHT FORWARD LTD` would also overwrite `openingText` if it came first.

The tests only cover undated label lines (`rows.test.ts:151,162`, `toDraft.test.ts:328`).

**Fix:** treat a line as a statement figure only when it has no date cell and the phrase starts the first text cell. Otherwise let it fall through to row assembly.
```ts
function classify(line: PdfLine, s: TableSummary): boolean {
  ...
  const undated = !hasDate(line);
  const label = line.cells.find((c) => !looksNumeric(c.text))?.text ?? '';
  const labelStarts = (phrases: readonly string[]) => startsWithPhrase(label, phrases) || hasAny(label.toUpperCase(), phrases) && label.length <= 40;
  if (undated && labelStarts(OPENING_PHRASES)) { s.openingText = s.openingText ?? lastNumeric(line); return true; }
  if (undated && labelStarts(CLOSING_PHRASES)) { s.closingText = lastNumeric(line) ?? s.closingText; return true; }
  if (undated && up.includes('CREDIT LIMIT')) { ... }
  ...
}
```
Also apply `undated` to the REMOVED_PHRASES branch. Dotted numeric dates (`12.09.2026`) pass `looksNumeric`, so on a dated row the "first non-numeric cell" is the description. A row like `12.09.2026 TOTAL GAS & POWER 54.00` is currently removed. Add tests for a dated "NEW BALANCE" purchase and a dotted-date "TOTAL …" merchant.

## Medium

### ME-01: `stmt_orig_currency` is not checked against known currencies, so one bad row crashes Activity for the whole household

**Files:**
- `supabase/migrations/20261011000300_statement_conversions.sql:17`
- `src/features/record/activity/ActivityRow.tsx:145-148`
- `src/features/record/activity/TransactionDetailSheet.tsx:104-106`

**Issue:** `original_currency` is guarded by `guard_transaction_currency` (`is_known_currency`). The new `stmt_orig_currency` only gets a shape check, `^[A-Z0-9]{2,4}$`, and any household member can insert it directly through the column grant. `formatAmount` passes the code to `Intl.NumberFormat({ style: 'currency', currency })`, which throws `RangeError: Invalid currency code` for 2-character or 4-character codes, including digit codes like `AB` or `XY12`.

**Failure scenario:** a buggy or modified client inserts a row with `stmt_orig_currency = 'AB'`. Every household member's Activity list throws during render of that row: `ActivityRow` calls `formatMoney` unconditionally once `stmt_orig_*` is non-null. The transaction sheet crashes the same way. The column is insert-only, so the row cannot be repaired from the app.

**Fix:** in the DB, use `check (stmt_orig_currency ~ '^[A-Z]{3}$')`, plus a trigger branch that calls `public.is_known_currency(new.stmt_orig_currency, …)` on insert. In the UI, render statement figures defensively:
```ts
const stmtText = (() => {
  if (isTransfer || row.stmt_orig_amount == null || row.stmt_orig_currency == null) return null;
  try { return formatter.formatMoney(money(Math.abs(row.stmt_orig_amount), row.stmt_orig_currency)); } catch { return null; }
})();
```

### ME-02: Numbers on a continuation line fill the previous row's empty debit/credit/balance slots

**File:** `src/engine/statement/pdf/rows.ts:441-447` (header mode)

**Issue:** for an undated line with no money placement, the text is appended to the previous row and **every numeric cell** goes through `applyNumeric(prev, …)`. Placement chooses the nearest numeric anchor however far away it is, so a figure sitting in the description column still lands in some numeric column. Statements commonly print foreign notes or FX rates on the wrapped line, for example `USD 45.00` split into two runs, or `Rate 1.2719`.

**Failure scenarios:**
- A foreign refund has its amount in the `credit` column. The continuation figure `45.00` is placed in `debit`, which sets `both-columns`. `bothColumnsAmount` then nets `credit - debit` and stores a wrong amount. It is only marked `pdf-ambiguous-column`, which does not block.
- A row with no running balance printed (balance only at end of day) gets the continuation figure as `balanceText`. The reconciliation link then breaks for that row and the next.

**Fix:** a continuation line may complete a row that has no amount yet. It should never add a second amount column or a balance:
```ts
numeric.forEach((c) => {
  if (prev.amountColumn !== null) return;      // already has its amount
  const p = placeCell(c, active);
  if (p.kind === 'column' && p.role === 'balance') return;
  applyNumeric(prev, c, active);
});
```
Also join the text and numeric cells of a continuation line before running `parseForeignNote`, so split `USD` / `45.00` runs are still recognised.

### ME-03: OFX `<CURRENCY>` with an unparseable `CURRATE` silently imports the foreign amount as the account amount

**File:** `src/engine/ofx/parse.ts:151-171`

**Issue:** with a `CURRENCY` aggregate, `TRNAMT` is in `CURSYM`. If `foreignFromOfx` returns null (missing, zero or malformed `CURRATE`; empty `CURSYM`; or overflow), `magnitude` keeps the foreign figure. The row is then imported in the account currency with no issue attached, so the amount is wrong by the exchange rate.

**Failure scenario:** a card OFX line has `<CURRENCY><CURRATE>N/A<CURSYM>USD`. $45.00 is stored as £45.00, with no flag in review.

**Fix:** when `cur !== null && orig === null && found === null`, push a blocking issue (`'unknown-currency'`, or a new `'bad-amount'`) so the row cannot be committed silently.
```ts
if (found !== null) { ... } else if (orig === null) issues.push('bad-amount');
```

### ME-04: Rollout ordering. The client selects the new columns, so an app or OTA build that ships before the migration breaks all transaction reads

**Files:** `src/db/transactions.ts:86` (`TRANSACTION_COLUMNS`), `supabase/migrations/20261011000300_statement_conversions.sql`

**Issue:** `TRANSACTION_COLUMNS` now names `stmt_orig_amount, stmt_orig_currency, conversion_source, fx_fee_of`. PostgREST returns 400 for an unknown column. Every month read, search and transfer-leg read fails until 20261011000300 is applied. The cron job in 20261011000200 also needs the Vault secrets `statement_purge_url` and `statement_purge_secret`, and the function env needs `STATEMENT_PURGE_SECRET` set to the same value. Without them the job fails every hour.

**Fix:** document and enforce this order:
1. `npm run supabase:db:push`, which includes the preflight.
2. `supabase secrets set STATEMENT_PURGE_SECRET=…` and the Vault inserts.
3. Deploy both functions.
4. Only then publish the EAS update or build.

Consider bumping the persisted query-cache `buster` in the same release.

## Low

### LO-01: pdf.js console output bypasses the D-15 log allow-list

**File:** `supabase/functions/read-pdf-statement/unpdf.ts:10-15`

**Issue:** pdf.js logs its own warnings and errors through `console.log`/`console.error` at its default verbosity, which is WARNINGS. This bypasses `buildLogLine`. The messages are mostly parser diagnostics, but they are uncontrolled output derived from an uploaded file, which D-15 rules out.

**Fix:** add `verbosity: 0` to the `getDocumentProxy` options, and assert it in `unpdf_integration_test.ts`.

### LO-02: No in-function time budget, and a worker kill skips `finally`, which contradicts "deleted straight after"

**Files:** `supabase/functions/read-pdf-statement/read.ts:100-166`, `src/i18n/locales/en.ts` (`pdf.consent`)

**Issue:** if a hostile or very complex 25-page PDF exceeds the Edge runtime's CPU or wall-clock limit, the isolate is killed. `finally` never runs, so the file survives until the hourly purge (up to about 2 hours). The client sees a generic `FunctionsHttpError` and shows "unreadable".

**Fix:** run the parse inside `Promise.race` with a budget (for example 20 s), and remove the file before returning `unreadable`. Alternatively, soften the copy to "deleted after reading, and always within two hours".

### LO-03: Any line containing "PERIOD" latches `periodLine`, even when it holds no dates

**File:** `src/engine/statement/pdf/rows.ts:327`

**Issue:** `s.periodLine === null && (up.includes('PERIOD') || …)`. Consider a heading "Statement period" on its own line, followed by "1 Sep 2026 to 30 Sep 2026" on the next line. The heading is captured first, `parsePeriod` returns null, and the real period line is never looked at. The year then falls back to the D-27 question, or row years come out wrong when one row carries an explicit year.

**Fix:** latch only when `parsePeriod(text, …) !== null`. Otherwise keep scanning.

### LO-04: Undoing an amount or currency edit cannot restore the statement figures

**Files:** `supabase/migrations/20261011000300_statement_conversions.sql:48-67`, `20261010000200_record_polish_patches.sql` (allowlist)

**Issue:** an edit clears `stmt_orig_*` through the trigger. Undo restores `original_amount` through `apply_patches`, which cannot write `stmt_orig_*`. So the Undo toast says the edit was undone, but the bank conversion and the linked fee display (gated on `conversion_source='statement'`) are gone for good.

**Fix:** either accept this and document it (D-34), or have `undo_replay` restore the figures from the step. The second option needs a server-only key gate like `materialised_through`.

### LO-05: A fee held for a kept mark-paid points at a line that can never show it

**Files:** `src/features/record/import/importPipeline.ts:747-762`, `src/data/queries/transactions.ts:19-25`

**Issue:** the held fee gets `fx_fee_of = pendingId`. The pending line is patched only through `status`, `local_date` and `original_amount`, so it never gets statement figures. `useLinkedFees` only runs when `conversion_source === 'statement'`, so the link is never surfaced.

**Fix:** either enable `useLinkedFees` for any row (fee lookup by `fx_fee_of`), or note in D-36 that fee links on mark-paid lines are stored only.

### LO-06: PDF uncertainty codes are not explained in Review

**File:** `src/features/record/import/ReviewStep.tsx` (ISSUE_KEY map)

**Issue:** the `pdf-*` issues map to `undefined` and render nothing. The row reads "cannot verify" and the user must tick "I've checked these rows" without being told what to check: a wrapped description, an ambiguous column or an assumed date.

**Fix:** add i18n keys for the four `pdf-*` codes and map them here.

## Info

`resolveExponent` does not throw for unknown codes (see HI-01), so this branch and its copy are dead. Use the ISO lookup from HI-01.

### IN-02: `clear_stmt_conversion_on_edit` does not need `security definer`

**File:** `supabase/migrations/20261011000300_statement_conversions.sql:48-53`

The trigger only assigns to `NEW`, which needs no privileges. Dropping `security definer` reduces surface. Execute is already revoked, so this is not exploitable.

### IN-03: The bucket insert policy allows names the function will never read

**File:** `supabase/migrations/20261011000100_statement_uploads_bucket.sql:11-18`

Any `<uid>/<anything>.pdf` up to 10 MB is accepted, and there is no per-user quota. Only `<uuid>.pdf` is ever read or deleted on demand. Others sit until the purge, which is a small free-storage abuse window. Add `and name ~ '^[0-9a-f-]{36}/[0-9a-f-]{36}\.pdf$'` to the `with check`.

### IN-04: OFX `<CURRENCY>` rows store the foreign `TRNAMT` text as `raw_amount`, while `original_amount` holds the charged figure

**File:** `src/engine/ofx/parse.ts:166-170`

The provenance string and the stored amount disagree. Either use the charged figure for `raw_amount`, or prefix it (`USD 45.00`) so audit reads are unambiguous.
