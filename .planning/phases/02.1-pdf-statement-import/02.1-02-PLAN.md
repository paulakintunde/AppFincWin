<objective>
Stand up the server-side storage for PDF statements: a private bucket whose only client permission is "upload into your own folder", and the D-12 backstop that removes any upload the normal delete-after-read missed.

Purpose: IMP-03's "the uploaded file is deleted" guarantee has two halves — the synchronous delete in the reading function (plan 02.1-03) and this purge. Correction to 02.1-PATTERNS.md: the purge cannot be pure SQL. Supabase's docs state that deleting from `storage.objects` by SQL leaves the file orphaned in the bucket, so the job selects stale names in SQL and deletes them through the Storage API from an Edge Function, invoked by pg_cron exactly like fx-monitor-daily.
Output: two migrations, one pgTAP file, the purge-statement-uploads Edge Function, a config.toml entry.

This plan is Phase-2-independent: it touches no Phase 2 file. Migrations are additive (Phase 1 D-26/D-27).
</objective>

Create `supabase/migrations/20260927000100_statement_uploads_bucket.sql` (header comment: D-04 same project/region, D-07 10 MB, D-10/D-13 only the service role reads or deletes; there is deliberately NO select/update/delete policy):
```sql
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('statement-uploads', 'statement-uploads', false, 10485760, array['application/pdf'])
on conflict (id) do update
  set public = false, file_size_limit = excluded.file_size_limit, allowed_mime_types = excluded.allowed_mime_types;

create policy "statement uploads: owner inserts own folder"
  on storage.objects for insert to authenticated
  with check (
    bucket_id = 'statement-uploads'
    and (storage.foldername(name))[1] = (select auth.uid())::text
    and array_length(storage.foldername(name), 1) = 1
    and storage.extension(name) = 'pdf'
  );
```
Create `supabase/migrations/20260927000200_statement_uploads_purge.sql` (header: D-12 backstop; purge threshold 1 hour on an hourly schedule, so a stray file lives under 2 hours — stricter than D-12's 24-hour ceiling, and no legitimate file outlives its read call, which deletes it in the same request; deletion itself happens in the purge-statement-uploads Edge Function through the Storage API because a SQL DELETE on storage.objects orphans the file):
```sql
create or replace function public.stale_statement_uploads(p_older_than interval default interval '1 hour', p_limit integer default 100)
returns setof text
language sql
stable
security definer
set search_path = ''
as $$
  select o.name from storage.objects o
   where o.bucket_id = 'statement-uploads' and o.created_at < now() - p_older_than
   order by o.created_at
   limit least(greatest(p_limit, 1), 1000)
$$;
revoke execute on function public.stale_statement_uploads(interval, integer) from public, anon, authenticated;
grant execute on function public.stale_statement_uploads(interval, integer) to service_role;

select cron.schedule(
  'statement-uploads-purge-hourly',
  '17 * * * *',
  $$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name = 'statement_purge_url'),
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'x-statement-purge-secret', (select decrypted_secret from vault.decrypted_secrets where name = 'statement_purge_secret')),
    body := '{}'::jsonb,
    timeout_milliseconds := 30000
  );
  $$
);
```
(Vault rows are created at deploy time by plan 02.1-12, never in git; locally the job finds null secrets and fails harmlessly, as fx-monitor-daily does.)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app (authenticated user) -> Storage | Client uploads untrusted bytes into the bucket |
| pg_cron -> purge Edge Function | Shared-secret HTTP call inside the project |
| Edge Function -> logs | Anything logged is visible in the Supabase dashboard |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02.1-02-01 | Information Disclosure | statement-uploads bucket | mitigate | Private bucket; no select/update/delete policy for any client role; pgTAP proves a user cannot see even their own upload |
| T-02.1-02-02 | Elevation of Privilege / Tampering | upload path | mitigate | INSERT policy pins the first path segment to auth.uid(), one level only, .pdf only; pgTAP covers other-user, nested and non-pdf paths |
| T-02.1-02-03 | Information Disclosure (retention) | abandoned uploads | mitigate | Hourly purge of anything older than 1 hour via Storage API (D-12); SQL delete forbidden by grep gate because it orphans files |
| T-02.1-02-04 | Spoofing | purge endpoint | mitigate | Own shared secret, constant-time compare, verify_jwt=false only because pg_cron is the caller; 403 otherwise |
| T-02.1-02-05 | Information Disclosure | purge logs | mitigate | Count-only log lines; no object names (names embed user ids); test asserts |
| T-02.1-02-06 | Denial of Service | oversized uploads | mitigate | Bucket file_size_limit 10,485,760 and allowed_mime_types application/pdf enforced by Storage (D-07); bounded purge batches |
| T-02.1-02-07 | Elevation of Privilege | stale_statement_uploads() | mitigate | security definer, search_path '', execute revoked from public/anon/authenticated, service_role only; pgTAP 42501 |
