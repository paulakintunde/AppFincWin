## User Constraints (from CONTEXT.md)

### Locked Decisions

**Where the PDF is read**
- **D-01:** Research decides where the PDF is read. The candidates are on the phone, a Supabase Edge Function, or a separate worker service. Research must test each candidate against real statements, not only reason about it.
- **D-02:** Tie-break: the phone wins if it is good enough. Keeping "your statement never leaves your phone" (Phase 2 D-17) is worth some reading quality. A server is used only if on-device reading cannot meet the D-03 bar.
- **D-03:** "Good enough" means: a typical statement of up to about 10 pages reads with its balances reconciling, in under about 10 seconds on the iPhone XR, without running out of memory. A server option has to clear the same outcome bar.
- **D-04:** If the file is uploaded, it is processed only in the existing Supabase project's region (us-west-2), under the same DPA as all other user data. There is no second region, and the region is named in the privacy copy. A separate worker service can win only if Supabase cannot do the job, and it then brings a new sub-processor and DPA. Research must call that cost out explicitly.
- **D-05:** Upload consent is a one-line notice on every PDF import, shown before the file is sent. Example: "To read a PDF we send it to our server in the United States. It's deleted straight after." Continue proceeds. There is no settings toggle and no remembered consent. If reading happens on the phone, this notice does not appear.
- **D-06:** If server reading is needed and the phone is offline, the app says so and queues nothing. Example: "PDF statements need a connection to read. Try again when you're online." CSV and OFX still import offline, as in Phase 2.
- **D-07:** Size limit is about 25 pages or 10 MB. Larger files get a clear "split the file" message, in the same way as Phase 2's 5,000-row limit (D-18). Research may adjust the figures if real statements need it, but a limit must exist.
- **D-08:** The PDF comes in through the file picker only. It uses the same "Choose file" entry as CSV and OFX (`expo-document-picker`, installed by Phase 2), and the format is sniffed from the file's content (Phase 2 `sniffFormat`).
- **D-09:** PDF import is built for all users, with no gating. Tiering belongs to Phase 9, which should weigh the server cost if reading turns out to be server-side.

**File retention and privacy**
- **D-10:** An uploaded PDF is deleted as soon as its rows are extracted, before the user commits. The preview, a flipped format reading (Phase 2 D-42) and the commit all work from the extracted draft, never from the file.
- **D-11:** There is no "keep a copy" option in Phase 2.1. The original file is never retained. Phase 2 D-45 already keeps each row's raw values for tracing. IMP-03's "a kept file is removed on account deletion" clause therefore has nothing to act on in this phase. Record that explicitly so Phase 10's account deletion knows there is no statement store to purge.
- **D-12:** Abandoned uploads are purged within 24 hours. A scheduled job (pg_cron, as the FX jobs already use) deletes any statement file older than 24 hours, whatever its state. It is a backstop for when the normal delete in D-10 fails, such as a crash or a closed app.
- **D-13:** The server keeps nothing from a statement. Extracted rows go back to the phone in the response and are never written server-side. The only stored data is what the user commits, through Phase 2's normal transaction path, with RLS and FX stamping unchanged.
- **D-14:** When a statement can't be read, only an anonymous layout fingerprint may be kept. That means: the bank name if detected, page count, column headers, and which step failed. It must never include amounts, names, dates, descriptions or account numbers. Its purpose is to decide which bank templates to add (D-18).
- **D-15:** Server logs and Sentry get metadata only: outcome, duration, page count, file size, layout id and error class. Never text, amounts, names, file names or account numbers. It is enforced by a scrubber, alongside the existing `src/services/errors/scrub.ts`, plus an automated test that runs a sample statement through reading and asserts nothing from it appears in logs or error events (IMP-03).
- **D-16:** The phone's temporary copy is deleted too. The picker's cached copy of the PDF is removed once the import is committed or cancelled, so the statement isn't left in the app's storage.
- **D-17:** Privacy copy states where the file is read and how long it is kept (IMP-04). In the import screen and in the privacy policy. If reading is server-side, example wording: "PDF statements are read on our server in the United States and deleted straight after. CSV and OFX files never leave your phone." If research picks on-device reading, the copy says the PDF never leaves the phone. The voice stays declarative, with no "we recommend" (PROJECT.md compliance rules).

**Layouts and files that can't be read**
- **D-18:** One generic reader, with bank templates added only where needed. A generic reader for tables and text in any text PDF is gated by Phase 2's reconciliation (D-46). A template for a specific bank is added only when real users upload that bank and the generic reader gets it wrong. This fits Phase 2 D-11 (no presets up front).
- **D-19:** Research chooses the test banks and statements from the sample statements it can find, with personal details removed. Neither the user nor this discussion named particular banks. The fixture set should cover at least one current account, one savings account and one credit card, statements with and without a running balance, and one statement that spans the new year.
- **D-20:** An unreadable PDF gets a plain reason and a pointer to CSV/OFX. Example: "We couldn't read this statement's layout. Most banks also let you download CSV or OFX from online banking, and those import reliably." Nothing is committed, and the file is deleted under D-10 and D-12.
- **D-21:** Password-protected PDFs are supported. The app asks for the password and uses it only to open this one file. The password is never stored or logged. If reading is server-side, it travels with the upload over TLS and is discarded after reading.
- **D-22:** One account per import, as in Phase 2 D-12. If a PDF covers several accounts (for example chequing and savings), the user picks which section to import and runs the import again for the others.
- **D-23:** Rows the reader isn't sure of are flagged, never guessed silently. Examples are a description that wraps onto the next line, a line with no date, or an amount that could belong to either column. These rows appear in the preview as "couldn't verify", alongside rows that fail reconciliation, and the user must review each one before committing (IMP-02).
- **D-24:** A PDF with no balances asks for one. The user enters the statement's closing (or opening) balance. If the rows then reconcile, no row-by-row review is needed. If the user skips this, every row is treated as unverified and a single explicit confirmation, "I've checked these N rows", commits them. This is how IMP-02 is met for statements without balances.
- **D-25:** Card lines with a foreign-currency purchase use the billed amount in the account's currency. The original foreign amount and currency are kept as provenance (Phase 2 D-45) and do not drive FX stamping.
- **D-26:** There is no "banks known to work" list in the app. Users just try a file, and unreadable ones get the D-20 message.
- **D-27:** A line date with no year takes it from the statement period. A statement running from December into January assigns the year by position. If there is no period and the year is ambiguous, the user is asked as part of the format read-back (Phase 2 D-42).

**Scans, OCR and AI**
- **D-28:** OCR is not in Phase 2.1. A PDF with no text layer is detected and explained. Example: "This looks like a scanned statement. Download it from online banking as a PDF, CSV or OFX file instead." Nothing is committed.
- **D-29:** There is no AI reader in Phase 2.1. This fits Phase 2 D-14 (no LLM). It avoids a new sub-processor, a new DPA, new privacy disclosure, and the risk of rows that look right but were invented. It can be revisited once the D-14 layout fingerprints show how many layouts go unread.

## Summary

**D-01 is decided: a Supabase Edge Function running `unpdf` (a serverless-safe wrapper around Mozilla's pdf.js) is the recommended read location, not on-device and not a separate worker.** This was tested with real code in this session, not just reasoned about: two real bank-statement-shaped PDFs (a CFPB public-domain sample credit-card statement, and a real community bank's own published specimen current-account statement with a running-balance table) were downloaded and run through `unpdf@1.8.1` under Node. Both extracted correctly and fast — a 6-page statement extracted in well under a second per run (after a one-time cold-start cost), using a package footprint of 2.4 MB (well inside Supabase's function bundle limits) — and, critically, **the position data pdf.js exposes for every text run (`item.transform` → x/y) was verified to reliably reconstruct the Date/Description/Debits/Credits/Balance table columns** by matching each row's numbers to the nearest header x-coordinate, which is exactly the generic-reader capability D-18/D-23 need.

On-device extraction was evaluated and rejected as the *default* build target, though not ruled out — it is a real, viable fallback that should get a cheap early spike (see Environment Availability and Open Questions), because D-02 says the phone wins only if it clears D-03, and D-03's bar (10 pages, <10s, no OOM, *on the iPhone XR specifically*) cannot be measured from this research session at all: there is no physical iPhone XR, Android device, or React Native/Hermes runtime available here. What *can* be established without a device is relative risk, and it is lopsided: (1) running pdf.js/`unpdf` itself inside Hermes is unproven and high-risk — it needs a disabled-worker fallback mode plus DOM shims (`DOMMatrix`, `Path2D`, sometimes `OffscreenCanvas`) that Expo does not ship, the same category of problem Phase 2's research already hit with `TextDecoder` being UTF-8-only under Hermes; (2) the only maintained native-module alternative, `expo-pdf-text-extract` (wraps PDFKit on iOS / PDFBox on Android), is a single-maintainer package first published 2026-08-13 with 13 GitHub stars, and its API returns **plain concatenated text only — no bounding boxes** — so on-device column reconstruction could not use the position-based technique verified above and would have to rely entirely on the balance-delta disambiguation technique documented below (which works, but has no positional fallback for the genuinely ambiguous rows). Given a Windows-only, no-Mac development environment, debugging a crash in that native module on a physical A12 device is materially harder than debugging a Deno TypeScript function. The safer, already-verified default is the Edge Function.

**The worker tier (D-04's "separate worker service") is not needed.** `unpdf` runs directly inside a Deno Edge Function via an `npm:` specifier — a pattern this repo already uses in production (`fx-sync` imports `npm:@supabase/supabase-js@2.116.0`) — so PDF reading stays inside the existing Supabase project and region with **no new sub-processor and no new DPA**. This directly answers D-04's "call that cost out explicitly": the cost is zero because the worker tier is unnecessary.

**Architecture:** the Edge Function is kept intentionally thin — it only turns PDF bytes into positioned text (page count, and per text-run `{ str, x, y, page }`), the same shape of raw material CSV/OFX adapters already start from. All statement-domain logic (column/sign inference, notation parsing, reconciliation, duplicates, transfers) stays exactly where Phase 2 already built it, in `src/engine/statement/*` — a new pure `src/engine/statement/pdf/toDraft.ts` module converts the Edge Function's `PdfExtractResult` into the existing `StatementDraft` shape, exactly mirroring `csvToDraft`/`parseOfx`. Nothing about `resolveProfile`, `buildPreview`, `reconcile`, `findDuplicates`, `matchTransfers` or `toImportCommit` (all Phase 2, plan 02-26/02-36) changes for PDF. This is what "PDF is one more format adapter" (D-40) means concretely.

**Primary recommendation:** Build `supabase/functions/read-pdf-statement/` (Deno, `npm:unpdf`) that accepts a Storage object path, reads the object with the service-role key, extracts positioned text page by page, deletes the object, and returns a slim JSON payload; convert that payload to a `StatementDraft` in a new pure `src/engine/statement/pdf/` module reusing Phase 2's existing pipeline unchanged from `resolveProfile` onward. Gate this behind a required Wave 0 spike that tries the on-device native-module path on the real iPhone XR first (cheap to attempt, decisive either way) — if it clears D-03, the plan should pivot; the research in this document is what to build if it does not, and is what should be scaffolded as the default so the phase is not blocked on unmeasurable hardware.

### Pattern 1: Keep the Edge Function dumb — extraction only, no statement semantics

**What:** `read-pdf-statement` never decides a sign, a column role, or a reconciliation result. It returns exactly: `{ pageCount, pages: { page: number; items: { str: string; x: number; y: number }[] }[], encrypted: boolean }`. Every domain decision (which column is Debits, what a positive number means, whether the balance checks) happens in `src/engine/statement/pdf/*` on the device, identically to how `csvToDraft` and `parseOfx` already work.

**When to use:** Any server-assisted extraction step where D-13 ("the server keeps nothing... extracted rows go back to the phone") applies.

**Verified example (real code run against the Carson Bank fixture in this session):**
```typescript
// Verified in this session with unpdf@1.8.1 against a real statement PDF.
// Header row gives exact column x-anchors:
//   Date x=44.1  Description x=94.5  Debits x=368.9  Credits x=452.2  Balance x=531.9
// A data row then reads:
//   y=198.1 x=44.1  "07/01/2019"
//   y=198.1 x=94.5  "Deposit = 131"
//   y=198.1 x=450.8 "$209.54"     <- nearest to Credits (452.2), not Debits (368.9)
//   y=198.1 x=537.2 "$654.82"     <- nearest to Balance (531.9)
// Column assignment = nearest header x-anchor to each item's x, grouped by shared y (±half a
// line-height tolerance, e.g. 13.1pt in this fixture) into one logical row.
```

### Pattern 2: Column ambiguity is resolved by the running-balance delta, not just position

**What:** Even without any position data at all (i.e., even if a future path only has plain concatenated text), a row that shows exactly one transaction amount plus a running balance can have its sign and "which column" resolved arithmetically: `signedAmount = currentBalance - previousBalance`. If `abs(signedAmount)` matches the row's amount token, the sign is derived from the balance's own direction of travel — no separate Debit/Credit column detection is required for the common case of "one transaction number + one balance number per row."

**Why this matters:** it is the fallback that makes the *on-device* path (plain-text-only, no bounding boxes) plausible at all for tables with parallel Debit/Credit columns, and it is a second, independent check even when position data *is* available (Edge Function path) — a row where the position-based column guess and the balance-delta sign disagree is exactly a D-23 "amount that could belong to either column" case and should be flagged, never guessed silently.

**Verified example (from the real Carson Bank fixture):**
```
Previous Balance: $445.28 (06/28/2019)
Row: 07/01/2019  "Deposit = 131"  amount token "$209.54"  balance token "$654.82"
delta = 654.82 - 445.28 = +209.54  -> matches the amount token exactly, sign = credit (money in)
```
This reproduces D-46/D-49's reconciliation logic to resolve a per-row sign, using only the arithmetic Phase 2 already implements in `reconcile.ts` — no PDF-specific sign logic needs writing from scratch. A row with *both* a debit and a credit value present (a same-line reversal) genuinely cannot be resolved this way and correctly becomes a D-23 "couldn't verify" row.

### Pattern 3: Multi-account section splitting (D-22) mirrors OFX's multi-statement picker

**What:** A PDF that covers more than one account is detected by scanning for section-header-shaped text (a line matching an account-kind keyword — "CHECKING", "SAVINGS", a card product name — followed by little else on that line, typically preceded by a page break or a large y-gap) and splitting the extracted pages into candidate `StatementDraft`s at those boundaries, exactly as `statementOptions(statements)` already does for a multi-statement OFX file (Phase 2 plan 02-26 Task 1). The user picks one, exactly as they do for OFX today; no new UI concept is introduced (per the UI-SPEC's "reuses the exact `importCsv.statementOption` pattern already used for multi-statement OFX files").

**When to use:** Whenever `pageCount > 1` and more than one section-header candidate is found.

### Pattern 4: Scanned-PDF and encrypted-PDF detection both come free from the same extraction call

**What:**
- **Scanned/no-text-layer (D-28):** `page.getTextContent()` returning zero or near-zero items across every page (verified structurally: a genuine text-layer PDF returns dozens of positioned items per page even for a single summary page, as seen with both fixtures tested) is the detection signal. No separate check is needed.
- **Encrypted (D-21):** pdf.js's `getDocument`/`getDocumentProxy` accepts a `password` option and throws a typed `PasswordException` with a stable `code` (`NEED_PASSWORD` on first attempt, `INCORRECT_PASSWORD` on a wrong retry) [CITED: usefulangle.com pdf.js password tutorial; mozilla/pdf.js PR #1695 introducing this exact flow — structurally confirmed present in `unpdf`'s bundled pdf.js build via `grep -c password` in this session, **not yet round-tripped against an actual encrypted PDF fixture in this session — flagged for the Wave 0 spike**].

### Anti-Patterns to Avoid
- **Letting the Edge Function decide signs or build the format profile.** That duplicates Phase 2's `inferProfile`/`convertDraft` logic server-side, doubles the surface that must stay correct, and works against D-13's "server keeps nothing" spirit (the less the server understands about statement content, the smaller the privacy/logging risk).
- **Using `pdf-parse` or `pdfjs-dist`'s default (browser/Node canvas) build in the Edge Function.** Both pull in a `canvas` native binding path that is reported broken on edge/serverless runtimes; `unpdf`'s serverless build exists specifically to avoid this.
- **Trying to run `unpdf`/pdf.js directly inside the React Native/Hermes bundle "to keep it on-device."** This was seriously considered and rejected for this phase's default: pdf.js's worker-disabled fallback mode plus its DOM-adjacent dependencies (`DOMMatrix`, `Path2D`, and in some code paths `OffscreenCanvas`) are not proven to work under Hermes, and Phase 2's own research already hit an analogous wall with `TextDecoder` being UTF-8-only under Expo's runtime. No verified production case of pdf.js running inside Hermes/RN was found.
- **Skipping the page-count pre-check before full extraction.** `pdf.numPages` is available immediately after `getDocumentProxy` resolves, before any per-page `getTextContent()` call — check it against the D-07 cap (25 pages) *before* looping every page, so a hostile or malformed 500-page PDF cannot burn the Edge Function's 2-second CPU budget before the cap is enforced.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PDF byte parsing (xref tables, object streams, content stream decoding) | A custom PDF tokenizer | `unpdf` (wraps Mozilla's pdf.js) | pdf.js is the de facto standard PDF parser in the JS ecosystem, security-hardened over a decade against a huge adversarial-input corpus; a hand-rolled parser would need to solve the same problem with none of that hardening, for a security-sensitive, untrusted-file-input feature |
| Column/table detection in a positioned-text page | A bespoke geometry clustering library | The header-anchor nearest-x technique (Pattern 1), verified against a real fixture in this session | The 60-line technique is already proven to work on real data; a general table-detection library (e.g. a JS port of Camelot/Tabula) would be materially heavier for a problem this constrained (bank statements have a small, regular set of column shapes) |
| Sign resolution for an ambiguous debit/credit column | A second, PDF-specific sign-inference engine | Phase 2's existing `reconcile.ts` arithmetic, applied per-row (Pattern 2) | The balance-delta technique *is* reconciliation math already built and tested for CSV/OFX; reusing it for per-row sign resolution avoids a parallel implementation that could disagree with the one enforcing IMP-02 |
| Password-protected PDF handling | A custom PDF decryption routine | pdf.js's built-in `password` option and `PasswordException` | PDF encryption (RC4/AES per the PDF spec) is exactly the kind of primitive that must never be hand-rolled; pdf.js already implements the full range of PDF encryption revisions correctly |
| Server-side error/log scrubbing for the Edge Function | Ad hoc `console.log` guards scattered through `index.ts` | A dedicated `scrub.ts` mirroring `src/services/errors/scrub.ts`'s pattern (pure, unit-tested, applied before every log line and before every thrown error reaches a response) | D-15 requires this be enforced and tested, not just remembered; the existing client-side scrubber is the direct, already-reviewed precedent to copy |

**Key insight:** this phase's engineering risk is concentrated entirely in the D-01 read-location choice and the column-reconstruction technique — both are now backed by real, executed evidence rather than assumption. Everything downstream of "we have a `StatementDraft`" is Phase 2's problem, already solved, and must not be re-solved for PDF.

## Common Pitfalls

### Pitfall 1: Assuming Supabase Edge Function CPU/memory limits are comfortable without a real-environment measurement
**What goes wrong:** A 25-page/10 MB PDF (the D-07 ceiling, deliberately the worst case) is parsed on a Deno isolate, not the Node process this session tested against; Deno's V8 startup/GC behaviour under Supabase's actual edge-runtime supervisor is not the same as a local Node script.
**Why it happens:** This session verified `unpdf` works correctly and is fast on a 1-page and a 6-page real statement *in Node*, and confirmed [MEDIUM confidence, WebSearch-derived, not independently re-fetched from a live Supabase docs page this session] that Edge Functions get roughly 256 MB memory, a 2-second CPU-time soft limit per request, and 150s (free)/400s (paid) wall-clock — but did not measure an actual 25-page PDF inside an actual deployed Edge Function.
**How to avoid:** Treat the exact page/size ceiling as provisional until a real deployment test runs a 25-page synthetic or real-shaped PDF through a deployed `read-pdf-statement` function and records actual CPU time reported by Supabase's own metrics. Enforce the page-count pre-check (Anti-Patterns, above) so a pathological file fails fast rather than burning the CPU budget.
**Warning signs:** Import silently times out or returns a 504/546 for large-but-plausible statements near the 10 MB/25-page boundary.

### Pitfall 2: Position-based column matching breaks on a PDF whose header row is missing, reordered, or spans two lines
**What goes wrong:** The header-anchor technique (Pattern 1) needs a header row with recognisable column-name text at stable x-positions; a statement that puts "Debit/Credit" as one merged header, or omits headers entirely (common on some card issuer PDFs), has no anchor to match against.
**Why it happens:** D-18 deliberately ships one generic reader with no bank-specific presets; real-world layout diversity is exactly what the fixture set (D-19) needs to cover before this phase ships.
**How to avoid:** Fall back to the balance-delta technique (Pattern 2) whenever no confident header match exists, and fall back further to "flag the ambiguous rows" (D-23) whenever neither technique resolves a row — never guess. Test against layouts with no visible header text as an explicit fixture case, not just the two verified in this session.
**Warning signs:** A statement with an unusual header format imports with every row flagged "couldn't verify" even though a human could read it easily — a signal to add a layout heuristic, not a bank-specific preset (D-18's boundary).

### Pitfall 3: A description that wraps onto a second line is mistaken for a new, dateless row
**What goes wrong:** In the verified Carson Bank fixture, `"C&J CLARK RETAIL ACH DEBIT SETTLEMENT STORE"` at y=158.8 is followed by `"NBR 131"` at y=149.5 with *only* an x=94.5 (Description column) item and no date, amount or balance on that line.
**Why it happens:** pdf.js emits one text item per line of wrapped text; a row-grouping-by-y algorithm that doesn't look ahead will treat the continuation line as its own (invalid) row.
**How to avoid:** A "row" with content in the Description column only, and nothing in Date/Amount/Balance, immediately following a row that itself has no balance/amount gap, should be merged upward into the previous row's description — this is precisely D-23's documented case ("a description that wraps onto the next line") and this session's fixture data proves it happens on real, ordinary statements, not just edge cases.
**Warning signs:** A row named "NBR 131" (or similar fragment) with no date and no amount appears in the preview as its own line.

### Pitfall 4: Treating any two-number row as unresolvable when it could be balance-delta-resolved
**What goes wrong:** Over-cautious flagging turns nearly every row into "couldn't verify" on a statement that actually has enough information (running balance + one amount) to resolve cleanly, defeating the point of D-24/D-46 (a file with balances shouldn't need row-by-row review).
**Why it happens:** It's tempting to flag any row with more than one numeric token as ambiguous by default.
**How to avoid:** Apply Pattern 2's balance-delta check *before* falling back to "flag it" — only flag when the delta doesn't cleanly match any candidate token (a genuine ambiguity, e.g. a same-line debit-and-credit reversal).
**Warning signs:** Every row of a statement with a perfectly good running balance column shows "couldn't verify" in the preview.

### Pitfall 5: Committing a real institution's branded specimen PDF verbatim into this (public) repository
**What goes wrong:** Several real, publicly-published "sample statement" PDFs were found during D-19 fixture research (e.g. a community bank's own specimen statement, a national bank's sample e-statement) that use obviously fictional customer data but carry the institution's real branding, logo and layout as a copyrighted document.
**Why it happens:** The fictional customer data (e.g. "JOHN TEST") makes the file *look* safe to redistribute, but the document's design/branding is still the institution's own copyrighted work, and this repository is public (per `STATE.md`'s "Public repo privacy" open item).
**How to avoid:** Use such PDFs only as local, uncommitted research/validation fixtures (as done in this session, in the scratchpad, never the repo). For committed test fixtures, either use a document that is verifiably public domain (a U.S. government work — see Runtime/Fixture section below) or generate synthetic statements locally with a small script whose output carries no real institution's branding.
**Warning signs:** A fixture file under `src/engine/statement/pdf/__tests__/fixtures/` (or similar) contains a real bank's logo, real bank name in a styled header, or was downloaded from a `.com` bank domain rather than authored by this project.

### Pitfall 6: A CSV/OFX file whose OFX-derived duplicate/transfer matching assumptions leak into PDF
**What goes wrong:** PDF statements have no `FITID`-equivalent exact key (Phase 2 D-47's OFX exact-duplicate path), so a PDF import that reuses OFX's duplicate-matching code path unmodified could either over-trust or under-trust matches.
**Why it happens:** D-40's "one pipeline" is correct at the architecture level, but `findDuplicates`'s `sourceFormat` parameter (Phase 2 plan 02-26/02-04) already exists specifically to vary matching strictness per format — PDF must pass `sourceFormat: 'pdf'` (or equivalent) through that existing parameter, not silently inherit CSV's or OFX's behaviour.
**How to avoid:** Confirm `findDuplicates`'s existing `sourceFormat` union type is extended to include a PDF variant (or reuses `'csv'`'s cross-format ±2-day rule, per D-54, since PDF has no `FITID`), rather than assuming no change is needed.
**Warning signs:** A PDF import's genuine duplicate rows aren't flagged, or legitimate same-day repeated transactions are wrongly suppressed.

### Pitfall 7: Shipping the on-device privacy copy before the D-01 outcome is confirmed on real hardware
**What goes wrong:** D-17 requires different copy depending on where reading happens; this research recommends the server path as the default, but the UI-SPEC (correctly) ships both copy variants pending the D-01 outcome.
**How to avoid:** Land the server-variant copy as the shipped default per this research; only switch to the on-device variant if the Wave 0 spike (Open Questions) succeeds and the plan is revised accordingly.

### 3. Edge Function extraction call (structurally verified: this is unpdf's real, documented API, exercised successfully in this session)
```typescript
// supabase/functions/read-pdf-statement/extract.ts
import { getDocumentProxy } from 'npm:unpdf@1.8.1';

export interface PdfExtractResult {
  pageCount: number;
  pages: { page: number; items: { str: string; x: number; y: number }[] }[];
  encrypted: boolean;
}

export async function extractPdf(bytes: Uint8Array, password?: string): Promise<PdfExtractResult> {
  let pdf;
  try {
    pdf = await getDocumentProxy(bytes, password ? { password } : {});
  } catch (err) {
    // pdf.js throws a PasswordException with a stable `.name`/`.code` on a missing or wrong
    // password [CITED, structurally verified via `unpdf`'s bundled pdf.js this session --
    // round-trip against a real encrypted fixture is a Wave 0 task, not yet done this session].
    if ((err as { name?: string }).name === 'PasswordException') {
      return { pageCount: 0, pages: [], encrypted: true };
    }
    throw err;
  }
  const pages: PdfExtractResult['pages'] = [];
  for (let i = 1; i <= pdf.numPages; i++) {
    if (i > 25) break; // D-07 page cap enforced before spending more CPU
    const page = await pdf.getPage(i);
    const content = await page.getTextContent();
    pages.push({
      page: i,
      items: content.items
        .filter((it): it is { str: string; transform: number[] } => 'str' in it && it.str.trim() !== '')
        .map((it) => ({ str: it.str, x: it.transform[4], y: it.transform[5] })),
    });
  }
  return { pageCount: pdf.numPages, pages, encrypted: false };
}
```

| V3 Session Management | No | Unchanged from the rest of the app |
| V4 Access Control | Yes | Storage bucket policy: the client can only `INSERT` via a short-lived signed upload URL scoped to its own `auth.uid()`-prefixed path, never `SELECT`/`UPDATE`/`DELETE`; only the Edge Function's `service_role` key can read or delete the object (mirrors the `fx-sync`/`fx-monitor` service_role-only pattern already in this repo) |
| V5 Input Validation | Yes | The PDF byte stream is fully untrusted input parsed by a well-hardened third-party parser (pdf.js via `unpdf`), never hand-rolled; page count and byte size are checked before and during extraction (D-07); every extracted string is treated as untrusted text through the same `MAX_DESCRIPTION`/`MAX_RAW_CELL` bounds Phase 2 already enforces on `DraftRow` |
| V6 Cryptography | Yes | Upload travels over TLS (Supabase's standard HTTPS endpoints); a PDF's own password (D-21) is never stored, only held in memory for the duration of the single extraction call and discarded; signed upload URLs are short-lived (2-hour fixed expiry, not configurable, which is more than sufficient for an interactive upload) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Malformed/hostile PDF crafted to trigger pathological parser behaviour (CPU/memory blowup) | Denial of Service | Page-count pre-check before full extraction (enforced before the D-07 cap is reached); rely on pdf.js's own decade of hardening against malformed input rather than a custom parser; Edge Function's own CPU/memory ceilings act as a hard backstop even if a pathological file slips through |
| Statement content (amounts, payee names, account fragments) leaking into server logs or Sentry | Information Disclosure | D-15's server-side scrubber (mirroring `src/services/errors/scrub.ts`), applied to every log line and every error thrown from `read-pdf-statement`, plus an automated no-leak test (Validation Architecture, IMP-03 row) |
| Uploaded PDF persisting longer than intended (crash mid-read, closed app before delete) | Information Disclosure / Repudiation of the "deleted straight after" promise | D-10's synchronous delete-after-read in the same Edge Function call, backed by D-12's 24h `pg_cron` purge as a backstop (mirrors `fx_auto_accept_holds`'s scheduled-cleanup pattern already proven in this repo) |
| A user's own signed upload URL reused or replayed after the import completes | Tampering | 2-hour fixed expiry (Supabase platform behaviour, not configurable — verified as a hard platform limit, so no additional expiry logic needs writing); the Storage object is deleted immediately after a successful read, so a replayed upload URL past that point has nothing to overwrite that matters |
| Committing a real institution's copyrighted specimen PDF as a test fixture in this public repository | Information Disclosure (of a licensing/legal kind, not user data) | See Common Pitfalls §5 — use only verified public-domain specimens or locally-authored synthetic fixtures in committed test assets |
