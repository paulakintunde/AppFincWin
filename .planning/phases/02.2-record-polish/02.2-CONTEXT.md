# Phase 2.2: Record polish - Context

**Gathered:** 2026-10-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Activity and the Record screens reach the depth of the prototype (`FincWin United.dc.html`). Phase 2's filter system stays and works in every view.

The phase delivers:
- **Activity views:** a view dropdown (By day, By week, In / out, Running balance, Calendar). Every group carries a net subtotal.
- **Sort and count:** sort (Newest, Oldest, Biggest, Smallest, A–Z) and a transaction count next to the total.
- **Recurring series:** recurring lines are detected from logged history and offered as a series.
- **Row actions:** clone, a read-only detail sheet, swipe to pay or delete, and Scheduled and Paid/Received tags.
- **Richer entry sheet:** keypad, Automatic payment, Refund, the "Marking this paid…" and FX "Saves as…" notes, and Received/Expected for income.
- **Paste-list import.**
- **Months, week start and caps:** month list counts with "Add next month", a week-start setting, and category usage with an optional monthly cap.
- **Sample figures** with "Start fresh".
- **Accounts:** deleting an empty account, and an account detail showing Coming in / Going out and the balance after pending.
- **Home-currency change** (REC-25).

Requirements: ACT-06, ACT-07, ACT-08, ACT-09, ACT-10, ACT-11, ACT-12, ACT-13, ACT-14, ACT-15, ACT-16, ACT-17, ACT-18, REC-19, REC-20, REC-21, REC-22, REC-23, REC-24, REC-25.

The visual and interaction contract is already approved in `02.2-UI-SPEC.md`, including its 11 "Confirmed Decisions" (2026-10-08). This file adds the data and behaviour decisions underneath that contract.

Not in this phase:
- the app-wide FAB, back stack and tab shell (Phase 3);
- shared household lines (Phase 8, HH-04);
- recurring transfers (Phase 2 D-56, still deferred);
- level gating of these features (Phase 9);
- cap-breach push notifications (Phase 10). This phase only stores the cap, shows usage and fires the in-app haptic and toast.

</domain>

<decisions>
## Implementation Decisions

### Automatic payment and refunds
- **D-01:** **"Automatic payment" is a label only.**
  - The detail sheet shows Method: Automatic or Manual.
  - The line stays `pending` until the user marks it paid, or an import row matches it (Phase 2 D-55).
  - Phase 2 D-05 holds unchanged: the app never claims a payment it can't see. Overdue logic is the same as for manual lines.
- **D-02:** **The Automatic flag lives on the recurring series template.**
  - Occurrences inherit it, and a "This and future" edit changes it (Phase 2 D-07).
  - One-off lines carry the flag themselves.
  - Additive migration only (Phase 1 D-26/D-27).
- **D-03:** **A refund is an expense-direction line with a `refund` flag.**
  - As in the prototype (`t.refund`, html ~3764, 4860–4861, 5882).
  - Money comes into the account (signed positive under Phase 2 D-44).
  - The line stays in its spending category and subtracts from that category's spend.
  - It does **not** count as income: In / out, income totals and Decide inputs treat it as negative spend, not earnings.
  - Refund is offered on expenses only. It is hidden on income and transfers.
- **D-04:** **Refunds net off category caps.** Cap usage is spend minus refunds in that category for the month.
- **D-05:** **A refund is standalone.** It has no link to the purchase it reverses and no picker, and partial refunds just work.
- **D-06:** **A category's net spend can go negative.** If refunds exceed spend in a month (for example a return in October for a September purchase), the category shows the true negative net. Totals must always add up, so there is no floor at zero.
- **D-07:** **Import suggests refunds, and the user confirms.**
  - Trigger: a money-in row on a card or current account whose description matches an earlier purchase from the same merchant.
  - It is offered as "Looks like a refund from {merchant}. Mark as refund?", following the D-21/D-52 suggestion pattern. Nothing is changed silently.
  - *Planner note:* this is a small extension of the existing import suggestion step. Keep it to the same matcher style as transfer detection. If it grows, it can be split into its own plan.
- **D-08:** **An import row matching a pending line flagged Automatic still asks before marking paid.**
  - It uses the same "Looks like this pays the pending {name} bill. Mark it paid?" prompt as Phase 2 D-55.
  - For Automatic lines the suggestion is **pre-ticked**, so accepting is one tap.

### Sample figures and Start fresh (REC-23)
- **D-09:** **Sample figures are real Supabase rows carrying an `is_sample` flag**, on accounts, transactions, categories and series. Additive migration.
  - Every screen and query path works unchanged.
  - These must exclude flagged rows: Decide inputs (Phase 4/5), the recurring detector (D-17), exports, Insights, and anything else that makes a claim about the user's real money.
  - "Start fresh" deletes the flagged rows.
- **D-10:** **Any edit makes a sample item real.** Editing a sample line, account or category clears its `is_sample` flag. From then on it is the user's own and Start fresh leaves it alone. This is how the UI-SPEC's "unedited items only" rule is implemented.
- **D-11:** **The first real save while samples exist prompts once.**
  - When the user saves their first non-sample line, the app asks to clear the sample figures.
  - If they decline, the line saves, the samples stay and the banner remains.
  - **The prompt is never shown again** (per user, server-stored, so it doesn't reappear on a second device).
  - The Start fresh banner stays until samples are cleared.
- **D-12:** **Sample figures are generated in the user's home currency** with realistic magnitudes, plus **one foreign-currency line** to show FX. They follow the UI-SPEC shape: accounts, about 20 lines in the current month and one recurring set. The planner decides whether generation happens on the server (an RPC) or on the client. Either way, rows go through the normal insert path, so RLS and FX stamping apply.

### Clone, Add next month and recurring detection (REC-19, ACT-11, ACT-15)
- **D-13:** **"Clone {PrevMonth}" offers last month's one-off lines**, meaning lines that are not series occurrences.
  - Series occurrences are excluded because they already exist in the current and next month (Phase 2 D-03).
  - Lines already present this month by the same name are skipped, and all candidates are ticked by default (UI-SPEC §6).
  - The UI-SPEC's body copy "Recurring lines only…" should be reconciled to this rule at planning time. Proposed wording: "Lines from {PrevMonth} that aren't already repeating. Anything already here by the same name is skipped."
- **D-14:** **Cloned lines are `pending`, on the same day-of-month, clamped to the month's end** (Phase 2 D-04's clamp). Amount, currency, category, account, name and payment type are copied. A whole clone is one undo step (Phase 2 D-24).
- **D-15:** **The detail sheet's "Clone transaction" opens a prefilled entry sheet.** It is dated today and nothing is written until Save. This is not an instant duplicate.
- **D-16:** **"Add {month}" materialises that month.**
  - It extends the user's materialisation horizon (Phase 2 D-03) to cover the added month.
  - Series occurrences there become real `pending` rows that can be edited and marked paid like any month.
  - The horizon needs to be stored per user (for example a `horizon_month` on the profile). It is undoable, and the cap is 12 months ahead (UI-SPEC §7).
  - An empty month that has been added must persist even with no rows, so the month list can't be derived from transactions alone.
- **D-17:** **The recurring detector runs on the device whenever Activity shows a month.**
  - It looks back over the last few months of logged history.
  - It reuses `src/engine/recurring/detect.ts` (already used after import, Phase 2 D-21) with the same thresholds.
  - It excludes sample rows (D-09), rows already in a series, and transfers.
- **D-18:** **"Not now" stores the dismissed set per user on the server.**
  - The exact lines or merchants dismissed are never re-offered, on any device.
  - A genuinely new recurring line still triggers a fresh offer.
- **D-19:** **"Mark all monthly" creates one monthly series per detected line, anchored to that line's latest logged row** (the Phase 2 D-09 path).
  - The anchor row becomes occurrence 1, so nothing is duplicated.
  - The whole batch is one undo step.
  - "Review each" walks the same per-line path one at a time.

### Paste, caps and settings (REC-21, REC-22, ACT-16, REC-25)
- **D-20:** **Paste accepts flexible lines.**
  - One item per line: a name and an amount in either order, with an optional date.
  - Separators can be tabs (a spreadsheet copy), commas or spaces.
  - Amounts go through the strict parser (Phase 1 D-24 / Phase 2 D-43, never `parseFloat`).
  - Unreadable lines are skipped and listed after commit.
  - The line parser is pure and lives in `engine/`, property-tested. It reuses the CSV tokenizer where that fits.
  - Rows land as `pending`, dated in the viewed month unless the line has a date. They go through the duplicate check, and the paste is one undo step (UI-SPEC §9).
- **D-21:** **A pasted line is an expense unless it starts with "+"**, which makes it income. Category is guessed by the existing rules (Phase 2 D-14) and is editable before adding.
- **D-22:** **A home-currency change re-converts category caps at today's rate.**
  - It uses the same on-demand rates fetched for the change (REC-25).
  - Caps are rounded to a whole unit, and a toast says the caps were converted.
  - It is all-or-nothing together with the currency change: if the rate fetch fails, nothing changes (UI-SPEC Confirmed Decision 11).
- **D-23:** **Week start and caps are stored on the server, per user.** Week start goes on the profile and the cap on the category row (categories are per user, Phase 2 D-33). Both follow the user across devices. Additive migrations. Week start defaults from the device region (region-preference precedence: user override, then device region).

### Accounts, balances and Phase 3 overlap (REC-24, ACT-06/08, ACT-17)
- **D-24:** **An account can be deleted when it has no live lines and no active series pointing at it.**
  - The delete is soft (Phase 2 D-30) and undoable as one step.
  - Otherwise only Archive is offered, with the reason shown.
  - Soft-deleted lines don't block the delete.
- **D-25:** **Running balance counts paid lines only, starting from the account's true balance at the start of the month.** That balance is the opening balance plus paid lines before the month (Phase 2 D-10), so the view matches the bank.
  - Pending lines are listed in order but marked as not yet moving the balance.
  - With no account filter, the running figure is in home currency (UI-SPEC Confirmed Decision 6).
- **D-26:** **Account detail's "balance after everything pending" counts every real pending row**, which runs through the end of next month (Phase 2 D-03), or further if months were added (D-16). It is labelled with the horizon ("after pending through {Month}"). Coming in and Going out are computed from the same pending set.
- **D-27:** **Phase 2.2 builds the shared pieces before Phase 3 exists:** `Dropdown`, `SwipeRow` and a detail-sheet primitive go in `src/ui`, built to `03-UI-SPEC.md`. Phase 3 then adopts them rather than replacing them. The FAB, the app-wide back stack and the tab shell stay in Phase 3.

### Claude's Discretion
- How detector thresholds and the look-back window are tuned, as long as D-17's reuse of `detect.ts` holds.
- Whether sample generation is a server RPC or a client generator (D-12).
- The schema shape for the horizon, the dismissed-series set and the "sample prompt shown" marker (D-11, D-16, D-18), within additive-migration rules.
- How swipe thresholds feel, within UI-SPEC's 88px reveal and full-swipe-commits.
- The order of work and plan split across the 20 requirements.

</decisions>

- `src/engine/csv/tokenize.ts` and `src/engine/money/parseAmount.ts` / `parseNotatedAmount.ts`: the basis for the paste-line parser (D-20).
- `src/engine/categorize/guessCategory.ts`: categories for pasted lines (D-21).
- `src/engine/statement/duplicates.ts`: the duplicate check for pasted rows.
- `src/engine/undo/*` and `src/data/mutations/undo.ts` / `undoCapture.ts`: one-step undo for clone, paste, Mark all monthly, Start fresh, Add month and delete account.
- `src/data/mutations/homeCurrencyRates.ts` and `moneyPrefs.ts`: the existing on-demand FX for a home-currency change (02-49). REC-25 may be largely built already, so the planner should verify what is left (D-22 cap re-conversion).
- `src/features/record/activity/{ActivityScreen,ActivityRow,MonthSwitcher,MonthTotalsBar,FilterSheet,activitySections}.tsx|ts`: the surfaces the view, sort, count and tag work extends.
- `src/features/record/entry/{TransactionSheet,RepeatsField,OccurrenceActions,EditScopePrompt}.tsx`: the entry-sheet extensions (keypad, toggles, notes).
- `src/features/record/categories/*`, `accounts/*`, `import/*`: caps and usage, delete account, and the paste entry point.

### Established Patterns
- `engine/` is pure, with no db, state, services, ui or react imports, and must keep branch coverage. The new logic (paste parser, net subtotals, week grouping, running balance, clone candidate selection, refund netting) goes there, with property tests.
- Supabase is the source of truth, with a TanStack Query persisted cache and a paused-mutation write queue. Mutations go through `src/data/mutations/*` with `expected_version`.
- Migrations are additive only (`supabase/migrations/`). Production is the only project, so run `npm run supabase:preflight` before `db push`.
- Haptics use only `notificationAsync`, `impactAsync` and `selectionAsync`.

### Integration Points
- Routes in `app/(app)/` (`activity.tsx`, `categories.tsx`, `accounts/`, `import.tsx`, `you.tsx`, `setup/`). The sample-figures choice hooks into the onboarding setup flow (`src/features/record/setup`).
- The You screen (`src/features/you/YouScreen.tsx`): the "Week starts on" row and the home-currency change.
- The Decide engine (Phase 4/5) must filter on `is_sample` (D-09). Record this as a cross-phase requirement.
