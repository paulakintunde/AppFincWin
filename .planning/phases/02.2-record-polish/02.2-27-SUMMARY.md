# Phase 02.2 Plan 27: Import refunds and Automatic pre-tick Summary

Statement import now offers `Looks like a refund from {merchant}. Mark as refund?` (unticked, via engine `matchRefunds`, accepted rows insert with `is_refund` true in the purchase's category) and pre-ticks pay matches on Automatic pending lines within the existing suggestion cap.

## What changed
- `buildPreview` takes optional `purchases`, runs `matchRefunds` on rows that are not duplicates, pay-matched or transfer-suggested; preview rows gain `refund` and `payMatch.automatic`. `CommitDecisions.refunds` (optional) drives `is_refund` and the category on insert.
- `useStatementImport` reads purchases once (account, 120-day lookback, expense rows only), maps `automatic: is_automatic` for pending occurrences, tracks `refundAnswers`, exposes `refundRows`/`acceptRefund`/`dismissRefund`, and commits from the effective pay answers (including pre-ticks).
- `MatchesStep` renders the refund card; the Matches stage is entered when refund rows exist.
- Analytics: `refund_suggestion_answered { accepted }` (literal property only).
- `suggestionCap.ts`: documented only (formula unchanged); tests prove pre-ticked matches count and refunds add no ops.

## Deviations from Plan
- [Rule 3 - Blocking] `ImportScreen.test.tsx` (outside files_modified): its mocked import state lacked `refundRows`/`acceptRefund`/`dismissRefund` and the pay-match rows lacked `automatic`, so MatchesStep crashed. Minimal fixture additions only.
- `useStatementImport.test.tsx` I-02 expectation changed from 1 to 2 range reads (file range plus the new refund purchases read).
- `PreviewInput.purchases` is optional (defaults to none) rather than required, so sibling callers and existing fixtures are unaffected.
