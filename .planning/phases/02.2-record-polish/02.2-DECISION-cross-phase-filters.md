# Decision: cross-phase filters for sample rows and refunds

**Date:** 2026-10-09
**Decided by:** Phase 2.2 context (CONTEXT D-01, D-03, D-09).
**Status:** decided. Binding on every later consumer of transaction data.

## Context
Phase 2.2 adds two flags that change what a transaction row means:
- sample rows (`is_sample`), seeded so a first-time user can look around;
- refund lines (`is_refund`), money coming back from a merchant.

Neither is visible in the amount or the direction alone, so any consumer that reads rows without checking the flags will report the wrong figure. Decide is the only place where a wrong answer causes real harm, so the rule is recorded here once.

## Decision
1. **Sample rows.** `transactions.is_sample`, `accounts.is_sample`, `categories.is_sample` and `recurring_series.is_sample` (CONTEXT D-09). Every consumer that makes a claim about the user's real money excludes rows with `is_sample = true`: the Phase 4/5 Decide engine inputs, Insights (Phase 7), exports (DAT), and the recurring detector (this phase). Screens and totals inside Record include them, because the banner tells the user they are samples.
2. **Refunds.** `transactions.is_refund = true` is an expense-direction line with a positive amount (CONTEXT D-03). Every consumer treats it as negative spend in its category: never income, never part of Money in. Decide's income and spending inputs must key on `is_refund`, not on the amount sign.
3. **Automatic payment.** `is_automatic` is a label only. It must never be read as "paid" (CONTEXT D-01); only the status says whether money has moved.

## Consequences
- Phase 4 (`.planning/phases/04-decide-engine/`, already planned): its executor must add `is_sample = false` and refund-aware sign handling to whatever query feeds the engine. Phase 4's verifier checks both explicitly.
- Phase 7 Insights and the DAT exports apply the same two rules when they are planned.
- Record screens in this phase keep sample rows visible and flag them; they are the only consumers that do.
