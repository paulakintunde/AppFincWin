# Phase 02.2: Record polish - Research

**Researched:** 2026-10-09
**Domain:** React Native (Expo SDK 57) Record screens on a Supabase-direct data layer; pure TypeScript engine maths; additive Postgres migrations
**Confidence:** HIGH on codebase mapping and schema constraints (read directly from the worktree); MEDIUM on a few design calls flagged in Open Questions

## Summary

Phase 2.2 is an extension phase, not a greenfield one. Every surface it touches already exists in `C:/dev/fincwin-p2/src/features/record/*` and the pure-maths half already has a home in `src/engine/{activity,recurring,csv,categorize,statement,undo,time}`. The work splits cleanly into four layers: (1) new pure engine modules with property tests (grouping/subtotals/week buckets, sort, running balance, calendar cells, clone candidates, series-offer selection, paste-line parser, category usage/caps, refund netting, pending in/out split); (2) one additive schema migration plus a few security-definer RPCs; (3) data-layer hooks and mutations that follow the existing `registerXMutations` + paused-mutation + `expected_version` + undo-step pattern; (4) UI that composes existing `src/ui` primitives plus three new shared primitives (`Dropdown`, `SwipeRow`, a detail-sheet shell) and a `Keypad`.

Four findings change how plans should be written. First, **Phase 3 is planned only, not executed**: `03-01..03-16-PLAN.md` exist with no SUMMARY files, `@gorhom/bottom-sheet` and `expo-haptics` are not in `package.json`, `src/ui/Sheet.tsx` is still the RN `Modal`-based sheet, and `03-UI-SPEC.md` contains no Dropdown spec at all (it specifies the tab bar, FAB, sheet container, header). CONTEXT D-27 says to build `Dropdown`/`SwipeRow`/detail sheet "to `03-UI-SPEC.md`"; in practice the Dropdown contract is the prototype `menu` pattern as transcribed in `02.2-UI-SPEC.md` section 1, and plans must build against that. Second, **accounts have no `deleted_at` column and no client write path to delete**, and `transactions.account_id` is `on delete restrict`, so REC-24's "soft, undoable delete" needs a new column, a grant, an `apply_patches` allowlist entry and read filters. Third, **`transactions_active` is a `select *` view**: Postgres expands `*` at creation, so every new `transactions` column (`is_refund`, `is_automatic`, `is_sample`) is invisible to the app until the migration does `create or replace view`. Fourth, **`detect.ts` as it stands (3 monthly rows, gaps 27-33 days, 10% tolerance) cannot produce the UI-SPEC's "N lines also ran in {Mon} at about the same amount"** for a line seen in only two months at a 20% tolerance; this is a real conflict between CONTEXT D-17 and UI-SPEC section 3 and is raised as Open Question 1.

REC-25 (home-currency change) is only half built. `useUpdateMoneyPrefs().setHomeCurrency`, `ensureRatesForHomeChange` and `homeCurrencyRates.ts` exist, but `YouScreen.tsx` has **no Home currency row, no picker wiring and no confirm sheet**, and the existing mutation is a fire-and-forget queued patch, which contradicts UI-SPEC Confirmed Decision 11 (all-or-nothing, inline "Getting rates...", no partial change on failure).

**Primary recommendation:** Build bottom-up in waves: (W0) one migration + RPCs + pgTAP, i18n keys, `expo-haptics` install; (W1) pure engine modules with property tests, in parallel; (W2) data hooks/mutations and shared UI primitives; (W3) screens by area (Activity views, row actions, entry sheet, paste/import, months/caps/accounts/samples/home-currency); (W4) `supabase db push` [BLOCKING] and device walkthrough. Keep every number the user sees going through `engine/` functions; keep `ActivityScreen.tsx` from growing further by extracting view components.

## User Constraints (from CONTEXT.md)

### Locked Decisions
Copied from `02.2-CONTEXT.md` (D-01 to D-27). Abbreviated headings, full text is in the source file; the planner MUST read that file.

- **D-01** Automatic payment is a label only; line stays `pending` until marked paid or an import row matches (Phase 2 D-05 holds; Overdue same as Manual).
- **D-02** Automatic flag lives on the recurring series template; occurrences inherit; "This and future" edit changes it; one-off lines carry it themselves. Additive migration only.
- **D-03** Refund = expense-direction line with a `refund` flag; money comes in (signed positive, Phase 2 D-44); stays in its spending category and subtracts from that category's spend; NOT income (In/out, income totals and Decide inputs treat it as negative spend); offered on expenses only.
- **D-04** Refunds net off category caps (usage = spend minus refunds for the month).
- **D-05** A refund is standalone: no link to the purchase, no picker, partial refunds just work.
- **D-06** A category's net spend can go negative; no floor at zero.
- **D-07** Import suggests refunds, user confirms ("Looks like a refund from {merchant}. Mark as refund?"), same matcher style as transfer detection; default unticked; may be split into its own plan if it grows.
- **D-08** Import row matching a pending line flagged Automatic still asks before marking paid; suggestion pre-ticked for Automatic lines.
- **D-09** Sample figures are real Supabase rows with `is_sample` on accounts, transactions, categories and series; must be excluded from Decide inputs, the detector, exports, Insights; Start fresh deletes flagged rows.
- **D-10** Any edit makes a sample item real (clears `is_sample`).
- **D-11** First real save while samples exist prompts once ("Clear the sample figures?"); decline keeps samples and banner; never shown again (server-stored per user).
- **D-12** Samples generated in the user's home currency, realistic magnitudes, plus one foreign-currency line; accounts, about 20 lines in the current month, one recurring set. Planner decides server RPC vs client generator; rows go through the normal insert path (RLS, FX stamping).
- **D-13** "Clone {PrevMonth}" offers last month's one-off lines (series occurrences excluded); same-name lines already present are skipped; all ticked by default; reconcile UI-SPEC body copy to "Lines from {PrevMonth} that aren't already repeating. Anything already here by the same name is skipped."
- **D-14** Cloned lines are `pending`, same day-of-month clamped to month end; amount, currency, category, account, name, payment type copied; whole clone is one undo step.
- **D-15** Detail sheet's "Clone transaction" opens a prefilled entry sheet dated today; nothing written until Save.
- **D-16** "Add {month}" materialises that month; extends the per-user horizon (e.g. `horizon_month` on profile); undoable; capped 12 months ahead; an added empty month persists (month list cannot be derived from transactions alone).
- **D-17** Recurring detector runs on-device whenever Activity shows a month; looks back a few months; reuses `src/engine/recurring/detect.ts` with the same thresholds; excludes sample rows, rows already in a series, transfers.
- **D-18** "Not now" stores the dismissed set per user on the server; exact lines/merchants never re-offered on any device; a genuinely new recurring line triggers a fresh offer.
- **D-19** "Mark all monthly" creates one monthly series per detected line, anchored to that line's latest logged row (Phase 2 D-09 path); one undo step; "Review each" walks the same path one at a time.
- **D-20** Paste: one item per line, name and amount in either order, optional date, separators tab/comma/space; strict amount parser (never `parseFloat`); unreadable lines skipped and listed after commit; pure parser in `engine/`, property-tested, reuses CSV tokenizer where it fits; rows land `pending`, dated in the viewed month unless line has a date; duplicate check; one undo step.
- **D-21** Pasted line is an expense unless it starts with "+"; category guessed by existing rules (Phase 2 D-14), editable before adding.
- **D-22** Home-currency change re-converts category caps at today's rate (same on-demand rates), rounded to a whole unit, toast says so; all-or-nothing with the currency change.
- **D-23** Week start and caps stored server-side per user (week start on profile, cap on category row); additive; week start defaults from device region.
- **D-24** Account deletable when no live lines and no active series point at it; soft delete (Phase 2 D-30), undoable as one step; otherwise only Archive, with the reason shown; soft-deleted lines don't block.
- **D-25** Running balance counts paid lines only, from the account's true balance at the start of the month (opening balance + paid lines before the month); pending listed but marked "not yet counted"; no account filter = home-currency running figure.
- **D-26** Account detail "after pending" counts every real pending row through the materialised horizon; labelled "after pending through {Month}".
- **D-27** Phase 2.2 builds `Dropdown`, `SwipeRow`, detail-sheet primitive in `src/ui`; Phase 3 adopts them; FAB, back stack, tab shell stay in Phase 3.

### Pattern 1: Single `netOf` and single group builder
**What:** every view's subtotal is computed by one engine function (`netOf` in `groups.ts`), not re-summed in components.
**Why:** ACT-08 says "every grouping shows a net subtotal"; the property "group nets sum to the total net" only holds if one function owns it.
**Subtotal semantics [CITED: 02.2-UI-SPEC section 1]:** signed home-currency sum of non-transfer lines; income and refunds positive, expenses negative; zero renders "0.00"; rows with null `amountHome` are counted in an `unconverted` count and the subtotal shows a small "plus N waiting for a rate" hint rather than silently omitting.

### Pattern 2: Flat FlashList with typed items
Extend `ActivityItem` with `{type:'group', key, label, count, net, tone}`; `getActivityItemType` returns `'group'` so FlashList recycles correctly; `cardPositions` treats `group` like `header`. All views (day, week, in/out, balance) emit this one flat list. Calendar is not a FlashList (fixed 7-column grid + day list). [CITED: FlashList v2 JS-only recycling, CLAUDE.md]

### Pattern 3: Mutation hook shape (copy `useBulkMarkPaid` / `useAddTransaction`)
Register a default `mutationFn` with `qc.setMutationDefaults(key, ...)` in `registerXMutations(qc)` (added to `mutations/index.ts`), use `scope: WRITE_SCOPE`, return the `stepId` synchronously, show the toast with `showToast({kind, text: undoLabelText(...), stepId})`. Batch writes (clone, paste) use the import chunk path (`useImportChunks` / `insertTransactionsBatch`, `IMPORT_CHUNK_MAX`) and one `inverseOfInserts` undo step; cap at `MAX_UNDO_OPS`. Optimistic rows go through `placeRowInMonth`.

### Pattern 4: Refund through the stack
- Stored as positive `original_amount` + `is_refund = true`, direction chosen by the user as Expense (D-03). `defaultStatusFor` unchanged (refund on a past date is `paid`).
- `initialFormState` for edit must reconstruct `direction = row.is_refund ? 'out' : sign-based`, with `refund = true`. Today it infers direction from the amount sign (`transactionForm.ts` line ~67): a refund row would be mis-edited as income. **This is the main correctness trap for REC-20.**
- `buildPatch`/`toNewTransaction` must write `original_amount = +magnitude` when `refund`, `-magnitude` otherwise.
- `monthTotals`, `filterRows` direction, `categoryUsage`, and the In/out view all key on `is_refund`, never on sign alone. Decide (Phase 4/5) must also treat it as negative spend; record that as a cross-phase requirement (CONTEXT code_context already lists this).

### Pattern 5: Server-stored per-user preferences
Add a `useRecordPrefs(userId)` query (profile columns `week_start, horizon_month, sample_prompt_answered_at`, plus `exists(is_sample)` for the banner) and mutation `useUpdateRecordPrefs`. Mirror `db/profile.ts` + `mutations/moneyPrefs.ts`: unconditional (not version-conditional) writes, `assertAllowedKeys`. Week-start default: `profiles.week_start is null` -> derive from `resolveRegion` (region-preference precedence: user override, then device region; never IP) with a small pure map in `engine/money/regionWeekStart.ts` (US/CA/JP/BR/IL/... Sunday-first; most of Europe Monday). Fall back to Monday. [ASSUMED: region list for Sunday-first countries; low risk, user can override]

### Pattern 6: Sample figures via server RPC (recommended)
`seed_sample_data(p_household_id, p_home_currency, p_today)`, `security definer`, `search_path = ''`, membership check as in the series RPCs: insert sample accounts (cash/current/card), ~20 transactions in the current month with realistic magnitudes scaled by a currency exponent/magnitude table in SQL (keep it in a JSON constant to avoid SQL/TS duplication), one foreign-currency line, one recurring set (call the same internals as `create_recurring_series` so occurrences materialise), all with `is_sample = true`. Inserts fire the normal triggers (`stamp_fx_rate`, guards), so RLS and FX stamping apply (D-12). `clear_sample_data(p_household_id)` hard-deletes in FK order (transactions where is_sample, series, accounts where is_sample and no non-sample transactions, categories where is_sample) and returns counts; not undoable (UI-SPEC section 11). Because edits clear `is_sample` (D-10 trigger), an edited sample line whose account is still flagged would orphan: **rule: a sample account with any non-sample line is converted to real** inside `clear_sample_data` (set `is_sample=false` instead of deleting). Test this in pgTAP.
**Why not client generation:** it would require insert grants on `is_sample`, letting any client mark arbitrary rows sample and then have Start fresh delete them.

### Pattern 7: Add-month RPC (hardest piece; give it its own plan + pgTAP)
`add_activity_month(p_household_id, p_month, p_undo_step)`:
1. Validate membership, month format, `p_month <= current + 12 months` (D-16 cap) and `p_month = next after current horizon` (only contiguous adds).
2. For each active series, generate occurrences with `date <= end of p_month` and `date > coalesce(materialised_through, anchor-1)`, reusing the date function and unique index `on conflict do nothing`.
3. Set `profiles.horizon_month = p_month` and advance each series' `materialised_through` (system restamp GUC, as `materialise_series` does).
4. Record an undo step server-side containing: soft-delete of each inserted row, plus **a rewind of `materialised_through` and `horizon_month`** to prior values. Rewinding `materialised_through` is necessary: otherwise, after undo, re-adding the month finds `materialised_through` already past the month and generates nothing (the high-water mark never rewinds by design, D-08). Follow the `record_series_undo_step` / `SeriesChangeSet.before` pattern (`engine/undo/inverse.ts inverseOfSeriesChange`).
5. The daily cron `materialise_recurring` uses `recurring_horizon(today)`; it never reduces `materialised_through` (`greatest`), so rows added by this RPC are safe. Make sure the cron path also respects `profiles.horizon_month` so a series created later still reaches the user's horizon: change `materialise_series` to `v_through := greatest(recurring_horizon(v_today), horizon_of_owner)`. Add a pgTAP case.
6. Client `monthsForSwitcher` gets `horizonMonth`; the empty added month appears even with zero rows (D-16).

### Pattern 8: Series offer pipeline (ACT-11, D-17..D-19)
`useSeriesOffers(month)` (query, derived): fetch up to N months of non-transfer, non-skipped, non-sample rows ending at the viewed month (reuse `useTransactionsForMonth` cache for months already loaded; one new range read for the rest; bound the window to the **last 6 months** [ASSUMED]), build `RecurringDetectRow[]` (`amount` in the row's own currency minor units, matching `detect.ts`), run `detectRecurring`, then `selectOffers` with dismissed keys (from `dismissed_series_offers`) and rows already linked (`recurring_series_id !== null`). "Mark all monthly" calls the existing series-create path per offer with the anchor = `rowIds` last row (reuse `suggestionToSeries` from `import/importPipeline.ts`; move it into `src/features/record/recurring/` or `data/mutations/recurringSeries.ts` so Activity can import it without depending on the import module), all inside one undo step (batch of `create_recurring_series` calls, each recording its own step today: needs a grouping mechanism, see Pitfall 7). "Not now" inserts keys into `dismissed_series_offers`.

### Pattern 9: Swipe row
`SwipeRow` wraps `ReanimatedSwipeable` with `renderLeftActions` (PAID/RECEIVED/UNPAY, width 88) and `renderRightActions` (DELETE, width 88), `overshootFriction`, `leftThreshold` so a full swipe commits (`onSwipeableOpen(direction)` -> perform action then `ref.close()`), disabled when `selectable` (bulk) is true, haptic `impactAsync(Light)` on commit, and `accessibilityActions` mirroring the swipes. Recurring occurrences: delete still routes to the `EditScopePrompt` scope question (UI-SPEC section 4). Transfers: swipe-left uses the delete-both `ConfirmSheet`.

### Anti-Patterns to Avoid
- **Deriving the month list from transactions only** (D-16): an added empty month vanishes.
- **Treating a refund as income via sign**: breaks totals, filters, caps and edit round-trip (Pattern 4).
- **Summing group subtotals in render code**: duplicates maths outside `engine/` and breaks the "adds up" property.
- **Writing `is_sample` from the client** or clearing it in client code.
- **Adding to `ActivityScreen.tsx` inline**: it is already 394 lines with ~15 pieces of state.
- **Importing `import/importPipeline` from Activity**: `suggestionToSeries` must be relocated first (also avoids a depcruise cycle).
- **`parseFloat` / `Number(text)` anywhere in paste or keypad parsing** (CLAUDE.md money rule, Phase 1 D-24).

## Common Pitfalls

### Pitfall 1: New columns invisible through `transactions_active`
**What goes wrong:** `select is_refund` from the view fails (or returns undefined in the client) although the table has the column.
**Why:** the view was created with `select *`; Postgres stores the expanded column list.
**How to avoid:** migration does `create or replace view public.transactions_active with (security_invoker = true) as select * from public.transactions where deleted_at is null;` then re-issues `revoke all ... from anon, public, authenticated; grant select ... to authenticated;` (the D-WR-07 pattern). New columns must be appended (they are, as `alter table add column` appends).
**Warning signs:** pgTAP test `has_column('public','transactions_active','is_refund')` failing; client `TRANSACTION_COLUMNS` select 400s.

### Pitfall 2: `apply_patches` allowlist drift
**What goes wrong:** bulk edit/undo of a column raises 22023 "unknown column".
**How to avoid:** every new patchable column is added to BOTH the `v_allowed` case and the `v_col_type` case in a `create or replace function public.apply_patches` (copy the latest body in full), plus a pgTAP test per column. Also update `TRANSACTION_PATCH_KEYS`, `CATEGORY_PATCH_KEYS`, `ACCOUNT_PATCH_KEYS`.

### Pitfall 3: Edit-clears-sample trigger fires on system writes
**What goes wrong:** the materialiser's bookkeeping update or `clear_sample_data` flips flags.
**How to avoid:** guard on `current_setting('fincwin.system_restamp', true) = 'on'`, the existing convention. Also ensure `mark paid` of a sample pending line clears the flag (it is a user edit) and the banner logic (`exists is_sample`) re-queries after every write that could change it.

### Pitfall 4: Running balance double-counts or ignores the pre-month balance
**What goes wrong:** balance starts at 0 or at `opening_balance`, so it disagrees with the account screen.
**How to avoid:** opening for the month = `account.opening_balance + paid_before_month` (new RPC), same BigInt path as `accountBalance`. For "all accounts" convert each account's opening and each row to home currency (rows carry `amountHome`; the opening needs a rate: `projectionHomeAmount` with the latest stored rate, "Waiting for a rate" when missing, never fetch, per `02-DECISION-fx-on-demand.md`). Property test: figure after the last paid row equals `accountBalance` paid total as of month end.

### Pitfall 5: Week 6
**What goes wrong:** success criterion says "Week 1 to Week 5" but a 31-day month starting on the week's last day yields 6 buckets (formula `floor((d+first0-1)/7)+1`).
**How to avoid:** support up to 6; omit empty weeks (UI-SPEC Confirmed Decision 5). Test months that produce 6 weeks for each week start.

### Pitfall 6: Added month then undo, or later series creation
See Pattern 7 steps 4-5. Without the `materialised_through` rewind, undo then re-add silently produces an empty month; without the cron change, a series created after the horizon was extended stops at next month.

### Pitfall 7: "One undo step" for batched series creation
**What goes wrong:** `create_recurring_series` records its own undo step per call (D-WR-04), so "Mark all monthly" over N lines yields N steps, violating D-19's single step.
**How to avoid:** add a batch RPC `create_recurring_series_batch(p_items jsonb, p_undo_step jsonb)` that loops the internals and records one combined step (follow `record_series_undo_step`). Check the 6000-op cap (N is small, no issue). pgTAP: undo reverts all N series and anchors.

### Pitfall 8: Detector excludes what the UI-SPEC expects (and vice versa)
`detect.ts` needs 3 monthly rows and sorts out groups where *any* gap is outside 27-33 days. Lines posted on the 31st/30th/28th months boundaries (e.g. 31 Jan, 28 Feb, 31 Mar) yield gaps 28, 31 (ok) but real-world bank dates drift. Also, because it requires every gap in one window, one missed month breaks the group. This is acceptable (conservative) but means "also ran in Aug" will not fire for exactly two prior occurrences. See Open Question 1.

### Pitfall 9: Import suggestion cap
`suggestionCap.ts` computes a safe maximum of accepted suggestions against `MAX_UNDO_OPS`; refund suggestions add patches. Include them in `acceptedSuggestionCount` and the cap tests, otherwise a large import can exceed 6000 ops.

### Pitfall 10: Keypad vs validators
The keypad must call the same `useAmountParser` rules (decimal separator by locale, exponent per currency including 0 and 3 decimal currencies, ceiling). Build `applyKey(text, key, {exponent, decimalSeparator, maxMinor})` as a **pure function in `engine/money/keypad.ts`** and property-test it (output always re-parses; never exceeds exponent; no leading zeros; backspace inverse of append). Do not let the component manage the string.

### Pitfall 11: Native module rebuild
`expo-haptics` is the only new native dependency; schedule a dev-build in the plan that installs it, and gate JS usage with a try/catch-free wrapper that is mocked in Jest (`jest.setup.ts`).

### Pitfall 12: Shared checkout / production DB
Per CLAUDE.md and memory: `supabase db push` hits production (the only project) and `main` is PR-protected. The push plan must be `[BLOCKING]`, run `npm run supabase:preflight`, and use `npm run supabase:db:push`. Do not use the Supabase MCP connector. Additive-only: the squawk gate (`npm run lint:migrations`) rejects `set not null` without default, type changes, drops, and renames without a `contract-ok` marker.

// Source: FincWin United.dc.html line 5014-5015 (prototype), adapted
export function weekOfMonth(month: string, day: number, weekStart: 0 | 1): number {
  const [y, m] = month.split('-').map(Number) as [number, number];
  const dow = new Date(Date.UTC(y, m - 1, 1)).getUTCDay(); // 0 = Sunday
  const first0 = (dow - weekStart + 7) % 7;
  return Math.floor((day + first0 - 1) / 7) + 1;
}
export function weekRange(month: string, w: number, weekStart: 0 | 1, dim: number) {
  const first0 = /* as above */ 0;
  return { from: Math.max(1, (w - 1) * 7 - first0 + 1), to: Math.min(dim, w * 7 - first0) };
}
