# Phase 10.1 Plan 23: Receipts in detail, entry, Activity, delete and realtime Summary

At level 2 the line's detail has a Receipt row ("None", "1 file", "3 files" or "Waiting to upload") that opens the Receipt sheet, and with files the detail shows the thumbnail strip, whose thumbnails open the viewer. The entry sheet offers "Add a receipt" on a new entry: the picked files stay on the phone in the sheet and are queued in the outbox with the line's id the moment the line is saved; closing the sheet any other way deletes them. In edit state a "Receipt" row opens the line's Receipt sheet. An Activity row with a receipt still on the phone shows the savedOffline glyph and "Receipt waiting to upload" under the name, and its spoken label ends with ", receipt waiting to upload". Deleting a line with receipts adds "Its receipts are deleted too." to the confirmation. A partner's receipt on a shared line arrives through the household realtime channel and refetches only that line's receipts.

## Decisions
- **Entry-sheet id path: client-generated.** `useAddTransaction().add()` returns the id it makes on the phone, so the picked files are enqueued right after the insert is issued (both the plain add and the add-with-repeat paths). The outbox already waits for the line to reach the server (`line_not_ready`). The picked cache copies are deleted once the outbox holds its own copies.
- **Receipt count = receipts, not pages.** The row and the entry count use receipt groups (a 3-page scan is "1 file"), matching the Receipt sheet's limit, which counts groups (D-21).
- **"Waiting to upload" covers failed uploads too** (both are still on the phone); the strip and the Receipt sheet still tell them apart. A failed thumbnail in the detail opens the Receipt sheet, where Try again / Remove live.
- **Transfers carry no receipts**: no Receipt row on a transfer's detail and no "Add a receipt" on a new transfer.
- **Below level 2 nothing is read**: the detail sheet mounts the receipts reader only when `useFeatureAccess('receipts')` is visible (a wrapper component, so the hook is never called conditionally), the Activity view model reads the outbox only then, and the delete check runs only then.

## Deviations from Plan
1. **[Rule 2] Plain-line delete with receipts now asks first.** A plain line was deleted at once with Undo (no confirmation existed to add the sentence to). A line that has receipts now gets the "Delete this transaction? Its receipts are deleted too." confirm (`DeletePrompt` 'lineDelete', rendered in ActivityScreen); a line without receipts is deleted at once exactly as before. A repeating line's scope prompt shows the sentence (`EditScopePrompt` gained an optional `note`). The entry sheet's own Delete confirmation adds it too.
2. **Delete check helper `lineHasReceipts`** (new file): the cached receipts query answers at once; with nothing cached and online it asks `listReceipts` for that one id; offline and uncached the answer is unknown and the prompt stays unchanged. It reads the QueryClient through `useContext(QueryClientContext)` and lazy-requires the db client, so screens and tests without a query provider are unaffected.
3. **The receipts sentence is wired on Activity only.** `useRowActions` takes `receiptsOn` (default false); ActivityScreen passes it. Home and the goal record detail share `useRowFlow` but do not pass it (their view models do not read feature access, and adding it would pull the level providers into their tests), so deleting from Home keeps today's flow (immediate delete with Undo, which also restores the receipts, since a soft delete purges nothing).
4. **New component `ReceiptCaptureSheet`** (the "capture choice" for a line not saved yet: photo, file, scan, the same limits, errors and permission card as the Receipt sheet). `useReceiptActions` now exports `pickReceipt` and `errorFor` for it.
5. **Picked files and the entry list:** "Add a receipt" shows only while the entry list is empty; "Add to list" deletes files already picked (receipts go with a single saved entry). A form kept as a draft (swipe-down on a new entry) keeps its fields but not its picked files.
6. **Realtime DELETE without the line id:** the table has default replica identity, so a DELETE event may carry only `id`. Then every cached receipts list of the household (`['receipts', householdId]`) is refetched; nothing outside receipts is touched. With `transaction_id` present only that line's key is invalidated.
7. **ActivityScreen.tsx and EditScopePrompt.tsx** were edited although not in the plan's file list (row prop, prompts).
8. **Copy keys added** (no wording changed): `receipt.row.files_one` ("{{count}} file", so one receipt reads "1 file"), `receipt.entry.label` ("Add a receipt", UI-SPEC section 3), `receipt.waitingA11y` ("receipt waiting to upload", the end of a row's spoken label).
9. **TDD order:** tests and implementation were written together per task and committed in one commit per task, not separate RED/GREEN commits.
10. `TransactionDetailSheet.parts.test.tsx`'s feature mock now answers per feature id (splits on, receipts off) so it is not affected by the receipts reader.
