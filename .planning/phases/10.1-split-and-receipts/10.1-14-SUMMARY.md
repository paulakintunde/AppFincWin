# Phase 10.1 Plan 14: Split by item, server side Summary

The database now recomputes every share from the items (never trusting client shares), stores the split as a hand-set `amount` rule together with the category parts and item list in one transaction, and offers a version-checked restore for Undo. Partners see parts categories, and the Phase 10 over-cap sum counts parts.

## Deviations from Plan

1. **Migration timestamp 20261127000400, test file 135.** The plan's 20261127000300 and test number 134 were already taken by 10.1-11.
2. **[Rule 1] hh_allocate takes int[] weights**, so extras and household-currency shares use `parts_allocate` (numeric weights, identical tie rule) from 10.1-05. Per-item splits (all-ones weights) still use `hh_allocate`.
3. **Over-cap re-issue goes further than a sum swap.** `alerts_on_transaction` now checks every category in the row's parts (not only `category_id`), and its trigger also fires on `category_parts` updates. Otherwise a non-primary part crossing a cap would never alert. Other server sums by category: none found (grep of all migrations).
4. **Extra refusals** beyond the contract: `rate_unavailable` (household amount not stamped yet), `before_invalid` (restore with a malformed before), `transfer_part_on_transfer_line`.
5. **Test-only:** pgTAP 135 temporarily replaces `hh_line_locked` and restores the real body (same approach as 131).
