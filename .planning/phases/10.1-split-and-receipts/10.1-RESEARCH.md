## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** One transaction stays **one line** (one movement on the bank balance). Its category parts are stored inside it. This replaces the prototype's behaviour, which turned one purchase into N separate transactions (`FincWin United.dc.html` L6514-6545). Reason: the line keeps matching the bank statement, so import de-duplication, undo and the household split stay right.
- **D-02:** Parts are integer minor units and always add up exactly to the line's total. The split sheet follows the prototype: rows of category + amount, an "add part" control, and the balance label "Adds up" / "X left to place" / "X over"; save stays disabled until it adds up.
- **D-03:** Editing the total of a split line never guesses: the split shows the gap ("$5 left to place") and asks the user to place it.
- **D-04:** A part may use **any** category, including Savings and Transfer. Each part counts the way its category counts today (a Savings part counts as saving in Decide and Insights; the builtin-key checks in `buildInputs.ts` apply per part).
- **D-05:** Activity shows a split line as **one row** with the full amount and an "N categories" tag; tapping it shows and edits the parts. Filtering Activity by a category shows only that part's amount. Category totals, caps (`engine/categorize/usage.ts`), Insights (`engine/insights/categories.ts`, month model) and Decide (`buildInputs.ts`, `judge/lines.ts` caps) read parts wherever they read a line's category today.
- **D-06:** A receipt can be a **photo** (camera or gallery), a **file** (image or PDF) or a **multi-page scan** that is straightened automatically, as in the prototype receipt sheet (L2747-2760, L5994-6003). Several files per line are allowed; "Remove all" leaves the line without any.
- **D-07:** On a **private** line only the owner can see its receipts. On a **shared** household line, everyone the line is shared with can open them; nobody outside the line ever can (storage access rules, not just app hiding).
- **D-08:** A receipt is kept **as long as the line**: until removed, until the line is deleted, or until account deletion, then deleted for good (storage objects removed, not just rows). Receipts are included in the data export (Phase 10 export needs a way to deliver files, since CSV cannot hold images).
- **D-09:** **Offline:** attaching a receipt saves it on the phone and uploads it when back online; the line shows "Receipt waiting to upload". Nothing is lost. (Receipt uploads are not ordinary row writes; the planner decides how they relate to the Phase 10 offline queue limit D-27.)
- **D-10:** **Phone first, server if needed.** The receipt is read on the phone (private, free, works offline). If that fails or reads badly, the user can choose "Read it online"; this shows a one-line consent note (02.1 D-05 pattern), the image is processed in us-west-2 (02.1 D-04) and deleted from the server right after reading, and the server keeps no copy (02.1 D-10..D-13). Never sent online without that choice.
- **D-11:** It reads **store, date, total and each item with its price**, plus tax, tip and discounts as their own rows.
- **D-12:** Unsure rows are **marked "Check this"** with the photo alongside; if the items don't add up to the total, it says by how much. **Nothing is saved until the user confirms.**
- **D-13:** Scanning is available **from Add** (scan first; the new line is filled in) **and from an existing line** (attach and split).
- **D-14:** On a shared line, every item **starts split the line's usual way** (its current rule, e.g. even); tapping an item gives it to one person or some people. Each person's share of the line becomes the total of their items (stored through the existing household split as the per-member amounts).
- **D-15:** Tax, tip and discounts are shared **in proportion to each person's items** (Splitwise Itemize style). Odd cents use the existing largest-remainder rule (`hh_allocate` / `src/engine/split/allocate.ts`), so shares always add up.
- **D-16:** Each item gets a **suggested category** (from the user's past lines and the store) that the user can change; the line's category parts are built from the items. This works on private lines too, not only shared ones.
- **D-17:** **Whoever can edit the shared line today** can split it by item. Everyone on the line sees the result, the receipt and who changed it, with the existing before-and-after notice and Undo.

## Summary

The phase is mostly well-trodden ground in this repo: server-side RPC writes with version checks (`set_line_split`), `hh_allocate` largest-remainder maths, a private Storage bucket with a read-then-delete Edge Function (`read-pdf-statement`), server-side undo through `apply_patches`, and an export manifest with a guard test. The genuinely new risk is native: Expo SDK 57 on EAS from Windows needs an image picker, a document scanner and an on-device text recogniser, none of which is installed, all of which force a new dev build and change the `fingerprint` runtime version (so no OTA to old builds). iOS cannot be verified until Apple enrolment lands (the CLAUDE.md constraint); the Android Pixel path is the certain one.

Recommended design. **Parts live in a jsonb column `category_parts` on `transactions`** (D-01 "stored inside it"). It rides on the existing row for RLS, realtime, cache, export, delete cascade and, crucially, undo (a column patch through `apply_patches`, no new entity). `transactions.category_id` stays set to the **largest part's category**, so every reader not yet converted degrades safely (counts the full amount under the main category) and `hh_resolve_default_rule` keeps working untouched. All readers switch through **one pure engine helper** `expandParts()` that turns lines into category-attributed amounts, with the unplaced remainder emitted as `categoryId: null` (Uncategorised). **Receipts** are rows in `transaction_receipts` plus objects in a new private bucket `receipts`; storage read policy joins to `transactions` (owner, or shared line in the caller's household). Removal goes through an RPC that queues the object path for a service-role purge function, because SQL deletes orphan Storage files. **Reading**: `@react-native-ml-kit/text-recognition` (or the Expo-module alternative, decided by a spike) returns blocks with frames; a pure engine parser rebuilds rows from frames and flags uncertain ones. **Online fallback**: AWS Textract `AnalyzeExpense` in us-west-2 behind a new `read-receipt` Edge Function (image in the request body, never written to disk or Storage, so there is no server copy to delete). Item split reuses `hh_split_plan` with the `amount` rule, computed from items and proportional extras by one pure TS function mirrored by a server-side recompute.

**Primary recommendation:** Start with a Wave 0 native spike (picker, scanner, OCR, one EAS dev build on the Pixel) in parallel with the pure-engine work (`parts`, `receipt` parser, `itemShares`), then SQL, then UI; keep split-by-item last because it depends on parts, receipts and the reader.

### Pattern 1: parts as a column, one reader helper
**What:** `transactions.category_parts jsonb null` = `[{ "c": "<category uuid>|null", "a": <int minor units, same sign as the line's original_amount>, "l": "<optional label>" }, ...]`, at least 2 elements when present, null when the line is not split. `transactions.category_id` is always the largest part's category (ties: lowest position).
**When to use:** every reader. Unsplit line yields `[{categoryId: line.categoryId, amount: line.amount}]`. A split line yields its parts, plus `{categoryId: null, amount: total - sum}` when `sum != total` (D-03 gap, "Uncategorised").
**Example:**
```typescript
// src/engine/parts/expandParts.ts  (pure; no imports from db/state/services/ui/react)
export interface LinePartsInput {
  id: string;
  amount: number;                 // signed minor units in the amount the caller wants (original or home)
  categoryId: string | null;
  parts: readonly { categoryId: string | null; amount: number }[] | null; // in the SAME currency as `amount`
}
export interface CategoryAmount { lineId: string; categoryId: string | null; amount: number; isGap: boolean; }

export function expandParts(line: LinePartsInput): CategoryAmount[] {
  if (!line.parts || line.parts.length < 2) {
    return [{ lineId: line.id, categoryId: line.categoryId, amount: line.amount, isGap: false }];
  }
  const out = line.parts.map((p) => ({ lineId: line.id, categoryId: p.categoryId, amount: p.amount, isGap: false }));
  const gap = line.amount - line.parts.reduce((s, p) => s + p.amount, 0);
  if (gap !== 0) out.push({ lineId: line.id, categoryId: null, amount: gap, isGap: true });
  return out;
}
```
Home-currency amounts: parts are stored in the line's original currency (they must add up to `original_amount`). A reader that works in `home_amount` converts with `allocate(homeAmount, partsAsWeights)` so converted parts also sum exactly (`homeAmounts.ts`). Do not convert each part separately (rounding drift). TS `allocate` rejects weight <= 0 while SQL `hh_allocate` accepts 0 weights [VERIFIED: allocate.ts and 20261122000600]; wrap it (filter zeros, re-insert 0) rather than loosening the money-critical function.

### Pattern 2: RPC-only writes with version check and undo
**What:** `set_category_parts(p_id uuid, p_expected_version int, p_parts jsonb) returns jsonb` mirrors `set_line_split` [VERIFIED: 20261122000600 L689-728]: select for update, owner/household access check, `version_conflict` answer, `hh_line_locked` check, validate, update `category_parts` and `category_id`, return `before`. `p_parts = null` removes the split (UI "Remove the split": caller supplies `keep_as` category).
Validation (SQL and TS share one rule set): 2 to 20 parts; each `a` integer, same sign as the line, non-zero; each `c` null or a category the **line creator** owns (reuse the pattern in `guard_member_category` / the existing category ownership trigger at 20260926000200 L79); `abs(sum) <= abs(total)` (a gap is allowed only as "left to place" in the **under** direction; an "over" can never be saved, per D-02).
**Undo:** add `category_parts` to the `transactions` allowlist inside `apply_patches` (the function has been re-created 10+ times for exactly this; latest at 20261106000100 L278 and the column list at its L387) so undo of a split is an ordinary version-checked column patch. The new RPC returns `before` and the client records the undo step the same way split changes already do. No new undo entity, no new touched-id logic.
**Category deletion:** `transactions.category_id` is `on delete set null` [VERIFIED: 20260926000200 L23]; a jsonb column has no FK. Add a `before delete` trigger on `categories` that rewrites `category_parts` elements pointing at the deleted id to `c: null` (becomes Uncategorised). pgTAP covers it.

### Pattern 3: receipts table plus private bucket
```sql
create table public.transaction_receipts (
  id uuid primary key,                       -- client-generated: idempotent retries, deterministic object path
  transaction_id uuid not null references public.transactions(id) on delete cascade,
  uploaded_by uuid not null default auth.uid() references auth.users(id) on delete cascade,
  object_path text not null unique,          -- '<line owner uid>/<transaction id>/<id>.<ext>'
  kind text not null check (kind in ('photo','file','scan')),
  mime_type text not null,
  bytes integer not null check (bytes > 0),
  page_count smallint,
  position smallint not null,
  created_at timestamptz not null default now()
);
```
Bucket: `receipts`, `public = false`, `file_size_limit` (config, recommend 10 MB), `allowed_mime_types` `{image/jpeg,image/png,image/webp,application/pdf}` (HEIC is converted on the phone). Policies on `storage.objects`:
- SELECT: `bucket_id = 'receipts'` and exists `transaction_receipts r join transactions t` where `r.object_path = name` and (`t.created_by = auth.uid()` or (`t.is_shared` and `t.household_id in (select user_household_ids())`)). This is the same visibility predicate as the `transaction_splits` select policy [VERIFIED: 20261122000600] so a private line is owner-only and a shared line reaches exactly its household.
- INSERT: path's first folder equals the line owner's id AND the second folder is a transaction the caller can edit (owner, or member of a shared line). Cap the insert path depth, as the statement bucket does [VERIFIED: 20261011000100].
- No UPDATE and no client DELETE policy: removal goes only through the RPC and purge function.
Table RLS: select = same predicate; no direct insert/update/delete grants; writes through `add_receipt` / `remove_receipt` RPCs (which enforce the count cap and the line access rule).
Note the order problem: the DB row can exist only after the object exists (the select policy joins the row) and the insert policy needs only the path. Sequence: upload object, then `add_receipt`. If `add_receipt` fails, the object is orphaned; the purge function also sweeps objects older than 1 hour with no row (mirror `stale_statement_uploads` [VERIFIED: 20261011000200]).

### Pattern 4: removal and purge are queued, never SQL deletes
A SQL `delete from storage.objects` orphans the file (the 02.1 migration says so explicitly [VERIFIED: 20261011000200]). Use a table `receipt_purge_queue(object_path text primary key, queued_at)` filled by `remove_receipt` and by a `before delete` trigger on `transaction_receipts` (covers line hard-delete cascade and the tombstone job). A `purge-receipts` Edge Function (service role, run every few minutes by `pg_cron` like `statement-uploads-purge-hourly`) removes the objects through the Storage API and deletes the queue row on success. Soft-deleting a line (deleted_at) must NOT purge: undo has to bring the receipts back; purge happens when `purge_record_tombstones` finally hard-deletes the line (D-30 pattern in 20260926000500). The UI "Its receipts are deleted too" copy is then true at the tombstone purge, which is when the line is gone for good.

### Pattern 5: offline outbox for files, separate from the 500-row queue
Receipt files are not ordinary mutations (D-09 says so). Keep a tiny persisted outbox (AsyncStorage JSON list: `receiptId, txId, localUri, mime, bytes, attempts, lastError`), files under `documentDirectory/receipts-pending/`. Drain on: app foreground, NetInfo reconnect, and after the mutation queue flushes (a line created offline has no server row yet, so its receipt must wait until the line exists). Object path derives from the client-generated `receiptId`, so a retry that gets 409/already exists is treated as success. Own cap by bytes and count (recommend 40 files / 150 MB) with a plain message; D-27's 500-row limit is not consumed. After 5 failed attempts (backoff) show "Didn't upload" (UI-SPEC). Delete the local file only after `add_receipt` succeeds. Local files must be removed on sign-out and account deletion.

### Pattern 6: item split server recompute
`set_split_by_item(p_id, p_expected_version, p_items jsonb, p_extras jsonb)` computes member shares itself: item cost per assignee by `hh_allocate(price, ones)`, member item subtotal `S_m`, then extras `E = tax + tip - discounts` by `hh_allocate(E, S_m weights)`, then `member_total = S_m + extra_m`; builds `p_amounts` for `hh_split_plan(..., 'amount', participants, amounts)` [VERIFIED: signature at 20261122000600 L285] and stores via `hh_store_splits`, sets `split_rule = 'amount'`, `split_manual = true`, writes parts from items, and `hh_event(... 'split_changed' ...)` with before/after like `set_line_split`. The client runs the **same algorithm in TS** (`itemShares.ts`) for the live preview; a parity test (same pattern as `hh_allocate` vs `allocate`) pins them together. Multi-currency: shares are in household currency; compute in the original currency then `hh_allocate(household_amount, original_currency_member_totals)` so the stored splits sum to `household_amount`.

### Anti-Patterns to Avoid
- **One transaction per part** (prototype L6514-6545): breaks bank matching, import de-dup, undo and the household split (D-01).
- **Converting each part to home currency independently:** drift; allocate the home total over the parts instead.
- **Counting both the line and its parts:** every reader must call `expandParts`; add an ESLint/test guard that greps for `\.categoryId` reads in the listed reader files (see Validation).
- **Deleting storage objects from SQL or trusting client deletes:** orphaned files, breaks D-08.
- **Signed URLs with long expiry or cached in the query cache:** persisted cache ends up on disk (AsyncStorage). Mint 60-second signed URLs on open, never persist them.
- **Sending an image online automatically** when on-device read is poor: forbidden by D-10; consent every time.
- **Floats for prices:** parse "12.50" with integer string handling into minor units using the currency exponent from the engine money module; never `parseFloat`.

## Common Pitfalls

### Pitfall 1: Readers that still read `categoryId`
**What goes wrong:** one forgotten reader counts a split line's full amount under the main category, and category totals differ between Activity, Insights and Decide.
**Why it happens:** about 12 call sites (list in CONTEXT code_context: `insights/categories.ts`, `month/model/*`, `categorize/usage.ts`, `activity/filters.ts`, `calendar.ts`, `buildInputs.ts` L119/190/218/235-254/321/561, `judge/lines.ts` L74-103, `fullCost/replaces.ts`, `householdMoney.ts`).
**How to avoid:** because `category_id` equals the largest part, an unconverted reader degrades to "full amount under the main category" rather than double counting. Still add a cross-reader invariant test: for a fixture ledger with splits, sum over categories in each reader equals total spend, and equals the same figure from `expandParts`. Convert all readers in one wave.
**Warning signs:** category totals sum to more or less than month spend.

### Pitfall 2: Savings and Transfer parts in Decide
**What goes wrong:** a part in Savings counted as spend, or a Transfer part leaks into expense totals.
**Why it happens:** `buildInputs.ts` checks builtin keys on the line; with parts, it must check per part (D-04). A Transfer part on a real transfer line (with `transfer_id`) is contradictory.
**How to avoid:** `expandParts` first, then run the builtin-key logic on each `CategoryAmount`. Block a Transfer part on a line that has `transfer_id` (validation message). Test with a Savings-part fixture through `decide()`.

### Pitfall 3: Sign convention and refunds
**What goes wrong:** refund lines (`is_refund`, positive amounts) with parts; part signs differ from the line.
**How to avoid:** parts carry the line's sign; validation rejects mixed signs; `expandParts` gap uses signed arithmetic. Property test: for any signed total and any parts with matching signs, `sum(expandParts) == total`.

### Pitfall 4: `allocate` rejects zero weights; SQL accepts them
**What goes wrong:** a person with zero items makes the TS preview throw while the server succeeds (or the reverse), breaking the live "Each person's share" card.
**How to avoid:** a thin `allocateWithZeros` wrapper in the engine (filter positive weights, allocate, re-insert zeros). If all weights are zero the line total cannot be shared: UI blocks save. Parity-test it against `hh_allocate` with the same cases.

### Pitfall 5: Item split vs the line's whole-line rule and locked lines
**What goes wrong:** per-item people overrides conflict with `split_rule` values (`even`, `weight`, `mine`) or with `hh_line_locked` (settlements).
**How to avoid:** store the result as rule `'amount'` with `split_manual = true` (so a default re-split `apply_rule_to_unsettled` leaves it alone [VERIFIED comment in 20261122000600 L14]); "Back to the usual split" calls the existing `set_line_split` with the previous rule; respect `line_locked`.

### Pitfall 6: Concurrency between two editors
**What goes wrong:** Alex and Sam both split the same line; last writer silently wins.
**How to avoid:** both RPCs take `p_expected_version` and answer `version_conflict` with `current_version`/`updated_by`; the sheet shows "Sam changed this line. Review and save again." (declarative copy). Realtime already publishes the row; `transaction_receipts` should be added to the realtime publication like `20261122000900_household_realtime_tables.sql` so a partner's new receipt appears.

### Pitfall 7: Expo Android photo permissions vs Play policy
**What goes wrong:** `expo-image-picker`'s manifest adds `CAMERA`, `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE` [CITED: docs.expo.dev/versions/v57.0.0/sdk/imagepicker]; Play's photo/video permissions policy can flag broad storage permissions.
**How to avoid:** the Android system photo picker needs no permission; add `blockedPermissions` for the storage pair in the config plugin and keep only `CAMERA`. Whether Play accepts this is a Compliance-phase check: [ASSUMED]. If the document scanner is used for scan and `launchCameraAsync` only for single photos, camera permission is still needed for the latter.

### Pitfall 8: iOS ML Kit pods and the simulator
**What goes wrong:** Google ML Kit iOS pods historically ship without arm64-simulator slices, so an iOS simulator build may fail to link.
**Why it matters:** CLAUDE.md says the iPhone XR is the certain iOS path; the simulator is a bonus. [ASSUMED] (training knowledge, not re-verified); settle in the spike once Apple enrolment allows an iOS build.
**How to avoid:** keep OCR behind a service interface (`readOnDevice(imageUri) -> OcrLine[]`) so Apple Vision can replace it later without touching the engine.

### Pitfall 9: OCR text order and column misreads
**What goes wrong:** ML Kit returns blocks in reading order, not row order; names and prices on the same printed row end up in different blocks; thousands separators and decimal commas misread; quantity lines ("2 x 1.50") split.
**How to avoid:** the parser groups lines by vertical centre (tolerance about half median line height), takes the rightmost price-like token as the row price, treats the next row without a price as a continuation of the name, and flags rows whose price is ambiguous. Ship a fixture corpus (owner supplies 20-30 receipts with personal details removed, the 10 D-24 pattern) and test the parser against OCR dumps of them.

### Pitfall 10: Date ambiguity
**What goes wrong:** "03/04/26" read as the wrong day/month.
**How to avoid:** use the account/locale date order; if both orders are valid dates, mark the date "Check this". Never default to today silently; if no date is found the line uses today and the Date row shows "Check this".

### Pitfall 11: Textract opt-out and data use
**What goes wrong:** by default AWS may store and use Textract content to improve its services; opting out needs an AWS Organizations "AI services opt-out policy" [CITED: aws.amazon.com/textract/faqs, fetched 2026-11-24: "Use of your content is necessary for continuous improvement"; opt-out via "AWS Organizations opt-out policy"; "content will not be stored in another AWS Region if you opt out"]. D-10 promises no server copy.
**How to avoid:** the owner must create an AWS Organization and attach the opt-out policy before launch; record it as a launch gate in the plan. Copy must say "deleted straight away" only about FincWin's servers unless the opt-out is in place. If the owner will not set up an AWS Organization, use the fallback service (see Open Questions).

### Pitfall 12: Supabase Free plan and storage
**What goes wrong:** project is on Free until revenue (memory: "Supabase Free until revenue"). Free plan storage is capped (1 GB total, [ASSUMED] from training), and Supabase database backups do not include Storage objects ([ASSUMED]; verify). The Phase 10 daily encrypted backup (D-19) will not cover receipts unless a separate step does.
**How to avoid:** compress aggressively (about 300-600 KB per image), cap files per line, and add an owner question on backup and quota. Recommend a monitoring query on `storage.objects` size.

### Pitfall 13: Export memory
**What goes wrong:** building one ZIP of hundreds of receipts in JS exhausts memory.
**How to avoid:** stream per file into several ZIPs capped at roughly 100 MB each (`fflate` `Zip` streaming class writing chunks to a file via `expo-file-system`), plus a `receipts.csv` (receipt id, line id, original file name, kind, date). Fetch with the user's own RLS-limited session so the export only contains what they may see.

### Parsing a price into minor units without floats
```typescript
// src/engine/receipt/amounts.ts  [pattern; verify against the money module's exponent helper]
export function parsePriceToMinor(token: string, exponent: number): number | null {
  const m = /^([-(]?)\s*[^\d-]*?(\d{1,3}(?:[.,\s]\d{3})*|\d+)(?:[.,](\d{1,3}))?\)?\s*-?$/.exec(token.trim());
  if (!m) return null;
  const negative = m[1] !== '' || /-\s*$/.test(token) || token.trim().endsWith(')');
  const whole = m[2].replace(/[.,\s]/g, '');
  const frac = (m[3] ?? '').padEnd(exponent, '0').slice(0, exponent);
  if (m[3] && m[3].length > exponent) return null;     // ambiguous grouping: caller marks Check this
  const minor = Number(whole + frac);
  return Number.isSafeInteger(minor) ? (negative ? -minor : minor) : null;
}
```

### Proportional extras (engine)
```typescript
// src/engine/receipt/itemShares.ts
export function itemShares(items: { price: number; people: string[] }[], extras: number): Map<string, number> {
  const itemTotal = new Map<string, number>();
  for (const it of items) {
    const parts = allocateWithZeros(it.price, it.people.map(() => 1)); // largest remainder, ties to lowest index
    it.people.forEach((p, i) => itemTotal.set(p, (itemTotal.get(p) ?? 0) + parts[i]));
  }
  const people = [...itemTotal.keys()];
  const extraShares = extras === 0 ? people.map(() => 0) : allocateWithZeros(extras, people.map((p) => itemTotal.get(p)!));
  return new Map(people.map((p, i) => [p, itemTotal.get(p)! + extraShares[i]]));
}
```
Sum invariant: `sum(result) === sum(item prices) + extras` (property test).

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (Edge Function caller) | Verified JWT via `userClient.auth.getUser()`, as `read-pdf-statement` and `delete-account` do |
| V3 Session Management | no change | Existing Supabase session |
| V4 Access Control | yes (core) | RLS on `transaction_receipts`; `storage.objects` policies joined to `transactions`; RPCs re-check line access, category ownership; no service role on client paths |
| V5 Input Validation | yes | SQL validation in RPCs (part count, signs, sums, categories), bucket mime/size allowlist, request size cap in `read-receipt`, path built server-side, never from client folder text |
| V6 Cryptography | no new | TLS in transit, Supabase storage encryption at rest; nothing hand-rolled |
| V8 Data Protection / Privacy | yes | No server copy online (body only, no Storage), no logging of image or text, consent every time, purge on deletion, signed URLs 60 s and never persisted in the query cache |
| V12 Files | yes | Mime allowlist, size limit, store under server-generated names, never execute or render server-side |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Reading another user's receipt by guessing a path | Information disclosure | Private bucket, select policy joins to row visibility, unguessable UUID paths |
| Member of the household reading receipts of a private line | Information disclosure | Policy requires `is_shared` for non-owners; pgTAP test |
| Uploading into someone else's line folder | Tampering | Insert policy requires path folder = line owner and caller can edit the line |
| Orphaned files after delete | Repudiation / privacy (GDPR erasure) | Purge queue + sweeper + delete-account listing from `transaction_receipts` |
| Client sends crafted parts that do not add up | Tampering | RPC validates; DB trigger re-checks sign and sum bound; never trust client `category_id` |
| Abuse of paid online reading (cost) | Denial of wallet | Auth required, per-user daily counter, request size cap, flag to switch off |
| Receipt content in logs or error trackers (Sentry) | Information disclosure | No image/text in logs; function logs counts and timings only (as `logMeta.ts` does); scrub Sentry breadcrumbs |
| OCR/vendor text injected into UI strings | Tampering | Treat as plain text; no HTML; length caps on names |
