## Deviations from Plan

1. **Migration timestamp:** 20261127000400 was already taken (split_by_item), so the migration is `20261127000500_series_category_parts.sql`; pgTAP file is 136 (135 was taken).
2. **[Rule 2] `src/db/transactions.ts`:** `fetchTransferCandidates` now adds `.is('category_parts', null)`. Otherwise an import's transfer link would patch `category_id` on a split line (the DB guard would just overwrite it with the largest part, leaving a transfer leg with parts). Split lines are no longer offered as transfer legs.
3. **Series shape/ownership check is a trigger**, not a CHECK constraint, so later series amount edits cannot be refused; the materialised lines are re-validated by the transactions guard anyway.
4. **Parts for a series** come from `p_series.category_parts` or, if absent, the anchor line's parts (so "make this split line repeat" needs no client change). No client sends `category_parts` in `p_series` yet.
5. **Clone amount:** clones always use the source amount today, so I added an optional `amountOverrides` map to `cloneCandidates` to make the scale branch real and testable.
6. When scaling a line with an unplaced gap, the gap is scaled with the parts and stays a gap (D-03), so the scaled parts then sum to less than the total. Gap-free lines add up exactly.
7. Series export manifest / apply_patches allowlist: series edits are not undone through apply_patches' transactions allowlist, so `recurring_series.category_parts` was not added there. Series editing (`edit_recurring_series_from`) does not yet accept `category_parts`; a later edit of a series keeps existing parts.
8. Import (D-29): no import path wrote parts or category on matched lines except the transfer link (fixed per item 2); the new tests pin that mark-paid patches contain only status, date and amount.
