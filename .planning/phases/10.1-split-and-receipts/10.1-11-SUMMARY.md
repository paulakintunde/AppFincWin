## Deviations from Plan

**1. [Rule 3 - Blocking] transactions_active did not expose the new columns.** The view froze its column list at 20261122000800, so every `TRANSACTION_COLUMNS` read through it would fail on the server. Added migration 20261127000300 that re-creates the view (same definition and grants) and pgTAP 134.

**2. [Rule 3 - Blocking] No client insert grant on category_parts.** 10.1-05 granted nothing, but the plan inserts a scanned line with its parts. The same migration grants `insert (category_parts)` only; updates stay RPC-only and item_split has no client grant. The guard trigger re-validates every inserted part set (134 proves a bad total is refused with PT001 and that a direct UPDATE of category_parts or item_split is refused with 42501).

**3. [Rule 3 - Blocking] PatchValue could not carry an array.** `src/engine/undo/types.ts` `PatchValue` now also allows `readonly PatchJsonObject[]`, needed for the merge patch and its undo (type-only change).

**4. [Rule 3 - Blocking] Import cycle.** StoredPart and StoredItemSplit live in rows.ts and are re-exported from categoryParts.ts.

**5. [Rule 1 - Bug] Existing tests pinned the old state.** persister.test.ts asserted cache version 19 (now 20); pgTAP 101's export-tables marker block lacked transaction_receipts (added, covered by 132); the fetchActiveIdsByCategory test now expects the `or` filter and the added select column.

**6.** householdSharing.ts now exports `patchLine`, `refreshAfterLineWrite` and `handleFailure` so the parts mutation reuses them (no behaviour change).
