## Summary

All six requests sit on existing, well-factored seams, and no new dependency is needed. The riskiest piece is REC-27's server side: categories have no `kind` column, `apply_patches` / `undo_log_fill` / `undo_replay` hard-code an entity allow-list in SQL (so "normal undo/history" for rules means a third full copy of those functions in a new migration), and rules must be household-scoped yet resolve per member. The second risk is the 817-line `TransactionSheet.tsx`: REC-28/29/30 all land there, so the bulk-list logic must be extracted into pure modules and a hook rather than grown in place. REC-26 is mostly orchestration: `goReview` already loads settled `existing` rows for the target account in `[first-2, last+2]` and `buildPreview` already runs `findDuplicates`, so reconcile "missing" and "extras" are both derivable from the same inputs with one new pure function and no change to duplicate rules. ACC-14 is small but has a native-behaviour subtlety: `performSignOut` only does `supabase.auth.signOut({scope:'local'})`, so the native Google session stays cached, which is exactly what makes `signInSilently` work for "Continue as".

**Primary recommendation:** Build schema first (rules table + undo extension + pgTAP), then pure engine (precedence, shared-rule resolution, `findExtras`, bulk draft model), then data layer, then UI; extract bulk-entry logic out of `TransactionSheet.tsx`; keep the one `[ASSUMED]`-heavy area (Google chooser/silent behaviour per platform) behind a thin service wrapper that is verified on the iPhone XR and Android in the final walkthrough.

### Pattern 1: Rules table design (D-24..D-27)
One table `public.category_rules`:
- `id uuid pk` (client-minted), `scope text check in ('personal','shared')`, `owner_id uuid not null default auth.uid() references auth.users on delete cascade` (creator; for personal = owner), `household_id uuid references households on delete cascade` (not null when shared, null when personal; check constraint ties scope to it).
- `keyword text not null check (char_length(btrim(keyword)) between 1 and 60)`; store the user's text and a generated/normalised `keyword_norm` computed **client-side with `normaliseDescription`** and checked by a length constraint (do not re-implement NFD in SQL; the client writes both, server only bounds length).
- Target: personal rules `category_id uuid references categories(id) on delete cascade` (D-26: "personal rules point at the user's own category id"). Shared rules `target_builtin_key text` XOR `target_name text` (see Open Question 1: categories have **no `kind` column**; derive "kind" as built-in key vs custom name, so "Groceries (expense)" = builtin_key `Groceries`; "Income" is the only income builtin).
- `deleted_at timestamptz` (soft delete; required so undo of an add = soft-delete patch, matching `inverseOfInserts`), `version int default 1` with the existing `bump_version` trigger, `updated_by` with `set_updated_by` trigger (gives "who changed what"), `created_at`, `updated_at`.
- `updated_by`/creator FKs `on delete set null` for shared rules so a departing member does not cascade-delete household rules (mirror transactions/`created_by`; see 36_account_deletion test: non-owner deletion leaves household data). Personal rules cascade with the user. [VERIFIED: pattern in 20260926000100_categories.sql, 36_account_deletion.test.sql]
- RLS: select where `(scope='personal' and owner_id = auth.uid()) or (scope='shared' and household_id in (select public.user_household_ids()))`. Insert/update with matching `with check`; shared insert also requires `household_id in user_household_ids()`. Grants follow the categories/import_profiles shape: `revoke all from anon; revoke insert, update, delete from authenticated; grant select; grant insert (id, scope, household_id, keyword, keyword_norm, category_id, target_builtin_key, target_name); grant update (keyword, keyword_norm, category_id, target_builtin_key, target_name, deleted_at)`. `scope`/`household_id` immutable (guard trigger pins them, like `guard_category`).
- Helper: `public.user_household_ids()` is the existing membership helper (security definer, `20260922000100_household_of_one.sql`; used by accounts, transactions, import_profiles policies). [VERIFIED: grep]

**Undo/history integration (D-24 says through normal undo):** `apply_patches`, `undo_log_fill` and `undo_replay` hold hard-coded entity lists (`'transactions','categories','recurring_series','accounts'`, plus `households` for system steps) and a per-column type `case`. Adding `category_rules` requires a new migration that re-creates all three functions in full (the project's established method; 20261010000200 header says "copied in full ... changed only where marked") with: entity added to the three lists; `v_allowed` entry `array['keyword','keyword_norm','category_id','target_builtin_key','target_name','deleted_at']`; type-case entries; a scope check branch (personal: `owner_id = auth.uid()`; shared: `household_id in user_household_ids()`); conflict report `record_name` = keyword. Also TS: add `'category_rules'` to `UndoEntity` (`src/engine/undo/types.ts`), `WriteEntity` (`src/db/errors.ts`), new label keys (`ruleAdded`, `ruleEdited`, `ruleRemoved`, and `addedMany` for REC-30) in `UNDO_LABEL_KEYS` + `src/i18n/locales/en.ts` + `undoCopy.ts`. `label_key` is only regex-checked in SQL (`^[a-zA-Z]{1,40}$`), so no SQL change is needed for labels. [VERIFIED: 20260926000500_undo_log.sql:31, 20261010000200_record_polish_patches.sql]
**Do this in its own plan and run the existing undo pgTAP files (35, 37, 44, 45) afterwards**: a regression in the copied functions breaks undo for all of Record. If the planner judges the third function copy too risky, the only fallback is direct CRUD with `updated_by` attribution and no Undo for rules, which contradicts D-24 and needs user confirmation. Recommendation: do it as specified.

### Pattern 3: Reconcile mode (REC-26)
- **Where:** insert stage `'choose-mode'` into `ImportStage` (`useStatementImport.ts:87`). ## Common Pitfalls

### Pitfall 1: Keyword first-occurrence bug in `matchKeywords`
**What goes wrong:** `normalised.indexOf(rule.keyword)` checks word boundaries only at the *first* occurrence. "business bus stop" for keyword `bus`: first hit is inside "business" (part-word), so a later whole-word `bus` is missed and ranked as part-word. User rules (D-09 "whole-word beats part-word") would inherit this.
**How to avoid:** When generalising, scan all occurrences (`indexOf` loop) and mark whole-word if any occurrence is whole. Add a regression test. This changes built-in ranking only in the buggy case; confirm existing tests still pass.

### Pitfall 2: `apply_patches` allow-list drift
**What goes wrong:** Adding `category_rules` to the table/RLS but missing one of the three function lists (undo_log_fill validation, apply_patches entity list, v_allowed, v_col_type case, scope branch, undo_replay) -> Undo of a rule silently refused or errors `22023`.
**How to avoid:** One pgTAP file proving: add/edit/remove rule via patches for personal and shared; second household member can patch a shared rule but not another user's personal rule; non-member cannot; undo of add soft-deletes; undo of edit restores; cross-household denied. (RESEARCH Pitfall 2 from 02.2 is the same trap.)

### Pitfall 3: Android `keyboardDidHide` re-opening the pad
**What goes wrong:** Today `keyboardDidHide` sets `activeField='amount'`; with REC-28 that re-opens the pad after every text edit. **How to avoid:** introduce `'none'` and test on the Android emulator and iPhone XR.

### Pitfall 4: Optimistic transfer rows
`insertRowsAsOneStep`'s `optimisticRow` nulls `transfer_id`. Bulk transfers would appear as two unrelated rows (possibly double-counted in totals) until refetch. Fix in `batchInsert.ts` and test.

### Pitfall 5: Silent Google sign-in returning a different user
See Pattern 5 mismatch guard.

### Pitfall 6: Draft staleness
Draft references account/category ids that may have been deleted/archived, or currencies changed. Revalidate on restore; drop invalid items with a note (declarative copy). Draft key includes user+household so a different user on the same device never sees it; sign-out wipes it.

### Pitfall 7: `kind` does not exist on categories
D-26 says "by name and kind"; the `categories` table has only `builtin_key`, `name`, `color_key`. See Open Question 1.

### Pitfall 8: Shared rule hard-delete vs undo
RLS grants no delete; remove = soft delete (`deleted_at`) so Undo works and "who removed" stays visible. Queries must filter `deleted_at is null`.

### Pitfall 9: Wave 0 coverage config
`jest.config.js` only adds 100% thresholds for folders in its hard-coded list and only if the folder has source. New `src/engine/entryList` must be added to that list or it silently falls under the 95% `engine/` bucket. `src/engine/categorize` and `src/engine/statement` already 100%: new code in them needs full branch coverage.

### Pitfall 10: Copy voice
Never "advice/recommend/you should" in new copy (the voice test guards `en.ts`). The phrasing "Always use Groceries for Tesco?" and "This statement overlaps 24 lines you already have" are declarative/neutral; keep that register for the cap note ("30 money out entries are in the list").
