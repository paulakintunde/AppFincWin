## Top 5 by user harm

1. **F-1, plus waivers never reaching the engine (C-1, C-2).** A user who has records but is "not ready" never gets an answer.
   - "Answer from quick estimates" loops back to the same card. Reproduced again today: Concert tickets $150 > quick estimates 3000/1200/800 > Not ready yet again.
   - No code passes `waivers` or `skipped` to the engine, so no waiver can clear anything either.
   - The card names whole categories ("Some envelopes or goals aren't linked…"), never the item that is missing, and setup has no step that fixes envelopes.
2. **The JS thread is busy for 15 to 30 s on most Decide actions (B-1).**
   - Check it to the answer: 35 s, with the JS thread busy 30.7 s of that.
   - Stepper Next (step 2 to 3): 18 s before anything changes on screen, JS busy 30 s.
   - Opening a setup item: 18 s, JS busy 19 s.
   - The engine's own `judgeCheck` takes only 3.8 ms (p50) on the device harness. The cost is repeated snapshot, prepare and rebuild across about 8 hooks per screen, re-run on every cache change.
3. **Writes take 40 to 52 s to reach the server on a warm emulator (F-2 confirmed as the app).**
   - The host reaches Supabase in about 150 ms.
   - The JS thread is saturated while the write waits, so the request and its reply queue behind the rebuilds.
   - Every write triggers another round of rebuilds, which makes it worse.
4. **Answer screen: Back and "New check" sit under the status bar and do not respond (A-ANS-1).**
   - `AnswerFrame` has no top inset. The Back button spans y 58 to 173 px, and the status bar covers y 0 to 132 px.
   - Two taps on Back did nothing. Only the system Back gesture leaves the screen.
5. **Setup Pay never ticks (C-3), and setup Back needs several presses (C-6).**
   - After saving pay ($3,000, day 15, About the same), Pay still shows "Not done yet" after the server write finished. The cause is that `income_types` is never written.
   - Each item saves with `router.replace('/decide/setup')`, which stacks another copy of the checklist. Back then looks broken, and the checklist has no Back control of its own.

**Other observations:**
- **ANR:** typing fast into "What is it?" made the UI thread stop responding for over 5 s ("Input dispatching timed out", "Skipped 68 frames", "Davey! 1258 ms"). Android showed "App not responding" and the process was killed (23:18 UTC). The input was synthetic (rapid deletes), but it shows a high per-keystroke cost on Decide home.
- **GC:** while Decide is open, Android logs a garbage collection about every 1.5 s that frees 15 to 42 MB, which means heavy object churn.
- **Cold start** to Home content took 118 s, but that includes the dev bundle loading from Metro, so it is not representative.

**Conclusion.** The slowness is the JS thread, not the network and not the engine's judge.
- One `judgeCheck` takes milliseconds.
- Each user action keeps the JS thread busy for 5 to 30 s.
- Pushing a route that has no Decide hooks still took 21.6 s. So the work is the mounted Decide screens (the tab stays mounted under pushed routes) rebuilding when navigation or a cache change happens.

### F-2 rechecked on a warm emulator: reproduced, and the app is the cause

The emulator had been up for more than 2 hours. Write latency, from `[persist] mutations=1` to `mutations=0` in logcat:

| Write | Took |
|---|---|
| Check create (Concert tickets) | about 45 s (22:35:06 → 22:35:51) |
| Quick estimates save | 52.3 s (22:40:16.1 → 22:41:08.4) |
| Check create (Headphones) | 40.6 s (22:49:43.9 → 22:50:24.6) |
| Pay setup (2 writes) | 26 s and 43 s |

- The host reaches the Supabase REST endpoint in 0.14 to 0.21 s.
- During the Headphones write the JS thread was busy 30.7 s of 35 s.
- **Most likely cause:** every write triggers B-1 and B-2 rebuilds on a saturated JS thread, so the request start, its reply and the mutation's resolve all wait in the JS queue. Then the 20 s write timeout (`src/services/supabase/timeoutFetch.ts`) and unlimited connection retries with backoff (writeErrors 1/2/4/8/12 s) can each add 20 s or more.
- Also: one write queue for the whole app (`WRITE_SCOPE`, `src/data/keys.ts:206`), so writes run strictly one after another.
- **Not verified:** when each request reached the server. The Management API `logs.all` endpoint is retired, and the new `/analytics/endpoints/logs` rejected the `edge_logs` table name. A plan should add a Sentry breadcrumb with request start and end times to settle it.

## D. Wordiness: one short line, details behind "Why?" or "More"
