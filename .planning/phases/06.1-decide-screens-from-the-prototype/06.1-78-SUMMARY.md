# Phase 06.1 Plan 78: Check it and Edit the check land on the check (H-15) Summary

DN-1 and DN-2 were not a navigation bug in the app. They were full JS reloads of the emulator's dev build. Another plan was
saving source files in the same checkout that Metro was serving, and each reload restarted the app at its first tab (Home)
with a fresh Decide home. A controlled save of a locale file reproduced it on the emulator: 15 s after the save the app was on
Overview, and Decide home's typed form was gone. The tabs layout itself stays mounted through every loading and refetch flip
(new regression test). The plan still hardens the paths it names: the Tabs get Screen elements only (the logcat warning is
gone), a same-frame double tap on Check it makes one check, and Edit the check routes once. Three routed items are also in:
furthest_step now moves forward, the answer stores what it showed so open checks leave Draft, and the record-context and
savings-goal reads keep Decide's five-minute freshness (G-72-2).

## Cause note (Task 1, measured before any fix)

**Set-up.** emulator-5554 (Pixel_8_API_36), dev build, Metro from `C:\dev\fincwin-ds` on :8081, restarted with `--clear`
(the old Metro answered the manifest with `runtimeversion:resolve ... exited with code 3221225794`, so the dev client could
not load at all). Temporary logs, removed before the Task 2 commit (`git grep TEMP78` is empty): a TabsLayout mount and
unmount counter, a TabsLayout render line (gate, `rc.ready`, accounts loading/fetching/count), the root navigation state
from `useRootNavigationState` (key, index and route names per level), the root Gate's route, `useConsent` loading, Decide
home mount and unmount (through useNewCheck), and the href of every Check it and open-check sheet push.

**Evidence.**

   `C:\dev\fincwin-ds` at 5c02582d", while plans 52 and 62 were changing files in that same checkout. Its shot times line up
   with those plans' work:

     6ed3da21 at 22:10:27, changed `src/i18n/locales/en.ts`, `src/i18n/locales/decideScreens/common.ts`,

     110969ms"), and the app showed the same blank white screen while it ran.
2. **Controlled reproduction.** With Decide home open and the Used car example typed in, a one-line comment was appended to

   Refresh cannot take the change in place and reloads the whole app. Two more reloads happened during this run, set off by
   saves in this checkout (`tabs UNMOUNT/MOUNT` at 1794584354047 and 1794584358650; `gate splash` at 1794584403337), and
   both times the navigation state came back as `(tabs) > tab[0/4] home`.
3. **The tabs layout does not remount from cache changes.** Across the whole session, `tabs MOUNT` and `UNMOUNT` lines appear

The audit's "no check was made" also fits: the reload cut the tap off before `create` ran, or before its optimistic row went
into the persisted cache. "The second try worked" fits too, because nothing was being saved at that moment.

**What this means for the rechecks.** A release or preview build has no Fast Refresh, so DN-1 and DN-2 should not happen on
the Pixel 6 preview build (06.1-74's P1 recheck). Emulator walks and Maestro proof runs need a Metro that serves a checkout
nobody is editing, or a frozen worktree like plan 72's. Otherwise any save can reload the app mid-tap.

## What changed (Task 2 and the routed items)

1. **Tabs layout** (`app/(app)/(tabs)/_layout.tsx`): the Screen list is built once at module level, with no null child.
   `grep -c "? null :"` is 0. The logcat "Layout children must be of type Screen … (tabs)/_layout" no longer appears (test).
   The gate, `backBehavior="none"`, freezeOnBlur, the tab bar and the Profiler and DecideV3Scope wrappers are unchanged.
2. **Check it** (`useNewCheck`): a ref guard sits next to the `pending` state. Two taps in the same frame both read
   `pending === false` from the same render, so each one made a check and pushed a route (T-06.1-78-01). The draft is still
   written (optimistically, so it works offline) before the full outer-stack href is pushed.
3. **Open-check sheet** (`OpenCheckSheet`): Edit the check, See today's answer and Save for it go through `pushOnce`. A second
   tap while the sheet closes is dropped. A ref guard was tried first, but the React Compiler lint (`react-hooks/refs`)
   rejects ref reads in closures that `actionRow` gets during render.
4. **furthest_step** (`useStepCheck`): the new `furthestStepOf(stored, check)` returns the largest of the stored step and
   `L0.visited_steps`, kept between 1 and 3. The draft flush writes that value, not `current.furthest_step`. The column only
   moves forward. 53's `editTarget` workaround still works and now agrees with the column.
5. **Open checks leave Draft** (`useAnswerEffects`, `AnswerScreen`): the answer calls `useSaveCheckAnswer().save(row,
   seenOf(result))` once per (check, shown answer), keyed by the check id and the seen JSON. An ask (`needs_input`), a
   not-ready answer and a loading answer are not stored. `save` skips a write when the stored answer is already the same. It
   uses the existing `saveCheckAnswer` mutation defaults (version chain, write scope, conflict handling). There is no schema
   change. One effect: "Changed since you looked" now compares with the last answer the user was shown.
6. **G-72-2** (`decideStale.ts`, `decideV3.ts`, `moneyPrefs.ts`, `recordPrefs.ts`, `growGoals.ts`, `useRecordContext.ts`):
   - `DecideV3Scope` provides `DECIDE_READ_STALE_MS` through the new `DecideReadStaleContext`, and the scope's own reads are
     inside the provider too.
   - `useRecordContext` passes it to money prefs, record prefs, the household horizon and sample-exists.
   - `useSavingsGoalRows` takes an optional `staleTime`, which the first-answer gate and the envelope account sheet (the
     answer's two goal reads) pass.
   - Outside a Decide screen the context is undefined, and the app default (60 s) applies.
   - A write's invalidation still refetches each key at once (`decideReadStale.test.tsx`).

## Device runs (decide-check-lands.yaml, emulator-5554, dev build, Metro :8081)

Each run has five rounds. Every round makes a small check (the answer must name it), uses the Used car example with Check it
("Step 2 of 3" must show), opens Edit the check on a Used car draft (a step must show), and deletes the round's two checks.
Counts come from each run's maestro.log. No Metro rebundle or reload happened during runs A, B or C, and nothing was
committed in the checkout while they ran. Runs A and B used the flow before the short-swipe change for the example chip; run C
used the committed flow.

**Result: 3 of 3 runs passed, 15 of 15 Check it to the stepper, 15 of 15 Edit the check to a step.** No run landed on another tab, and the app was never sent to Home.

Earlier attempts failed, each for a reason in the flow or the emulator, never DN-1 or DN-2. They led to the flow fixes in
deviation 6:
- A Back on a slow start left the app.
- The Used car chip was off screen.
- `check-what` was off screen, because Decide home keeps its scroll position.
- The shared to-tabs pressed Back blindly while a closing sheet hid the tab bar, and left the app.
- **Once, the open-check sheet lost its panel and left an invisible backdrop over the screen** (G-78-2 below), so the Edit
  the check tap fell on the backdrop.

That last one was reproduced by hand on the same emulator. A Used car row was tapped and the sheet showed. Within 4 s the
hierarchy held only `sheet-gesture-root` and `sheet-backdrop` ("Close", full screen). The screenshot showed Decide home with
no dim and no panel, and the app was idle (6 % CPU). Android Back cleared it. A second try a minute later opened the sheet
normally, and Edit the check opened "Step 2 of 3" in 8 s.

Also seen: on this account every lamp78 answer was "Not ready yet", so the new answer store was not exercised on the
device. Not-ready answers are deliberately not stored, and the stored-answer path is covered by the unit and screen tests.

## Deviations from Plan

1. **[Rule 3 - Blocking] Metro restarted.** The running Metro (from C:\dev\fincwin-ds) could not resolve the runtime version
   (`exited with code 3221225794`), so the dev client showed "There was a problem loading the project". It was stopped and
   restarted with `--clear` on :8081 from the same checkout.
2. **[Cause outside the plan's file list] No layout file needed a fix for the cause.** The confirmed cause is a dev-only
   reload from parallel file saves. app/(app)/_layout.tsx and checkHref.ts (plan 64's files) are not involved, so there is no
   gap row for them. A process gap row for 06.1-74 is below.
3. **Routed items outside the plan's file list (orchestrator):** useStepCheck.ts (plan 64's file this wave) changed in one
   surgical spot (the flush's `furthestStep` plus a helper). Also changed: useAnswerEffects.ts, AnswerScreen.tsx (2 lines),
   answerScreen.test.tsx (mock and 1 test), and the G-72-2 files.
4. **The gate keeps its current rule.** The plan asked for "a loading flip after the first settled render keeps the last
   decision". needsFirstAccount already returns false while loading or on error, and the stability test proves the navigator
   stays. Adding held state would change nothing the test can see, so it was not added.
5. **Check it still pushes right after the optimistic create, without waiting for a server row.** The plan said "navigate
   only after the check row exists". The stepper and the answer read the pending optimistic row (06.1-52, `fallbackRow` and
   `pendingRows`), and waiting for the server would break offline Check it. The test checks that `create` runs before `push`.
6. **decide-check-lands.yaml was fixed during the runs.** It now waits for the tab bar before the first Back (on a slow start,
   a Back press left the app), and it looks above and below for the Used car example chip, because Decide home keeps its
   scroll position.
7. **Worktree guard.** C:\dev\fincwin-ds is a manual worktree on `feat/06.1-decide-screens`, not a `worktree-agent-*`
   branch. The orchestrator named this branch, so commits went there by explicit path.
