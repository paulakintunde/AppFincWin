# Phase 06.1 Plan 84: release-blocking device-pass problems Summary

A sheet now commits its open position to React once its slide ends, so a panel can no longer vanish after a screen change.
Spare money is confirmed on the answer itself. A replayed Decide history write no longer shows as a failed change. Two small
screen-reader fixes are in too. No engine change. CACHE_SCHEMA_VERSION stays '9'.

## What was done

| Item | Root cause | Fix | Tests |
|---|---|---|---|
| **G-61-1** sheet opened during a screen change shows only its backdrop | The open slide and the dim lived only in Reanimated's props registry. React kept committing the first render's animated style: the closed position (translateY = window height, dim opacity 0). Reanimated 4.5.1 (`FORCE_REACT_RENDER_FOR_SETTLED_ANIMATIONS`) returns settled values to React from a 500 ms JS interval. `getSettledUpdates` first **deletes** entries older than 2 s, then collects those older than 1 s. A JS thread busy for about 1.5 s right after the slide drops the open values without React getting them. A Decide screen mounting and running its reads is that kind of stall. The next React commit of the panel then moved it below the screen and set the dim to 0, and it stayed that way. This matches the dumps: only `sheet-gesture-root` and `sheet-backdrop` were there. `sheet-backdrop-fill` was missing too, because UiAutomator drops views with alpha 0. It was seen only when opened as part of a screen change, and stayed for 20 s and more. 06.1-81's onLayout re-issue did not help: Fabric's onLayout fires before mount, and the problem is the lost sync, not the frames. | `Sheet.tsx`: when a slide to rest finishes (the `withTiming` callback, `finished`), the sheet sets `atRest`. The panel then commits `translateY: 0` and the dim commits `BACKDROP_OPACITY` as plain styles after the animated style. Reanimated's live values (a drag) still apply on top. Before the slide ends, React still commits the closed position, so nothing flashes. An open counter ignores a slide end that comes from an earlier open. The open slide, Keep editing and the first-layout re-issue all report it. | `Sheet.screenChange.test.tsx` (3): React commits closed before the slide ends; after a 5 s stall, `layOutSheets()` and a re-render of the screen under the sheet, the committed panel is at 0 with its dim, the backdrop takes taps and a press inside lands; a drag still moves the panel. All 11 Sheet suites pass (61 tests). |
| **G-61-2** "Your spare money hasn't been confirmed yet" can never be answered | The readiness item reads `decide_settings.unspent_anchor` (+ `_at`). The only screen that wrote it was the old Unspent step, deleted with the old Decide screens in 06.1-36. The Fix went to Records, which has no such control. | The Fix (and Give it more to go on, through the same handler) opens the new `SpareMoneySheet` on the answer. It shows the engine's own figure (`unspentSum(inputs, month).total`, worked out only while the sheet is open), with **That’s right** or **Use my own figure** (MoneyInput, 0 up to MAX_INPUT_MINOR) → **Use this figure**. Saving writes `unspent_anchor = figure + heldBack` and `unspent_anchor_at = today` through `useSaveSetupStep`, with the existing `unspentConfirmed` undo label, a toast with Undo and a light haptic. The engine reads it on the next run. `FIX_ROUTE` no longer sends it to Records. | answerScreen.test (2): Fix opens the sheet (no push) and That’s right saves the engine figure plus heldBack with today; the person's own figure is saved instead. |
| **G-61-12** "An item with the same details already exists." on a write that landed | The entry was labelled "Change", and the only failed-write entity without a label was `decide_check_history`. Its only unique key is the client id (no other unique constraint in 20261111000100), so a 23505 is the same row landing again: a retried request whose response was lost, or a paused write resumed. `insertCheckHistory` was the one Decide insert with no CR-A03 read-back, so the replay was recorded as failed and Home showed it in red. The mutation's own comment already said a replay is not a failure. | `insertCheckHistory`: on 23505 it reads the row by id and returns it as success. With no row it still throws. `failedWriteLabels` now names `decide_check_history` ("Decide history", an existing string) instead of "Change". | decideCheckHistory.test (2), failedWriteLabels.test (1) |
| **G-61-6** cleared price field loses "Price" | RN Android `BaseViewManager.setAccessibilityValue(null)` calls `setContentDescription(null)` and does not rebuild it from the label | `MoneyInput` always sends `accessibilityValue={{ text: spoken ?? '' }}`. The empty text goes through `updateViewContentDescription`, which keeps the label. | MoneyInput.test: type "5" then clear, so the label stays and the value is `{ text: '' }` (2 older asserts updated) |
