## Root cause of "Back from step 2 goes to Decide home" (A-ST-3)

The reproduction test (home opens step 2 directly; press Back) passes on code this plan did not change: the on-screen Back already replaced to step 1 with `dir: 'back'`, and KindStep does not auto-skip when `dir` is `back`. The path that does go home is the **Android system Back**: the steps replace one another, so the stack under any step is Decide home, and the app-wide `AndroidBackHandler` sees an outer-area screen and calls `stackBack`, which pops straight to home. The same applied to Back from the answer, which also replaced the step. Fix: StepFrame registers its own `hardwareBackPress` listener while focused (`useFocusEffect`), calling the step's `onBack` and returning true; RN calls the newest listener first, so it runs before the app-wide one. Being focus-scoped, a step left mounted under the pushed answer does not catch the answer's Back.

**2. [Rule 1 - Bug] A step kept under the pushed answer would hold a stale copy of the check**
- **Found during:** Task 2
- **Issue:** with the answer pushed, the step stays mounted. `useStepCheck` keeps its own edited copy, so after the answer changed the pay mode or date, Back would show the old copy and the next step edit would overwrite the answer's change.
- **Fix:** `useStepCheck` drops its local copy (`latest`, `edited`) whenever the stored check changes and no edit is held. Saves patch the cache optimistically (`useSaveCheckDraft.onMutate`), so a just-flushed edit is already in the stored row. Test proved to fail without the fix.
- **Files modified:** useStepCheck.ts (not in the plan's file list), stepper.test.tsx
- **Commit:** 400586ba

- **Commit:** 400586ba
