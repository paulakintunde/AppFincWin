# Phase 06.1 Plan 47: Deferred Decide typing, once-only answer work, shared links read Summary

Typing in Decide home or the stepper no longer runs the engine or the home parser on the keystroke's own render: the shown verdict and the home previews follow deferred values, the answer's pay-day list is built once per Prepared and check, Past decisions reuse useDecideV3's links query, and a Maestro flow prints the four device timings plan 51 checks on the Pixel 6.

## What was built

**Task 1 (B-6, B-7, B-2), commit f9ea7550**
- `useCheckEngine`: `evaluation` judges `useDeferredValue(judged)`. `both`, `judgeOn`, `timeline` and `readyDate` keep the live check (they run on demand). `futures` reads the deferred check so it matches the evaluation it extends. The CheckEngine interface is unchanged.
- `paydays()` goes through `paydaysOf(prepared, judged)`, a module WeakMap keyed on the Prepared and the judged check objects. Repeated calls return the same array and walk `cashTimeline` once.
- `perfMark('decide.answer:end')` fires the first time an evaluation is non-null for a check id.
- `useAnswerEffects` already kept a `done` ref keyed `${id}|${code}|${variant}`, so markSeen and recordHistory already ran once per verdict. New test: 5 re-renders with new-but-equal results and new `writes` objects give one markSeen, one recordHistory and one analytics event. A changed code writes again, once. Nothing is written while loading.
- Tests: deferred verdict settles on the last typed price and equals a direct judge on the same Prepared; `paydays` is `toBe`-stable across calls and re-renders, with `cashTimeline` called once.

**Task 2 (B-6 / ANR on home typing), commit d78bf53b**
- `DecideHome`: `deferredText = useDeferredValue(text)`, `deferredPrice = useDeferredValue(price)`. `parsed` (parseQuick), the Reads as line, the tax note and the `draft` passed to the date and plan sheets use the deferred values. The TextInputs, `home`, `kind`, `ready` and Check it (`newCheck.start(fields)`) use the live values.
- `perfMark('decide.answer:start')` in the Check it handler.
- Test: 20 keystrokes inside one act parse fewer than 20 times, the last parse sees the full text, the field shows it live, and Check it receives the full typed text.
- `.maestro/decide-timing.yaml` (two documents, appId com.fincwin.app) prints:
  - `checkit_answer`: headphones 180, Check it until the not-ready card or the verdict card (`answer-not-ready|answer-verdict`). It is marked `gated` if the intro or safety-net card shows first. That card is then passed with common/decide-gate.yaml.
  - `write_settle`: the same start until `answer-notice-unsaved_changes` is not visible (90 s wait).
  - `stepper_next`: used car 9000, step 2, Next until "Step 3 of 3".
  - `setup_pay`: `fincwin://decide/setup`, tap `setup-row-pay`, until `setup-item-frame` and "Pay and payday" show.
  - Loose ceilings: 15 s, 30 s, 8 s, 8 s. Typing uses common/decide-type-check.yaml and scrolling uses common/scroll-to.yaml. There is no hideKeyboard and no scrollUntilVisible.
- I checked the flow's syntax only. I did not run it on any device or emulator (plan 51 runs it).

**Task 3 (B-8), commit afe3e80e**
- `usePastDecisions` calls `useDecideLinks` with all live check ids, sorted, exactly as `useDecideV3` builds them. Both now share one cached query. The decided checks' links are filtered in memory, so the output is unchanged.
- `useHomeFacts.ts` needed no change. It has no chained reads of its own. `usePastCount` rides on `usePastDecisions`, so it gets the shared key too.
- Test (`pastReads.test.tsx`, real QueryClient, mocked db fetchers):
  - With useDecideV3 and usePastDecisions mounted together, the links network fetch runs once (`toHaveBeenCalledTimes(1)`) with `['c-bought','c-open','c-passed']`.
  - Only the decided checks' links are kept, newest decision first.
  - Checks and savings goals are both `fetching` on the first render.

### Reads: chained vs. together (B-8)

| Read | Waits on | Why |
|---|---|---|
| decide_checks, savings_goals, fx_latest, custom_currencies | nothing | already enabled on user/household only; start on the first render together |
| decide_links | decide_checks (its ids) | truly needs the check ids. Now uses useDecideV3's key, so on Decide (where useDecideV3 is already mounted) it is a cache hit, not a second round trip |
| linked lines (`past-decisions`) | decide_links | needs the target ids from the links |
| goal lines | savings_goals + decisions | needs the waiting goals' ids |

Before this plan, Past decisions used a second links key (decided ids only), which needed its own fetch after the checks arrived. There was no `enabled: Boolean(previous.data)` chain between independent reads to remove.

## Deviations from Plan

**1. [Rule 1 - Lint/correctness] paydays cache moved out of the hook**
- **Found during:** Task 1
- **Issue:** A closure cache inside `useMemo` fails `react-hooks/immutability`. An eager `useMemo` array would walk the cash path on every stepper keystroke, which is the cost B-6 removes.
- **Fix:** A module-level `paydaysOf` with a WeakMap keyed on the Prepared and the check. `paydays` stays `() => readonly LocalDate[]`.
- **Commit:** f9ea7550

**2. useAnswerEffects not changed**
- The once-only ref was already there (signature `id|code|variant`, with 'none' for no variant). Only the test was added. The file stays out of the commit.

**3. checkit_answer and write_settle start as Check it returns**
- common/decide-type-check.yaml taps Check it as its last step, and the plan asks the flow to type through it. So the clock starts when that subflow returns, not just before the tap. The figure slightly undercounts (Maestro waits for the tap to settle). This is noted in the flow header for plan 51.

**4. The B-6 home test cannot fail on its own**
- All 20 keystrokes run in one act, so React batches them. The "fewer than 20 parses" assertion would also pass without useDeferredValue. Deferral is covered by the code and the acceptance grep. The real responsiveness check is the Pixel 6 run in plan 51.
