## Summary

The most important finding is that **today's tester Decide screens do not run the v3 engine**. The check flow, home, quick check and past decisions import the old engine (`@/engine/decide`: `decide()`, `prepareContext`, `computeCheck`) and the old `SnapshotResult` shape. `DECIDE_V3 = true` (PR #98) only changes `decideEngine()`, which setup, settings and the shadow host read. `useDecideV3` and `computeV3` are not called by any check or home screen [VERIFIED: grep of `useDecideV3|computeV3|resultForCheck` in `src/features/decide` finds only setup, settings, shadow and `snapshot/v3`]. So 06.1 is the first time any user-facing check calls `judgeCheck`/`evaluate`, which means the whole `Result` to words path (facts, notices, caveats, basis, options, afterBuy) must be built as a production renderer. Only a test-side reference exists (`sayLine` in `src/engine/decide/v3/__tests__/reviewed/page.ts`).

The second finding is that **05.5 has not started** (`.planning/phases/05.5-one-shared-money-model/` holds only `.gitkeep`). No month-picture reader, no new snapshot builder and no old-engine deletion exist. 06.1 therefore keeps using the tangled path `useDecideSnapshot()` -> `buildDecideSnapshot` -> `buildV3Inputs` -> `prepare` (`src/features/decide/snapshot/v3/computeV3.ts`: `preparedV3`, `computeV3`), and Grow plan 06-10 edits `buildV3Inputs.ts` and `settingsSource.ts` to read Grow's connection points. The engine barrel exports `homeFigure` and `monthAfterPlans` but not the three D-57 account figures, so 06.1 builds a small pure month-picture function in the engine to the 05.5 contract shape.

Third, **Grow's data model conflicts with Decide's unlock (D-14, D51, D52)**: Grow forces `locked = true` on the safety-net goal in the database (`check (not is_safety_net or ... locked)` plus a guard trigger) and `safetyNetInputsOf()` always returns `locked: true`. Decide's unlock-for-answers state therefore has no home once the interim `decide_settings.safety_net_locked` column is migrated and abandoned. This needs a decision (Q1 below). Several other prototype features (quick-estimate lines D41, "Not set yet" and "No other debts" confirmations, "What Decide said on {date}" history, intro-card acknowledgement) also lack a store or an engine input (see Persistence).

**Primary recommendation:** Build 06.1 as five waves on one new folder: (0) tokens, copy, pure helpers and the engine gaps (`parseCheckV2` round trip, month picture), which can run before Grow merges; (1) the engine-facing hook and answer renderer; (2) home, stepper and answers; (3) setup, sheets and past decisions; (4) deletion of the old screens, Maestro, wording sign-off and release. Resolve Q1-Q4 with the owner before wave 1.

### Pattern 1: One prepare, many judges
`preparedV3(source, v3)` caches `Prepared` per source identity (WeakMap, 4 variants). `computeV3(source, v3, storedInputs, uses, checkId)` returns the `Evaluation` for one check. The existing hook `useDecideV3()` (`src/data/queries/decideV3.ts`) builds `source` and the settings source internally but returns only `inputs` and the home `evaluation`. 06.1 needs a sibling hook that returns `{ prepared, judge(check) }` so typing a price re-runs only `judgeCheck`. Reuse the same memo inputs (`snapshot.source`, `settingsSourceOf(...)`) rather than re-deriving them.

### Pattern 2: Result to sentences through one resolver
Port `sayLine` (`reviewed/page.ts` lines 289-314) into production code. Rules it already encodes: key per code via `FACT_KEYS`/`NOTICE_KEYS` plus discriminators (`DISCRIMINATOR_KEYS`), `COPY_RESOLVERS` for `categoryId`, `seriesId`, `envelopeId`, `accountId`, `debtId`, `missing`; money for numeric values except `PLAIN_NUMBER_KEYS`. One sentence per row (UX-19), never joined. A test must iterate every code in `FACT_VALUE_KEYS`, `NOTICE_VALUE_KEYS`, `CAVEAT_VALUE_KEYS` and fail on a code with no key or an unresolved placeholder.

### Pattern 3: Tone to state mapping
`VERDICT_TABLE` has four tones; D-16 has seven states. Implement `stateForVerdict(code, variant, once)` exactly as the UI-SPEC table, using `verdictRowFor(code, variant, once)` (barrel) for chip/title/body keys. Unit test iterates `Object.keys(VERDICT_TABLE)` and fails for any row without a state, shape and chip word.

### Pattern 4: Big-buy rule without a hardcoded edge
`bandOf(whole, thresholds).band >= 6` where `thresholds = homeThresholds(currency, usdRate)` (both on the barrel). Band 6 starts when `whole > bandEdges[4]`... verify off-by-one in a test: `bandOf` gives `2 + count(edges[1..13] strictly below whole)`, so band 6 means four of `edges[1..4]` are below the price, i.e. price above `edges[4]` (USD 500,000 minor = US$5,000 when edges are in cents: `BAND_EDGES_USD[0]=5_000` is $50, `[4]=500_000` is US$5,000) [VERIFIED: `src/engine/decide/v3/constants.ts:51`, `judge/bands.ts:13-20`]. "Whole" is `Purchase.whole` (price + tax + one-off fees, my share). Also a test that the rule is the same through `Result.band` after a judge. No new engine helper is needed; UI-SPEC's "pure helper in the engine barrel" is satisfied by `bandOf` + `homeThresholds`.

### Pattern 5: Home words never reach the engine
Detect home kind/words in the screen layer (`quickParse.ts` is the "Reads as" parser to extend), show the new `decide.screens` note and block Check it. Test that no `CheckV2` with a home itemType is ever judged (D-02).

### Anti-Patterns to Avoid
- **Copying anything from `src/features/decide/check/*`, `home/*`, `setup/*` UI or the parked 05.3 branch** (BO-09, UI-SPEC). They are on the old engine and are deleted.
- **Hardcoding colours, US$5,000, or the footer wording** (`noRawColours`, copy guard).
- **Storing a second copy** of anything Grow owns (net size, debt due day) in `decide_settings`.
- **Deriving state from colour alone** (UX-09): every badge is glyph + word.

## Common Pitfalls

### Pitfall 1: `parseCheckV2` silently drops the Variant C fields
**What goes wrong:** a check saved with running costs, a sale or a purchase date reopens without them; the answer changes and the user sees a different number than the one they saw.
**Why:** `toStoredV2` spreads the whole check; `parseCheckV2` returns only fields up to `taxIncluded` [VERIFIED: `adapters/inputsV2.ts:~141-160`].
**Avoid:** extend the parser first (wave 0), with fast-check round-trip tests and caps, before any screen saves these fields. This is an engine change (100% folder, Stryker).
**Warning sign:** a round-trip test `parseCheckV2(toStoredV2(c))` unequal to `c` for any generated check.

### Pitfall 2: Unlock cannot be stored where Grow keeps the net
See Q1. If the plan assumes `savings_goals.locked = false`, the DB guard forces it back to true and the Grow summary says the interim column is dropped.

### Pitfall 3: Wording lock vs late edits
Any locked-string edit after sign-off fails CI. Do all D-19 and Grow-fact renames first; sign once; add `decide.screens` to scope before signing.

### Pitfall 4: Deleting old modules breaks shared importers
`features/income` imports `decide/setup/steps/types`; `data/mutations` import `home/settingsPatch`, `notifications/waitReminder`, `journal/pastDecisions`; `devHarness` imports `perf/perfMarks`; tabs layout mounts `shadow/DecideShadowHost`. Move first, delete last, run `depcruise`.

### Pitfall 5: First user-facing v3 answers differ from what testers saw
Testers today see old-engine answers. v3 is stricter (safety net, overdraft, tax). Expect support questions; the intro card and "Records up to" lines are the mitigation. Also the DB `decide_checks_answer_v3_shape` allows the ten codes only; confirm any new code is allowed.

### Pitfall 6: Colour carries meaning alone
`short` text must be #933720, not #B4472A (4.36:1). Every state: shape + word. Short-month bars grow downward (UX-30).

### Pitfall 7: Tight 100% folders
`features/decide/snapshot` and `journal` are 100% branch. Grow 06-10 edits `snapshot/v3`; coordinate merge so coverage does not drop on either side.

### Pitfall 8: Prototype sheets absent from the spec index
`decide-screens.js` also defines D54 (Full cost), D55 (Every date, next 90 days), D56 (Month by month), D57 (How this was worked out), D58 (Your month after buying = N14), D59 (Costs that stop), D60 (Buy later), D61 (Cheaper one), D62 compare (N16), D63 (I bought it), D64 (Save for it: change the amount), D65 (Free help), D67 (Investment check preview, **excluded by D-13**), D32E/D32I/D33A/D33E (pay and bill edit sheets), D49I/D49S (Investing/Saving at least, read-only with Open in Grow), D43C (Closing costs, **excluded, home**). D-01 says "every Decide screen in the prototype", and UI-SPEC covers some only implicitly. The planner should inventory `sheet('D..'` and `screen('..'` ids in `decide-screens.js` and give each a task or an explicit exclusion.

### Pitfall 9: Quick-estimate "Savings can be used? Yes" is an unlock-like input
It would count outside money as spare. Treat like the "Yes, I have it" button (OQ-3, not built) unless the owner says otherwise (Q2).

### Pitfall 10: Running-cost template amounts have no source
The old engine's `RUNNING_COST_PROMPTS` holds categories only, "never amounts (D-05)". The prototype pre-fills amounts ($323 a month for a used car). See Q5.

## Questions for the Owner

Genuine product decisions not answered in CONTEXT or UI-SPEC. Each has a recommended default; ask before building (owner rule), in plain English.

1. **Where does "let answers use my safety net" live?** Grow always keeps the safety net locked, in its database too. Decide's Unlock screens (D51, D52) need a place to remember the choice. *Recommended default:* a new small column on the flagged safety-net goal named for Decide ("answers may use it", default off), written only by the Decide unlock screens, with Grow's lock rules left as they are (Grow's own screens still show it as protected). The old Decide settings column is then not used. The alternative is to keep the old column for a while, which Grow plans to stop reading.
2. **The "Quick estimate" tiles Loan, Savings and Income on More details (D41).** Only Expense fits the engine today. Loan, Savings and Income have no input in the maths. *Recommended default:* build Expense now (it maps to running costs or a one-off cost). Build Loan, Savings and Income by adding them as temporary lines to the numbers used for that one check only, with new right-answer cases for you to approve; Savings marked "Yes, answers can use it" counts as spare money only for that check and says so. If you would rather not risk new maths in this release, hide those three tiles and ship Expense only.
3. **What does "Save for it" do?** Grow's plan opens its new-goal sheet. Today's Decide also marks the check as waiting and sets the cooling-off reminder in the same step. *Recommended default:* one save does both: the goal is made in Grow (linked to the check, locked, and for installments only the up-front part), and the check moves to "waiting", with one Undo.
4. **Setup items you can answer with "nothing".** "No other debts", "Not set yet" for the safety net, "No rules" and "These bills are right" tick their setup item but have nowhere to be stored. *Recommended default:* store four small "I answered this" flags on your Decide settings. The two onboarding screens that still open the old Decide (first check, rough figures) are pointed at the new quick estimates (D39) and new check.
5. **Where do the pre-filled running-cost amounts come from (a car: insurance, fuel, repairs)?** The old rules never held amounts. *Recommended default:* a small table in the app, by kind and country, with round example figures labelled "quick estimates", dated and reviewed by you on the wording page; where your records already hold a matching bill (for example car insurance), that real amount is used instead.
