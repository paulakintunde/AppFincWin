# Phase 06.1 Plan 76: Sheet empty-backdrop trap, focus jump and toast Dismiss Summary

A sheet that is asked to close but stays open now always brings its panel back (one `keepEditing()` path), its backdrop takes no taps while the panel is leaving, the Android keyboard pad moves the panel once per show or hide and ignores the floating keyboard toolbar, and the toast Dismiss is a 48 x 48 dp target.

## What was built

### Task 1: No empty backdrop (DB-4, DB-3, DB-14)

- `keepEditing()` in `src/ui/Sheet.tsx`: sets the panel's `translateY` to 0 (full `sheetUp` slide if the panel is still at or past its own height, i.e. never reached the screen; `sheetDrag` otherwise) and the backdrop to `BACKDROP_OPACITY`. It always sets a fresh animation, even when the value already reads 0, so the native view is re-synced.
- Used by: the discard prompt's "Keep editing" (and its own Back/backdrop, which call the same `onKeep`), `requestDismiss` when the sheet is dirty (before the prompt opens) or not dismissible, `onBlockedDismiss`, and the post-drag frame (`requestAnimationFrame(keepEditing)` replaces the old inline Pitfall 5 restore).
- A new `leaving` state is set when a drag sends the panel off screen; the backdrop Pressable gets `pointerEvents={leaving ? 'none' : 'auto'}`. `keepEditing()` clears it, and it resets when the owner closes the sheet (adjusted during render, like `discardOpen`).
- A clean sheet's Back and backdrop still call `onDismiss` inside the press handler; a test now pins that (DB-14).
- Root cause note: on the device the panel was off screen while the "Close" backdrop stayed. The tests reproduce the closest path the code allows: a touch that moved the panel (a finger held during the slide-in, or the touch stream cut by the prompt's own Modal, so no END arrives) followed by Back/backdrop, then "Keep editing". Before the fix the panel stayed where the touch left it (300 / 400 / 250 px down) and every later tap hit the backdrop. Whatever moved the panel, the next dismiss request and "Keep editing" now restore it.

### Task 2: No focus jump; 48 dp toast Dismiss (DB-5, DB-12 part)

- `useAndroidKeyboardHeight()` keeps the last height in a ref and skips repeat reports; a `keyboardDidShow` under `KEYBOARD_MIN_DP` (100 dp) counts as 0. iOS is unchanged (no listeners).
- Pad sequence for one focus and one blur (base = `sheetPadBottom + insets.bottom`):
  - Floating toolbar (device case, about 63): before `base -> base+63 -> base` (two moves of 63 px); after `base -> base -> base` (no move).
  - Docked keyboard with a repeat didShow (300, 300, hide): before `base -> base+300 -> (re-render) -> base` (an extra render on the repeat); after `base -> base+300 -> base`, one render per show and per hide.
- `ToastView` Dismiss: `width/height 48`, `marginVertical -18`, `marginLeft -8`, `marginRight -28`, `paddingLeft 8`, glyph left-aligned and centred vertically. Its footprint in the row stays 12 x 12, so the toast's height and the glyph's place do not change. The old `hitSlop` is dropped for Dismiss; Undo keeps its `CONTROL_HIT_SLOP`.

## Deviations from Plan

1. **[Rule 2 - correctness] Restore also on the request, not only after "Keep editing".** The plan lists the restore on keep-editing routes. The dirty and non-dismissible branches of `requestDismiss` also call `keepEditing()`, so a tap on a backdrop whose panel is lost brings the panel back at once (with the prompt in front) rather than relying on the user picking "Keep editing".
2. **"Off screen" for the backdrop's pointerEvents is the drag-leaving state.** The JS side cannot see a panel lost natively; the backdrop is non-tappable while a drag sends the panel away, and deviation 1 covers the lost-panel case.
3. **ToastView test:** the old case asserted that both controls had no min size and the 12/8 hitSlop. It now asserts that for Undo only; Dismiss has its own 48 dp case.
4. **Commit split:** Task 1's commit holds the restore work; the keyboard hook change in the same file landed in Task 2's commit.
