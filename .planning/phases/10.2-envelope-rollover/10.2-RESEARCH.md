## Summary

A category's monthly limit is `categories.monthly_cap` (bigint, home-currency minor units, per user). It is read in about fourteen places, but only **three** read paths exist: (a) the usage engine `categoryUsage(rows, cap)` called from `useCategoryMonthUsage` (Categories screen, entry-sheet category picker, over-limit toast); (b) `overCapRows` (Activity row badge); (c) the Decide chain `useDecideSnapshot.categoryCaps` to `buildInputs.limitsOf` to the judge's `category_monthly_cap` line. Everything else (Decide home rules card, RulesSetup, AddRuleSheet, CategorySheet field, level `holdsData`, export, home-currency conversion SQL) either displays the **plain** stored limit or writes it. The clean design is: keep `monthly_cap` meaning "the plain limit" untouched and add a pure **effective limit for month M** (`plain + carried`, clamped) that the three read paths consume through one shared hook. With rollover off the hook returns the plain limit and every number is byte-identical.

Recommended storage: **compute carries from history, do not store a carry per month.** Store only (1) `profiles.rollover_since` (text `YYYY-MM`, null = off, set to this month when switched on) and (2) `categories.rollover_from` (text `YYYY-MM`, null = none), the month the category's current limit started counting (set whenever that category's limit is set, changed or removed). The chain for a category starts at `max(rollover_since, rollover_from)` with carry-in 0 for that month. This satisfies D-05 (first carry at end of the switch-on month), D-06 (turn off = null, on again = new `rollover_since`, old months can never be reached), undo (restoring the two columns restores every carried figure exactly, no ledger to unwind), the offline write queue (two ordinary column writes, no month-close job), and home-currency change (nothing stored in money, so nothing to convert). Cost: the client must read the spend of past months, which today it does not (see S2 finding).

**Primary recommendation:** Add `src/engine/categorize/rollover.ts` (pure, 100% branch folder), one `useEffectiveLimits()` data hook feeding the three read paths, `profiles.rollover_since` + `categories.rollover_from` in one migration (plus `apply_patches` allowlist for `rollover_from`), and change nothing in `engine/decide/**`; pass the effective limit through `categoryCaps` only.

## Storage choice and recurrence

### Recurrence (exact)

Let `L` be the category's plain limit (minor units, > 0), `s_m` the month's net spend (`categoryUsage.spent`: spend minus refunds, may be negative; paid and pending, not skipped, not transfers; home currency). For the chain start month `m0`, effective limit `E_{m0} = L`. For each later month:

```
R_m     = E_m - s_m                      // remaining; negative = over
E_{m+1} = min(2L, max(0, L + R_m))       // D-02 floor 0, D-03 cap 2L
carried_{m+1} = E_{m+1} - L              // in [-L, +L]; shown as "+ carried" or "- over"
```

Equivalently the carried amount is `clamp(R_m, -L, +L)`. Pure integer add/subtract/min/max: no rounding rule is needed, and `2L <= 2e13` is far below `Number.MAX_SAFE_INTEGER` (cap is bounded to 1e13 by the DB check). Property tests: `0 <= E <= 2L` always; `E` is monotone non-decreasing in carry-in and non-increasing in spend; with `s = E` every month the chain is stable.

### Right-answer cases (L = 50000 means $500.00)
| # | History | Result |
|---|---------|--------|
| 1 | Oct E=500, spend 420 | Nov E=580, "$500 + $80 carried from October" |
| 2 | Oct E=500, spend 550 | Nov E=450, "$500 - $50 over in October" |
| 3 | Oct E=500, spend 500 | Nov E=500, carried 0, no carried line |
| 4 | E=900 (carried +400), spend 0 | next E=1000 (cap 2L), carried +500 shown "$500 + $500" |
| 5 | Oct E=500, spend 1500 | R=-1000, E_Nov=0 (floor), carried -500; Nov spend 0 gives E_Dec=500 (excess debt beyond one month is not carried) |
| 6 | Oct E=500, refunds exceed spend, s=-100 | R=600, E=1000 (clamped), refunds count per D-04 |
| 7 | Month with no rows | s=0, E grows by L up to 2L |
| 8 | Switched on 12 Nov | Nov E=500 (no carry-in); Dec E from Nov's result; Oct never read |
| 9 | Switched on then off then on | `rollover_since` reset to the new month: fresh |
| 10 | Spend line with no home figure (`amountHome` null) | counted as 0, flagged `unconvertedCount > 0`; UI shows the existing unconverted cue, never a guessed carry |

### Why compute-from-history (recommended) over a stored per-month carry
- A stored carry row needs a month-close writer. Nothing in the app runs at month end; a lazy "close last month on open" write races across devices and household members, breaks offline (queued writes replay out of order), and goes stale when a late entry edits a closed month. Derived carries heal automatically.
- Undo and D-06 fall out: restoring `rollover_since`/`rollover_from` restores every number; there is no ledger to reverse.
- Home-currency change needs no conversion migration for the carries.
- Cost: reading past months. The chain length is bounded by months since the later of `rollover_since` and `rollover_from`; a limit change re-bases it. Worst case is a user who never touches limits over several years; mitigate with a range read from `chainStart` to last month's end (existing `fetchTransactionsInRange`, `src/data/queries/decide.ts` L318-ish uses it for a 12-month lookback, `DECIDE_LOOKBACK_MONTHS = 12` at L43) cached under its own query key. A year of rows is already read by Decide, so this is comparable. Open question O2 covers a cap on chain length if the planner wants one.

**Alternative (not chosen):** `category_carries(owner_id, category_id, month, carry)` ledger. Only worth it if profiling shows the range read is too heavy; then store a periodic checkpoint, not every month.

## Mid-month limit change (Claude's discretion): proposed rule

**Rule:** a change to a category's plain limit (set for the first time, raised, lowered, or removed) **restarts that category's chain this month**: `rollover_from = monthOf(today)`. The current month's effective limit becomes the new plain limit with no carry-in; the new limit's first carry is at this month's end (same as D-05). Past months are never re-worked (their figures simply stop mattering). Removing a limit sets `rollover_from = null` and the chain disappears; setting one again starts fresh. The confirm text in the CategorySheet states it when the category currently has a carried amount ("Changing the limit starts carrying again from this month").

Why: with derived carries a single stored limit would otherwise re-value past months at today's limit, silently rewriting history (contradicts D-05's spirit) and an unbounded chain; a re-base needs no history of past limits and mirrors D-06.

Right-answer cases:
| Case | Before | Change | After |
|---|---|---|---|
| a | E_Nov = 580 (500 + 80), Nov 10 | limit 500 to 600 | Nov E = 600, no carried line; Dec carries from Nov spend vs 600 |
| b | same | limit 500 to 500 (no change) | nothing re-based, E_Nov stays 580 |
| c | no limit, rollover on since Sep | cap set to 300 on 5 Nov | `rollover_from` Nov; Nov E=300; Oct/Sep never counted |
| d | E_Nov = 450 (over 50) | limit removed | no limit, chain gone; set again later starts fresh |
| e | rollover turned off then on 20 Nov | n/a | all categories start Nov, no carry-in, Dec first carry |
| f | undo of case a | restore `monthly_cap` 500 and `rollover_from` | E_Nov = 580 again (chain from the earlier start) |

Alternative if the owner dislikes dropping a carry on a small tweak: keep the carry-in dollars by seeding (`rollover_seed` bigint, written at change time from the computed carry-in). More storage and a stale-seed risk; recommend only if asked (O1).

## Common Pitfalls

1. **Reading only this month.** `useCategoryMonthUsage` loads one month (S2). Assuming past spend is available yields silent zero carries. Use a range query from `chainStart`.
2. **Activity shows past months.** `overCapRows` must use each month's effective limit; using today's effective limit for October mislabels the badge.
3. **Diverging "spent".** Three spend definitions (usage, overCapRows, chain). Route all through one function; add a test that Categories, Activity and chain agree on a fixture.
4. **`over` boundary.** `categoryUsage` calls spend exactly equal to the limit `over` (L40, `>=`) while `overCapRows` needs strictly greater. Do not "fix" either as part of this phase; define carried amounts from `R = E - s` (zero at exact spend, so no carry or over line) and keep existing badges unchanged.
5. **Decide leaks.** Any change to `limitsOf`/`lines.ts` or adding fields to `V3Inputs` moves goldens. Only the value in `categoryCaps` changes.
6. **Partner privacy.** Never read a partner's limit or carry; keep the `shared_line_categories` RPC as is.
7. **apply_patches redefinition.** The allowlist is copied whole in each migration; copy the **latest** (`20261125001100_debt_details.sql`) or you drop later columns. `lint:migrations` checks compat.
8. **Home-currency change.** Past months' amounts are cross-converted at read via `homeAmountFor`; carries recompute, so no stored figure goes stale (a benefit of the derived design).
9. **Late edits to closed months** change carries retroactively (by design, they heal). State it in the You note.
10. **Time zone/month boundary.** Use `rc.today` (local date in the user's time zone) for "this month", never `new Date()`.

Engine API sketch (pure, no imports from db/state/ui/react):
```ts
export interface CarryMonth { month: string; limit: number; effective: number; carried: number; spent: number }
export function carryChain(input: {
  limit: number;                       // plain, minor units, > 0
  startMonth: string;                  // YYYY-MM, first month, effective = limit
  throughMonth: string;                // the month to report (inclusive); months after startMonth..throughMonth-1 carry
  spentByMonth: Readonly<Record<string, number>>; // missing month = 0
}): readonly CarryMonth[]
// effective(m0)=limit; for next: effective=min(2*limit,max(0,limit+effective-spent)); carried=effective-limit
```
`throughMonth` is `monthOf(today)`; the current month's `spent` is not folded into the future (only closed months carry), so the current month's effective limit is stable all month.
