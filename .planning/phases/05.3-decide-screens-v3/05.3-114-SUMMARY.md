# Phase 05.3 Plan 114: Back from an answer reaches Decide home with one (tabs) Summary

One shared shell helper, `returnToTab(href, navState)`, now handles every Decide v3 return to a tab. Back from an answer dismisses to the existing (tabs). It no longer pushes a second copy, so the next Back leaves Decide and does not show the answer again (UAT gap 33).

## What was done

- **Task 1:** `src/shell/navigation/returnToTab.ts` holds three functions:
  - `hasTabsInStack`, moved verbatim from `importReturn.ts`. It is re-exported there, so `importReturn.test.ts` and `finishImport` are unchanged.
  - `focusedIsTabs`, new.
  - `returnToTab`, with three branches: a plain `navigate` when (tabs) is focused; `dismissTo` when `canDismiss()` is true and a (tabs) is beneath; `replace` otherwise (onboarding).
- **Task 2:**
  - `useBackToDecide` reads `useRootNavigationState()` into a ref and calls `returnToTab(DECIDE_TAB_HREF, ref.current)`.
  - `DOUBLE_BACK_MS` and `lastRef` are gone. The guard is now a local `inFlight` flag inside the focus effect, so each focus starts it at false. A second press during the same focus is swallowed. A Back after the answer is focused again works at once.
  - Four more sites now call `returnToTab`:
    - AnswerScreen's "Back to Decide" after a record sheet writes
    - NeedsInputCard's "Update my records instead"
    - HelpScreen's update button
    - ReadinessAnswerProvider's `openActivity`. The provider wraps both the answer (outer) and Decide home (tab), and the tab case keeps the plain navigate.
- **Task 3:** The ten listed suites mock `@/shell/navigation/returnToTab` and add `useRootNavigationState: () => undefined`. Their tab-href assertions now check `returnToTab('/activity' | '/decide', undefined)`. Negative checks now assert `expect(returnToTab).not.toHaveBeenCalled()`: two in ReadinessAnswerProvider (`navigate` lines kept) and one in AnswerScreen. No other assertion changed.

## Regression test failed before the fix

`backToDecideRouter.test.tsx` uses `renderRouter` over the REAL `app/(app)/_layout` and `app/(app)/(tabs)/_layout`, following `shellNavigation.test.tsx`. Leaves are stubs, and the answer route runs the real `useBackToDecide(true)`. Run against the old `router.navigate('/decide')`, all 3 cases failed. The (app) stack after one Back was `["(tabs)", "decide/answer/[id]", "(tabs)"]`, which is two (tabs). The same-tick double Back case counted 2 (tabs). After the fix all 3 pass:
1. Opened over Activity: Back goes to `/decide`, and the (app) stack is exactly `["(tabs)"]`. Back again shows neither the answer nor `/decide`.
2. Opened from Decide: Back goes to `/decide` with one (tabs).
3. Two Backs in one tick give one navigation and one (tabs). The answer is then reopened at once, and its first Back is honoured.

renderRouter ran fine here, so the nav-state fallback was not needed.
