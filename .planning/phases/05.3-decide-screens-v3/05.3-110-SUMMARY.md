# Phase 05.3 Plan 110: Back from an answer goes to Decide home Summary

System Back and the edge swipe on the answer screen now navigate to `/decide` in one press, through a focus-scoped `useBackToDecide(enabled)` hook (UAT gap 27).

## What was done

- `useBackToDecide` registers `setSwipeBackInterceptor` and a `hardwareBackPress` listener under `useFocusEffect`; both are removed on blur. The listener calls `router.navigate(DECIDE_TAB_HREF)` and returns true, so the app-wide `router.back()` handler does not run. Two presses within 600 ms navigate once.
- `AnswerBody` calls `useBackToDecide(!(sheet?.open ?? false) && !confOpen)`, so an open record or confidence sheet keeps Back (D-06 step 1). The header's round back ("Back to the check") is unchanged.
- Test `answerHardwareBack.test.tsx` runs the real `BackHistoryProvider`, `AndroidBackHandler` and `AnswerScreen`, with the tab under the answer set to Activity. Four cases: one Back navigates to `/decide` and never calls `router.back`; no sheet Modal is mounted with no sheet open; an open record sheet keeps Back and one Back after it closes goes to Decide; two quick Backs navigate once.

## Modal diagnosis result

With no sheet open, no visible RN Modal is mounted on the answer screen. `src/ui/Sheet.tsx` returns null when `!visible`, so there is no hidden Modal to swallow the first Back. The cause of the device's "first Back does nothing" is therefore not a Modal. The remaining static candidate is the 600 ms `replaceOnce` guard or the app-wide `goBack` revealing the tab underneath. This was not reproduced in a test. The new hook removes the dependency on `router.back()` for this screen. The device Back check in 05.3-112 confirms it. No `OPEN:` item.
