# Phase 05.3 Plan 64: dueDrops in the cash path and unspent Summary

The cash check and unspent money now read the same dueDrops rule as the month card. "Someone else paid it", "Someone else always pays this" and a skipped occurrence stop counting as money going out everywhere the answer subtracts bills. Agreement tests run through `evaluate()` and show that the three figures move by the same amount.

## What was built

- **cash/path.ts**. `buildCashPathV3` takes `drops?: DueDrops`. In the bill and debt loop, a due in `paidThisMonth` is skipped first (a recorded payment wins), then a due with a non-null `drops.has()` is skipped. This applies on every date from asOf to the horizon, so always_other drops Netflix in October, November and December too.
- **evaluate.ts**. `evaluateOnce` passes `dueDrops(inputs)` to the cash path.
- **funds/unspent.ts**. `billsAndErest` and `suggestedUnspent` take `drops?: DueDrops`. For profile (d) (a balance-based earner), the horizon bills count only occurrences that `drops.has()` leaves in. For the other profiles `billsDue` comes from the month model, which already left drops out (05.3-63). A comment in `rollForward` explains why it does not read dueDrops (see Deviations).
- **funds/build.ts**. `buildFunds` and `unspentSum` pass `dueDrops(inputs)`, so the Unspent money card's worked sum matches the funds figure.

## Deviations from Plan

### 1. [Plan inconsistency] paid_by_other on 2026-10-20 with asOf 2026-10-10
- **Found during:** Task 2.
- **Issue:** the plan's agreement case dates Rent's paid_by_other after asOf. 05.3-63's rule (from its plan) ignores a paid_by_other dated after asOf, so nothing drops. A paid_by_other can only drop a due on or before asOf, and the cash path only starts at asOf. So the only date where all three figures can move is asOf itself.
- **Fix:** the test keeps the plan's 10-20 case and shows all three figures move by 0 (they still agree). It adds a Rent due on asOf (10-10, after the 10-05 anchor) where all three move by 90000.

### 2. [Rule 1, correctness] rollForward and refine do not read dueDrops
- **Issue:** the plan says to drop flagged dues in `rollForward`'s dueAtAnchor after settling, and to pass dueDrops from refine.ts:211. In `rollForward`, dueAtAnchor is used only to find which paid lines were already held back. Settling first and then dropping unsettled dues changes nothing, so the parameter would be dead code. The only way to move "unspent" there would be to release the held-back amount, raising the rolled value. That double counts: once the answer exists, every unspent figure the user confirms later already leaves the bill out (the suggested figure they confirm comes from billsDue). It would overstate money the user has, for example by a partner's Rent each month, which is the harmful direction for Decide.
- **Fix:** no change to `rollForward` or refine.ts. A comment in `rollForward` says why. Unspent agrees through `funds.suggested` (the D-43 suggested figure), which rises by exactly the dropped dues. The confirmed figure stays the user's (D-30). In the short window where an anchor was confirmed before the answer, the freed money shows as drift or unexplained money until the user re-confirms. That is cautious and puts the question to the user.
- **Files not modified as a result:** src/engine/decide/v3/month/refine.ts, src/engine/decide/v3/month/__tests__/refine.test.ts.
- **For owner review:** if the owner wants the rolled figure to rise instead, the waiver needs a timestamp so the engine can release only dues answered after the anchor.
