# Phase 05.3 Plan 117: Queued settings changes survive an earlier save Summary

When an earlier decide_settings save lands, both mutation kinds (setup steps and plain settings) now re-apply every change still queued behind it, of either kind and in the order made, so a new own option (a queued `custom_options` patch) no longer flips to "A removed option" when an earlier save finishes first (UAT gap 35, cache part).

## What changed

- **`src/data/mutations/decideSettingsQueue.ts` (new):**
  - `queuedSettingsPatches(qc, userId, exclude)` returns the pending patches under `updateDecideSetup` and `updateDecideSettings` for this user only. They come oldest first (sorted by `mutationId`) and leave out the caller's own vars.
  - `withQueued(row, patches)` layers the patches over the row in order.
  - `isOldestQueued(qc, vars)` checks across both keys.
  - `confirmedSettings` is the one shared confirmed-row map, with one wipe handler (`decide-settings-confirmed`).
- **`decideSetup.ts` and `decideSettings.ts`:**
  - onSuccess now writes `withQueued(row, queuedSettingsPatches(...))` instead of the bare server row.
  - onError rebuilds from `confirmedSettings` plus the queued patches of both kinds.
  - onMutate captures the confirmed row only for the oldest pending mutation across both kinds.
  - Removed: the per-file maps, the `decide-setup-confirmed` wipe handler, `pendingEdits` and `pendingSettingsEdits`.
- Unchanged: `markSession`, invalidation, and `recordFailedWrite` (field names only).
