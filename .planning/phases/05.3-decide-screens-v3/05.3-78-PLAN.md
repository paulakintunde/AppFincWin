<objective>
Make Undo after deleting a saved plan bring it back.

What the delete path is (cited): `src/features/decide/v3/lists/useRowActions.ts` `useDeleteRow` ->
`src/features/decide/past/useDeleteDecision.ts` `deleteDecision` (picks the live goal from the cached `useSavingsGoals` list) ->
`src/data/mutations/decideChecks.ts` `useRemoveDecision` -> the `editCheck` mutationFn goal branch, which builds forward and
inverse ops with `planBulkPatch` (src/engine/undo/inverse.ts line 120; inverse expectedVersion = expected + 1, line 149) and sends
both in ONE `apply_patches(p_ops, p_undo_step)` call. The server inserts that step itself (20261028001100 line 474) without
`allow_system_keys`, but its ops patch only `deleted_at`, which `apply_patches` allows on decide_checks and savings_goals for any
step (lines 175 and 181). So, unlike Plan it / Not buying, the delete is NOT the allow_system_keys problem.

The likely app cause (to prove in Task 1): the expected versions come from the cache. `editCheck` resolves them with
`resolveExpectedVersion`, which only knows versions this device recorded with `recordWrittenVersion`
(src/data/sync/versionChain.ts). `decideOutcome.ts` never calls `recordWrittenVersion`, and its success only invalidates (an
un-awaited refetch). A check saved as a plan moves its version by 2 on the server (answer_v3 save, then the outcome), and the
goal is cached as the optimistic row from `onMutate` (`version: 1`). A delete pressed before the refetch lands is sent with a
stale version: the forward write is refused (VersionConflictError -> a "changed elsewhere" failed write in `editCheck.onError`)
and the toast's Undo then has no recorded step.

Output: a reproduction test and the version recording that fixes it.
</objective>
