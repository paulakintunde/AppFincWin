## Switch back (D-04)

In plain words: how to turn the new Decide off again for everyone. Two ways.

1. **Publish the switch off.** Set `export const DECIDE_V3: boolean = false;` in `src/features/decide/availability.ts`, run the gate, land it through a PR, then publish to the same channel:
   `eas update --channel <c> --environment <c> --message "05.3 switch-back: Decide shows Coming soon"`
2. **Go back to the last good update** on that channel, without a code change. The plan text says `eas update:rollback`. The commands this project has written down and tested are in `docs/ops/ota-policy.md` "Rolling back a bad update":
   - `eas update:republish --group <last-good-group-id> --message "rollback: <reason>"` (first choice; find the group with `eas update:list --branch <c> --json --non-interactive`)
   - `eas update:roll-back-to-embedded --branch <c> --runtime-version <fingerprint>` (only if no earlier update on the channel is safe)

After either one, every entry point shows Coming soon for a normal account: the Decide tab, the FAB / You > Add "New check" (not registered), the nine v3 routes (redirect to `/decide`) and the reminder-tap observer (off). `src/features/decide/v3/__tests__/entryGate.test.tsx` proves this for `decideEngine() === 'v2'`.

**Test accounts are the exception.** They keep the new Decide through their own `profiles.decide_v3 = true` flag until that flag is cleared. Clearing it is a server change in production. It needs the owner's OK first. Do it with the Supabase CLI or the Management API, using the FincWin token from `C:\dev\fincwin\.env.local` exported for that one command. Never use the Supabase MCP connector: it points at a different account.

Clients pick up either switch-back on their next cold start (`checkAutomatically: 'ON_LOAD'` on preview and production builds, per `docs/ops/ota-policy.md`).
