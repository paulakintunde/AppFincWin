## Summary

The v3 engine, the snapshot layer and the 05.2 data/mutations are done and tested; this phase is overwhelmingly **UI composition over existing pure contracts**, plus three small server/engine changes (D-12 engine, D-15 migration, D-13 attribution) and the switch-on. No new library is needed and no native change is needed, so the cutover can go by OTA (`runtimeVersion: fingerprint`). The v3 engine is a single entry point: `evaluate(inputs, check) -> Evaluation { result, month, funds, purchase, planCard, quoted, cash, futures }`; the app reaches it through `computeV3(source, v3Settings, storedInputs, uses?, checkId?)`. Today the only production caller is `useDecideV3()` in `src/data/queries/decideV3.ts`, which evaluates an empty check (`{}`) for the 05.2 setup page. 05.3 needs a per-check hook beside it.

Five findings change how the plans must be written and are not in the UI-SPEC or CONTEXT: (1) **`decideGoAhead.ts` is wired to the old engine** (`CheckInputs`, `Assessment`, `PaymentStep`), so "Record as bought" needs a new v3 write builder, not a reuse. (2) **No column stores the v3 answer code**: `decide_checks.verdict_at_decision` and `last_seen_state` are CHECK-constrained to the four legacy values, so "stored chip", "Changed since you saved" and "Last saved answer" have no source until a storage decision is made. (3) **"Help me check this" figures only reach the engine for users with no full logged month**, because `inputs.rough` is built only when the snapshot kind is `'rough'`; for the common `records_look_behind` case "Check with these figures" would change nothing. (4) **The D-12 fix is more than passing `picture`**: with a seasonal picture the slider would become dead unless `seasonalReadyMonth` also takes a per-month lift, and the judge and the explorer use different price/unspent bases that must be proven equal. (5) **Value (L2), Major asset (L6) and Very large (L7) fields are never read by the engine** (`value.*` and `layerAnswers` are stored only), so those cards are record-keeping with no effect on the answer.

**Primary recommendation:** Build everything under a new `src/features/decide/v3/` tree (components, view-models) with new `app/(app)/decide/*` route names guarded by `useDecideAccess().v3`, leave all old files untouched (so the follow-up deletes by directory), put pure view-models in a folder added to the jest 100% list, and split work so the two blocking owner checkpoints (D-12 shadow approval, D-15 migration push) sit in early, separate waves and the cutover is a single final one-line change gated on the owner's Pixel sign-off.

### Pattern 1: One computation, many surfaces (success criterion 1)

**What:** every surface (home check card, check screen, answer, saved plan row, past decision) gets its `Result` from `computeV3`. `resultForHome/Check/SavedPlan` are literally the same function (`computeV3.ts:63-65`). **But they drop `checkId`**, so a saved volatile-cover answer (`decide_answers.kind='volatile_cover'`, key = check id) is ignored. Call `computeV3(source, v3, storedInputs, undefined, checkId)` directly for any check that has an id. Test: same stored check -> same `result.code` from all three call sites.

### Pattern 2: Code -> copy keys, UI picks variants

`verdictRowFor(code, variant)` -> `{ chipKey, titleKey, bodyKey, tone }`. Notice/fact/missing/readiness keys come from `NOTICE_KEYS`, `FACT_KEYS`, `MISSING_KEYS`, `READINESS_KEYS` (`copy/verdictTable.ts`). Values per code: `FACT_VALUE_KEYS`, `NOTICE_VALUE_KEYS`. The UI chooses these `_variant` keys already in `en.ts`: `income_from_expected_{confirmed,last_year,low}` (by `values.source`), `month_heading_short_category` (when `categoryId` present), `emergency_used_rebuild` (when `months` present), `line_crossed_{percent,money,tenths}` (by `values.unit`), `account_use_question_fund` (fund variant). Engine ids (`categoryId`, `seriesId`, `envelopeId`, `accountId`) are resolved to names by the UI (`COPY_RESOLVERS`). A missing code's placeholders are read from a notice's values (`MISSING_VALUE_SOURCE`: volatile_cover_question <- income_volatile, unexplained_money_question <- unexplained_money, account_use_question <- account_use_unknown, pay_arrival_question <- pay_not_seen).

### Pattern 3: Draft autosave

`decide_checks` row, status `open`, `inputs` jsonb. `useCreateCheck`, `useSaveCheckDraft`, `useAbandonCheck`, `useReopenCheck` in `src/data/mutations/decideChecks.ts`; `useCheckDraft.ts` and `useCheckSaveStatus.ts` in `check/` are the current drivers (v2-engine shaped). `readStoredCheck(json)` accepts v2 as stored and upgrades v1; `toStoredV2(check)` is the JSON-safe form (Percent -> decimal text). `parseCheckV2` is total (bad fields reset to defaults). Store the new check as `toStoredV2(CheckV2)`.

### Anti-Patterns to Avoid
- **Reusing `decideGoAhead.ts`/`useBoughtCheckComputation.ts`/`CheckFlowScreen`/`useCheckDraft`** for v3: they depend on the old engine that the follow-up deletes (see P-01).
- **Writing UI strings under `decide.v3.ui.*` without extending the reachability test** (P-04).
- **Computing money in components.** All figures come from the Evaluation; formatting through `useMoneyFormatter`/`formatMoneyA11y`; integer minor units only.
- **`numberOfLines` outside the allowlist** (`decideTextFit.test.ts` counts exact occurrences per file).

## Findings by research question

### 1. Engine contract (`src/engine/decide/v3`, barrel `index.ts`)

All of `types.ts` is exported as types. Key shapes `[VERIFIED: types.ts]`:
- `Result { code, variant, legacyState, split: FundingSegment[], facts: Fact[], notices: Notice[], missing: MissingCode[], reasons: ReasonCode[], readyBy: ReadyBy|null, band: Band|null, layers: Layer[], confidence: Confidence, parts: {oneOff: Code, monthly: Code|null}, readiness?: Readiness }`.
- `Code = 'needs_input'|'not_yet'|'monthly_short'|'emergency_use'|'fits_unspent'|'fits_month'`; `Variant = 'payday'|'not_covered'|'low_month'`. Precedence (`CODE_PRECEDENCE`, strictest first): `needs_input, not_yet, monthly_short, emergency_use, fits_unspent, fits_month`. **Later in the list = more favourable**, which is how a "better code" for D-13 is compared (`CODE_PRECEDENCE.indexOf`).
- `FundingSegment { source: 'month'|'unspent_earlier'|'envelope'|'emergency', amount }`. `ReadyBy = {kind:'date',date}|{kind:'month',month}`.
- `Confidence { level: 'rough'|'fair'|'firm', reasons: ConfidenceReason[] }`. Reasons: `few_months, early_in_month, under_logged, unsaved_changes, unspent_stale, unspent_drifted, rough_figures, provisional_rates, no_setup, user_said_cover, pay_missed`. **There is no copy for these reasons in `en.ts`** (grep found none) and the shipped `ConfidenceChip` takes `'strong'|'fair'|'rough'` (old engine's word; v3 says `'firm'`). Both need new work (P-08).
- `Readiness { ready, missing: ReadinessCode[] }` with codes `past_month_missing|activity_not_current|envelopes_unconfirmed`. **`readinessOf` returns `missing.sort()` (alphabetical)** so the engine order is `activity_not_current, envelopes_unconfirmed, past_month_missing`. The UI-SPEC table and the D-06 example ("Record September" first) assume chronological order; the view-model must order explicitly (past_month_missing, activity_not_current, envelopes_unconfirmed) and a test pins it.
- `Evaluation { result, month, funds, purchase: Purchase|null, planCard: PlanCard|null, quoted: QuotedCheck, cash: CashCheck, futures: Futures|null }`. `futures` is non-null only when `reasons` contains `volatile_cover_declined` (D-48: not_yet with Instead attached, `userRate: null, years: 1`).
- `evaluate(raw: V3Inputs, check: CheckV2): Evaluation` (`evaluate.ts`). A not-ready result is not a verdict (D-52): consumers must read `result.readiness.ready` first.

- Functions (`supabase/migrations/20260926000500_undo_log.sql`): `apply_undo_step(p_step_id uuid)` (:652), `rollback_undo_to(p_step_id uuid)` (:690), both call `undo_replay(p_step undo_log)`. **The latest `undo_replay` definition is `20261010000200_record_polish_patches.sql:330`** (adds the `allow_system_keys` / `fincwin.undo_replay` settings); `apply_undo_step` and `rollback_undo_to` have only the original definitions (grep of all migrations). `apply_patches` latest = `20261028001200_series_end_reason_and_debt_paid_off.sql:161`; `undo_log_fill` latest = `20261028001100_apply_patches_v3.sql:6`.

## Runtime/Record and routing details planners need

### Record path (DSV-13)
`buildGoAheadWrite({inputs: CheckInputs, assessment: GoAheadAssessment, running, ctx, mint})` is built on the **old** `CheckInputs`/`Assessment`/`PaymentStep` types and writes: day-one rows (one-off flagged), payment series (monthly/weekly/etc.), a `debts` row for loans (`term_months`, `apr`, `minimum_payment`, `secured`), running-cost series, ended replaced series, and a `decision` object `{verdict: assessment.state, estimate_*, broke_line, cooling_off, row_roles, series_roles}`. The RPC is `record_decide_go` and `verdict` must be one of `fits|adjust|no|missing` (= `Result.legacyState`). `ctx` needs `cashAccountId, cardAccountId, debtCategoryId, savingsCategoryId, transferCategoryId, investAccount, replacedSeries, runningCostCategoryIds`. A v3 builder maps `Purchase` (`dayOne`, `schedule.cadence/count/payment/finalPayment/firstDate/financed`, `monthly`, `runningMonthly`) to the same `NewTransaction`/`NewRecurringSeries`/`DecideGoDebt` shapes (the row shapes are engine-independent). It must live in `src/data/mutations/` (writes reach `db/fxResolve`) and be injected through a `src/shell/decide` provider like `CommitMutationsProvider`. Reuse: `GoAheadVars` mutation (`mutationKeys.decideGoAhead`), `registerDecideGoAheadMutations`, `newStepId`, the duplicate-tap guard (`findAll` pending), the failed-writes path, the cooling-off reminder (`reminders.scheduleCoolingOffReminder`). Tests: a pure `buildBoughtWrite` golden suite (cash; loan with debt; instalment weekly/biweekly; down payment; household share = my part only; refuses missing account), plus provider test.

### Where is the stored v3 answer? (P-02)
`decide_checks`: `verdict_at_decision` and `last_seen_state` are `text CHECK in ('fits','adjust','no','missing')` (`20261016000100_decide_tables.sql:18,22`); `last_seen_basis` in `('logged_months','first_read_rough_figures')`; `ready_by date`, `wait_monthly`, `estimate_*`, `broke_line`, `status in ('open','bought','waiting','passed')`. `SeenV3 {v:3, code, variant, readyBy, unspentAfter, lineFacts}` and `changeSinceLooked`/`seenOf` exist in the engine but **nothing persists them** (the home `seenOf` in `OpenChecksCard.tsx` is a local old-engine function). ## Common Pitfalls

### P-01: Reusing the old Go-ahead path
**What goes wrong:** plans say "reuse decideGoAhead as Record as bought (C14)". It consumes old-engine `CheckInputs` + `Assessment`; reusing it keeps the old engine alive and blocks the D-01 deletion; `useBoughtCheckComputation` calls `buildDecideSnapshot`.
**How to avoid:** new `buildBoughtWrite` from `Purchase` (see Record path); keep RPC and row shapes.
**Warning signs:** a v3 file importing `@/engine/decide` (non-v3) or `CheckInputs`.

### P-02: No place to keep the v3 answer (above)
Unresolved, the saved-plan, past-decision and "Changed since you saved" tasks cannot be written.

### P-03: Write-queue rule - do not await invalidations in `onSuccess`
A paused/queued mutation's `onSuccess` that awaits `invalidateQueries` blocks the serial queue (scope `WRITE_SCOPE`) while offline and stalls every later write. Follow the existing mutation files: optimistic cache write (`upsertRow`), fire-and-forget invalidation, `mutationKeys.*` registered in `registerMutationDefaults` (`mutations/index.ts`) so a rehydrated paused mutation can resume; a new mutation (v3 record builder, refine choices) must be registered there and covered by `registry05_2.test.ts`-style registry test. Mint ids and `stepId` once at call time (so replay reuses them), as `useGoAhead` does.

### P-04: Copy tests break on the new namespace (section 7)

### P-05: Static text-fit allowlist and `numberOfLines`
Every new `.tsx` under `src/features/decide` with a one-line figure, a fixed-height bar/dot/glyph or absolute label needs an allowlist entry with an exact count, or `decideTextFit.test.ts` fails. User-typed names (item, payee, envelope) use `ellipsizeMode` + full name in the a11y label, listed as `user-name`.

### P-06: `readiness.missing` is alphabetical (section 1)

### P-07: `resultFor*` drop `checkId` (Pattern 1); and `useDecideV3` evaluates `{}`

### P-08: Confidence chip and sheet speak the old engine
`ConfidenceChip` level type is `'strong'|'fair'|'rough'`; v3 is `'rough'|'fair'|'firm'`. `ConfidenceSheet` lists old reason copy. Map `firm -> strong` word or add `decide.v3.confidence.*` copy for the 11 `ConfidenceReason` codes; D-57 chip "Rough, from your figures" appears when `reasons` contains `rough_figures`.

### P-09: "Help me check this" does not reach the engine for users with logged months
`buildV3Inputs` builds `inputs.rough` only when `built.kind === 'rough'` (`buildV3Inputs.ts:520`), and `buildSnapshot` returns `'rough'` only when there is no full logged month and figures exist (`buildSnapshot.ts:786`). `model.ts` feeds `roughExpenses` from `inputs.rough`. So typing the five figures for a user with a full month and `records_look_behind` changes nothing, and the UI would claim a "Rough, from your figures" answer it does not produce. Options for the planner: (a) scope "Help me check this" to the no-history case (D-57) and, for `records_look_behind`, show only "Update my records instead"; (b) an engine change letting rough figures fill this month's gap (shadow/I28 re-run, owner approval) - larger and not requested. Also: where do the five fields persist? `decide_settings.rough_income/rough_spending` (05) and `rough_saving/debt/invest/as_of` (05.2) via `useUpdateDecideSettings`/`useSaveSetupStep`; keep those columns through the follow-up `decide_cleanup` ("reviews the `rough_*` columns"). Flag to the owner; default (a).

### P-10: Layer cards that do nothing
Engine never reads `CheckV2.value.*` or `layerAnswers` (grep: only parse/store in `inputsV2.ts`/`legacy.ts`; purpose affects only `canUseEmergency`). So the Value card (L2), Major asset (L6), Very large (L7) fields, and "I've talked this over with a professional" are stored record-keeping with no effect on the answer. Do not word them as inputs to the answer; consider the L6 "Legal and closing costs"/"Moving costs" fields: the property preset already has `closing_costs` and `moving_costs` extras (L4) - the L6 duplicates must not be written to `extras` (double count) and should be stored under `layerAnswers` with `L6.*` keys (`layerOfAnswerKey` requires a layer prefix, e.g. `'L6.closing'`; `visibleLayerAnswers` hides but keeps answers, I43). Recommend telling the owner (UI-SPEC open question 11 default) before building them.

### P-11: UI-SPEC "layers by band" vs the engine
The engine is authoritative: `BAND_LAYERS` + `layersFor(band, {periodic, hasExtras})`; L3 (payment plan) and L5 (whole plan) are added by `periodic`, L4 by item-type extras, regardless of band; L2 from band 5, L5 from band 6, L6 from 9, L7 from 12; `insteadLinkFor(band)` gives `none|link|prominent|open`; `stagedRequired(band)` true at 15. Drive visibility from `Purchase.layers`/`Result.layers`, never a copied table.

### P-12: Band chip range text
`homeThresholds(home, usdRate).bandEdges` has 13+ edges; with `source: 'missing'` it is `[]` and `bandOf` returns band 15 with `band_rate_missing`: show only "Band {n}" (UI-SPEC). Range = `[edge[n-2], edge[n-1])`; band 1 below `edges[0]`. Compact money format needs a formatter variant (check `useMoneyFormatter` for a compact option; else add one in `src/engine/money` with tests).

### P-13: Activity refund chip needs a picker prop
`RefundPickerSheet` initialises `selectedId` from `anchor.refund_of` for `refund->purchase`; D-14 needs a new optional `preselectId` prop (and the purchase may be outside the 12-month window list: handle like the "linked stays in list" branch). The chip logic (payee match within 12 months, same currency, unlinked) is pure: put in `refundPickerModel.ts` neighbour with tests. All Activity v3 parts already depend on `useDecideAccess().v3`.

### P-14: Cutover collateral
Flipping `DECIDE_V3` also enables for everyone: Activity income-tag chips/sheets, "How are you paid?" card, refund tags, setup/settings routes, `FAB`/You > Add "New check". The owner walkthrough must cover them; the switch-on plan should list them.

### P-15: Derived state in two places for the chip/“same answer” guarantee
Home check card, saved-plan row and answer must call the same function; a test mounts all three with the same fixtures and asserts one `code` (success criterion 1).

### P-16: Gap `useDecideAccess` fails closed
`profile?.decide_v3 === true`; while the profile loads it returns v3 false, so a v3 user briefly sees Coming soon. Build the tab root to wait for profile load (loading skeleton) rather than flash Coming soon, but never flash v3 for non-v3.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Deep link with crafted id/step into a check | Tampering | UUID validation in the route, ignore unknown params, unauthorized id resolves to NotFound |
| Replay of a queued record-as-bought (double tap, offline) | Tampering | mint ids once, pending-mutation duplicate guard, `record_decide_go` refuses "already decided" |
| Version-check bypass in D-15 (skipping a real conflict) | Tampering | only adjust `expectedVersion` when the row's version equals the accounted-for value; pgTAP case for a third-party change |
| Production DB write by an agent | Elevation | no `db push` outside the approved checkpoint; no Supabase MCP; preflight asserts project ref |
| Wrong answer from a stale or double-counted input (sales tax in extras, deposit twice) | Integrity (Core Value) | tests that tax/deposit only count via their fields; engine ignores `modelled_elsewhere` extras |
| Prescriptive/advice copy (store compliance) | Compliance | DCU-09 + V3 guards on every key |
