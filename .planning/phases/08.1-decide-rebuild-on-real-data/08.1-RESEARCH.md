## Summary

Everything 08.1 needs already has a home in the code. The work is mostly wiring and a few small, well-bounded engine and schema changes:

1. **D-05/D-06 (ready-by means "stays above $0").** `planReadyBy` (`src/engine/decide/v3/judge/judge.ts:735`) returns the day spare money covers day one plus the first payment. The cash path is already prepared once per check (`openCashPath`, `src/engine/decide/v3/cash/path.ts:126`) and the purchase is applied by `applyPurchaseFlows`. A fresh check on a later date needs the path re-opened from that date with the balance it would have then. Recommended: a pure helper `firstSafeStart(...)` in `src/engine/decide/v3/judge/readyBy.ts` that steps candidate start dates (each payday first, then the 1st of each month, up to 12 months), rolls the opening balance forward on the no-purchase path, re-opens a 90-day window and applies the purchase flows; the first candidate whose lowest point stays at or above $0 (and above the protected net, as the judge already requires) is the date. At most 12 candidates x 90 days: well inside the APP-05 budget, and only on `not_yet` answers.
2. **D-06.** If no candidate within 12 months passes, `readyBy = null` and a new fact `not_within_year` leads, with the cheaper option and Save for it as the two offered actions. The SN-27 guard (judge.ts:945, revision 06.9) stays: no date at all when the plan makes the usual month short.
3. **D-07.** The no-purchase path is already computed (the open path plus the opening balance). A new fact `below_zero_without { date }` is emitted when its lowest point within 90 days is below $0. It is a fact, never a code change: the answer code is unchanged.
4. **D-09 (expected line).** No "expected spending" record exists. Recommended shape: a column on `recurring_series`, `amount_kind text check (amount_kind in ('exact','expected')) default 'exact'`, written only through the series RPCs and `record_decide_go`. The month picture (`src/engine/month/picture.ts`) counts an expected series as `max(0, expected - actual spending in that series' category this month)`, so real spending replaces it and never double-counts. A new table was considered and rejected: expected lines need everything a series already has (cadence, category, account, undo, end_reason).
5. **D-10/D-11 (one save).** `record_decide_go` (latest body in `20261116000100_decide_go_end_reason.sql`) already ends series and writes rows in one transaction with one undo step. Grow's `record_debt_sale` (`20261106000300_grow_debt_plan_and_sale.sql:261`) writes the sale and the payoff. The new `record_decide_go` body calls the same internal steps (factored into a shared `private` function, not copied) when the save carries ticked `sale` / `payoff` items, and closes a linked goal the same way Grow closes a goal. One undo step covers all of it.
   **Two write paths today.** The live Bought screen (`screens/actions/BoughtScreen.tsx`, routed in `src/shell/decide/ActionRoutes.tsx`)
   saves through `useGoAheadV3` in `src/data/mutations/decideGoAhead.ts`. `buildBoughtWrite` / `useRecordBought` in `boughtWrite.ts`
   (which has `endSeriesOf`) is used only by `devHarness/BoughtWriteHarness.tsx`. Plan 07 must leave one writer: the screen's path
   gains everything (stops, recorded series, expected lines, sale, payoff, goal close), and the duplicate is removed.
6. **D-12 (household purchase shared).** `buildBoughtWrite` already applies `purchase.share` through `myShareOf`. A Household-scope purchase is instead written as one shared line (the full amount, `is_shared`, the household's default split resolved like any shared line); its running costs become shared series. A joint-account payment creates no owing (Phase 8 owing rules, unchanged).
7. **Household in Decide (D-01..D-03, carry-over 08-28/08-29).** 08-28's migration is re-dated to `20261123000200`. The snapshot builder (05.5) takes a `scope: 'me' | 'household'` input. `'me'` is today's behaviour (viewer's records and their share of shared lines, CMP-F19 viewer scoping). `'household'` adds the shared lines in full and each opted-in partner's rounded total from `partner_money_total` (both sides on), never their items. When no partner is on, the answer carries one caveat naming who has not shared.
8. **D-04 (Activity month total).** `useActivityViewModel.ts` sums full amounts. Home's Mine figure uses `countsForMe` / `myShareOfLine`. Activity's total and category subtotals switch to the same helper; rows keep their full amount with a "your share" label.
9. **APP-21 (server switches).** `app_config` (`20260922000200_app_config.sql`) is read at launch for `min_supported_version`. A `decide_off` key read the same way gives "off fast" (one update, no app release). "On slowly" is the existing per-account `profiles.decide_v3` plus `docs/ops/decide-testers.json` and the release gate (05.4-32). On a failed read the last known value is kept; a network error never turns Decide off.
10. **Build name in the footer (SC8).** No Decide footer shows the build name today; add it beside the legal footer for accounts on the tester list only.

## Architecture patterns to keep

- Engine purity (`src/engine` imports nothing from db, state, services, ui or react); depcruise enforces it.
- Engine changes: right-answer cases first (owner-approved), then failing tests, then code, then `DECIDE_ENGINE_REVISION` bump (`shadow/revision.ts`, lock rewritten with `REVISION_WRITE=1`) and a changed-answers review.
- Copy: every new string goes to `src/i18n/decideWordingSigned.json` sign-off; UX-19 (25 words, 3 numbers); declarative, never "you should".
- Member names only through the one resolver (08 D-32).
- Migrations dated after `20261122000900`; each push is an owner checkpoint with the FincWin token exported per command (never printed, no MCP), `npm run supabase:db:push`.

## Pitfalls

- **Revision churn.** Four plans change engine answers (D-05/D-06, D-07, household scope, FIN-12). One revision bump and one changed-answers review at the end (plan 08.1-13) avoids four owner reviews; each engine plan runs with `REVISION_WRITE` unset and records the expected lock failure in its SUMMARY.
- **Post-05.5 audit overlap.** The context says the build starts after 05.4-43 (mutation score) and 05.4-45 (nightlies) because D-05 touches the code those tests cover. Engine plans start with a gate that checks the audit is recorded; non-engine plans (migrations, Activity total, switches) do not wait.
- **Double counting expected lines.** An expected series and the real fuel transactions in the same category must never both count in full: the `max(0, expected - actual)` rule is property-tested.
- **Shared money spent twice.** `sharedMoneyFor` slices must sum to the total (property test, SC8 of Phase 8).
- **Old builds and new columns.** `amount_kind` has a default, so old builds keep reading `exact` series; no column is dropped in 08.1.
