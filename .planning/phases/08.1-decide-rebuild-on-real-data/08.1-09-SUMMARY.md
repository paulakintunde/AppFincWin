# Phase 08.1 Plan 09: Record as bought, client half Summary

Record as bought now has one writer. Under the purchase, every other part of the save is a tick row: running costs (a fixed one becomes a bill, a varying one becomes expected spending), the sale money in, the old loan's payoff, bills that stop, and closing the goal. Only "Close the goal" starts ticked; unticked parts are never sent; one save, one Undo. The month picture counts an expected line as max(0, expected - real spending in its category this month).

## What was built
- **One writer.** `goAheadInputOfV3` / `useGoAheadV3` (the path the screen already used) take an `extras` argument: `runningCosts`, `stops` + `recorded`, `sale`, `payoff`, `goalId`. `endSeriesOf` and `StoppableSeries` moved into `decideGoAhead.ts`. `boughtWrite.ts` (the second, harness-only builder), `mutationKeys.recordBought`, `registerRecordBoughtMutations` and its two test files are deleted. The dev harness now writes through `useGoAheadV3` (sample check + the engine's own Evaluation, `sampleEvaluation`). `grep` shows exactly one module defining `endSeriesOf`.
- **Fixed vs varying (D-09).** `RunningCostLine.varies?: boolean` (templates: fuel and maintenance true; insurance and registration false; user-added lines default fixed; survives `parseCheckV2`). A fixed line writes an exact bill series; a varying line writes a series with `amount_kind 'expected'`. Never a transaction (T-08.1-20).
- **Expected-line rule (engine, tests first).** `V3Series.amountKind` (read from `recurring_series.amount_kind` by `buildInputs`). `expectedDueCounts` (`month/model/expected.ts`) returns the amount each of this month's expected dues counts: `max(0, expected - paid, series-less spending in the same category this month)`, the category pool shared in date then id order so spending is never used twice; a line with no category, an exact series and later months count whole. The one map is read by `thisMonth` (billsDue) and by the open cash path (`openCashFlows`, via `prepare`), so `leftAfterPlans` and `afterBillsBeforePayday` agree. fast-check pins: never more than max(expected, actual); real spending at or above expected removes it; total counted = max(0, expected total - spent).
- **Tick rows (UI-SPEC section 5).** `BoughtSaveRows`: groups "Costs that start", "Money in and out", "Costs that stop", "Your goal" (empty groups omitted), one `ToggleRow` per item, spoken label = title, sub-line, "ticked"/"not ticked". `hapticTap` on tick and on Record purchase. The screen stays a screen (`DetailScreen`, Back, title focus); heading "Record as bought", date line "Bought on {{date}}." inside the date field, primary "Record purchase", then toast "Recorded: {{item}}." with the step so one Undo reverses everything. `RunningCostOffers` (the one-by-one offers after the save) is removed; the row tick is the confirmation.
- **Route.** `BoughtRoute` reads the recorded bills, the debts and the goals, passes `stopRows` (only a recorded bill that would really end), `payoff` (live, still owed loan the sale pays; amount = the sale up to what is owed) and `goal` (an open goal made by this check), and adds `recorded` to the save so the stops end bills with `end_reason: 'stopped'`.
- **Contract todos switched on.** `bo07.recordAsBought.contract.test.ts` holds the two exact titles as real tests (engine side: the expected map; source scan of the one writer). The manifest file `contractManifest.test.ts` is frozen by its own header and keeps passing untouched (todo to test needs no edit there). The builder-side proof is in `src/data/mutations/__tests__/decideGoAhead.test.ts`.
