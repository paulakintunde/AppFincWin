# Phase 08.1 Plan 25: One-earner fix (suggest equal shares) Summary

A member whose share of the joint money is $0 only because of the group's rule (What each person brings with no pay-ins and nothing carried, or the bill split at 0%) now gets a `share_zero_by_rule` line on their own answer and a named card on "How spending is shared"; both open the set-shares editor at equal shares, and only Save changes the rule. No answer moves.

## Owner answers built (2026-11-21, A for all five)

- **Q1 A (trigger):** `zeroShareMembers` (engine/household/zeroShare.ts, PURE) flags member i only when there are 2+ members and a joint account, shares are not out of date, the counted rule is bring or bill, `paidInBy[i]` is 0 on every joint account, their cash slice is 0, the counted joint money is above 0, and an equal split would give them more than 0. Private accounts are never read. `householdPlan` returns `zeroShare: { rule } | null` for the viewer; the app builder (householdScope.ts) and the right-answer fixture both pass it into `V3Household.zeroShare`.
- **Q2 A (words):** the answer line "Under {{rule}}, your share of the joint money is {{zero}} this month. With equal shares, each person counts the same part." with "See equal shares" and "Not now"; settings card "Under this rule, {{name}}'s share ...".
- **Q3 A (who sees it):** every member sees the settings card, which names the person (one, several, or "your share" when it is the viewer).
- **Q4 A (Not now):** hides the answer line on this phone until next month (AsyncStorage `fincwin:zero-share-not-now:{householdId}` = 'YYYY-MM'); it shows again next month if still true. The settings card cannot be hidden; it goes when the rule changes or the share is above $0.
- **Q5 A (cases and revision):** HH-35..HH-42 added as `approved` (approvedAt 2026-11-21); `DECIDE_ENGINE_REVISION = '07.2'`; lock rewritten once with `REVISION_WRITE=1`, then the revision test was green without it.

## Deviations from Plan

### Auto-fixed issues

1. **[Rule 1 - Bug] `percentsOf` threw on a split with a member at 0** (plan 23 code, spendRuleView.ts). `allocate` takes only positive weights, so a 100/0 bill split or a set split with a 0% member crashed "How spending is shared" (exactly the OE-07 household). Fixed: zero weights get 0 and 100 splits among the rest. Tests added. Commit f6c59bd9.
2. **[Rule 2 - Correctness] `{{zero}}` instead of a literal "$0"** in every new string, so a GBP/EUR/CAD household reads its own zero. `CAVEAT_VALUE_KEYS.share_zero_by_rule` declares `['rule', 'zero']`, as facts already do for `zero`.
3. **[Rule 2 - Privacy] Dismissal key uses the `fincwin:` prefix** (`fincwin:zero-share-not-now:{householdId}`) instead of the plan's `fincwin.zeroShare.notNow.{householdId}`, so `wipeDeviceData()` clears it on sign-out and account deletion.
4. **[Rule 3 - Blocking] Tests outside the plan's file list:** `copyContract.test.ts` (its corpus must emit every caveat, so it gains one share_zero_by_rule input) and `phaseGate.test.ts` (HH count 34 to 42, approved HH-07..HH-42).
5. **Pure part of the settings trigger lives in spendRuleView.ts** (`zeroShareIdsOf`), not useZeroShare.ts, because the hook's imports (useDecideV3 -> auth -> Google sign-in native module) cannot load in a screen test; useZeroShare.ts is the hook only.
6. **Extra key `settingsYou`** so the viewer is never written as "You's share"; `settingsNoName` (Q3 B only) was not added.
7. **ZeroShareLine derives the rule name from the caveat** and takes `{ householdId, caveat, currency, today }` (no `ruleName` prop); the screens read the target through `currentSuggestion()` so a test can swap it.
8. **Settings screen ignores joint bills accounts** for the trigger (their dues are not known there; plan 23's known gap), and leaves out accounts in another currency (no rate applied there).
