# Phase 08.1 Plan 11: FIN-12 "0% if paid in full" back-charge Summary

A "0% if paid in full" plan is now costed: when its payments run past the promotion's end date, the stated rate is charged back from day one and the answer, the plan card and the schedule carry that cost.

## What was built

- `plan/deferredInterest.ts`: `deferredInterest({asOf, schedule, promoEnd, rateAfter, country})`. Cleared (last payment on or before the end date) = no cost. Otherwise: each payment period up to the end date, interest on the balance left before that payment is summed (no compounding before the end date); it lands on the end date; the same payments then carry on at the stated rate. BR-25 worked: back-charge $196.80, $43.47 more after, $240.27 interest, $1,440.27 paid, 20 payments. Integer maths, half-up per period.
- `PayV2.plan` gets optional `promoEnd` and `rateAfter`. Present (even null) = the plan step asked for them. Absent = the old flag-only behaviour (fact `deferred_interest_term`), so stored checks and BR-14 are unchanged.
- `purchase.ts`: with the switch on and the fields asked for, a missing or past end date asks `promo_end_missing`; a missing rate after asks `plan_rate_missing` (never assumes 0%). Back-charge replaces the schedule (totalInterest, totalPaid, lastPaying, count, finalPayment) and adds fact `back_charge_cost { amount, date }`; cleared adds `promo_cleared { date }`.
- Plan sheet (`InstallmentPlanSheet`): "0% if paid in full" switch; when on, "Promotion ends" (date, existing picker) and "Rate if not paid in full" (percent) with the helper and the example-rate line; the plan rate field is replaced (apr is saved as 0). Inline errors (`Note tone="warn"`, role alert) on Use; result card shows a `tight` row with the stateTight glyph, the word "Warning" and the back_charge_cost sentence.
- Persistence: `toStoredV2` / `parseCheckV2` carry the two fields (rate as text).
- Right-answers: BR-24, BR-25, BR-26 approved 2026-11-20 and pass on the engine (none in knownRed).

## Deviations from Plan

1. **[Rule 3] Where the UI lives.** The plan said CostsStep has an existing "0% if paid in full" ToggleRow. It does not (CostsStep is the running-costs step; no such switch existed anywhere). The switch and fields were built in `InstallmentPlanSheet`, which owns the plan fields. CostsStep.tsx is unchanged.
2. **Cases in knownRed.** Task 1 left BR-24..26 as drafts (knownRed only holds approved cases). After approval the engine was built in the same pass, so they never needed knownRed. No separate red commit.
3. **BR-25 variant.** The account holds $500 but savings above the safety net cover the sofa, so the true answer is "Fits, but borrowing costs more" (borrowing_costs_more), not "Fits only by borrowing" as drafted. Case text and expected variant were corrected; figures unchanged.
4. **BR-24 fact.** The draft expected `back_charge_cost`; a cleared plan has no charge, so it carries the new fact `promo_cleared` (end date named) instead.
5. **New missing code** `promo_end_missing` (constants priority list, copy, answer "what is missing" label, PRICE_STEP_FIXES).
6. `periodsBefore` in schedule.ts is now exported; `deferredInterest` exported from the v3 barrel (barrel test updated).
